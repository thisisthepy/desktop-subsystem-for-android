# SPEC

이 문서는 Desktop Subsystem for Android의 요구사항과 수용 기준을 정의한다. 근거는 [INTENT.md](INTENT.md)에 있다.

- 상태 표기: `Draft`(합의 전), `Agreed`(구현 가능), `Done`(수용 기준 통과)
- 요구사항 ID는 한 번 부여하면 재사용하지 않는다. 폐기할 때는 `Withdrawn`으로 남긴다.
- 처음 판(2026-10-16)의 요구사항은 모두 `Draft`다. 소유자가 합의하면 `Agreed`가 되고, 그때부터 구현한다.
- 수치 목표는 실측 전 제안값이다. 측정 방법을 함께 적고, 실측 결과로 소유자가 확정한다.

## 1. 용어

| 용어 | 정의 |
|---|---|
| 호스트 | 사용자의 데스크톱 OS. 처음 대상은 Windows 11이다 |
| 게스트 | 전용 경량 VM에서 도는 안드로이드. Windows에서는 HCS로 만든 VM이다 |
| 동반 서비스 | 호스트에서 도는 DSA 프로세스. 세션 관리, 셸 통합, 합성기, 호스트 쪽 HAL 서비스를 맡는다 |
| 합성기 | 동반 서비스 안에서 게스트 태스크마다 호스트 창을 만들고 화면을 올리는 부분 |
| 에이전트 | 게스트의 시스템 앱. 앱 목록, 알림, Intent, 화면 상태, 입력 주입을 맡는다 |
| 제어 채널 | 동반 서비스와 에이전트 사이의 소켓 연결. 메시지는 PR-2의 프로토콜을 따른다 |
| 태스크 창 | 안드로이드 태스크 하나에 대응하는 호스트 창 |
| 세션 | 게스트 VM이 시작해서 종료할 때까지의 기간 |

## 2. 아키텍처

게스트 안드로이드는 64비트 전용(x86_64)으로 구성하며, 32비트 앱은 지원하지 않는다.

```
[안드로이드 전용 VM: 게스트]                       [Windows 호스트: 동반 서비스]
 앱 → SurfaceFlinger
   → 커스텀 hwcomposer ── 창 제어·입력 ──(vsock ↔ hvsocket)── 합성기: 태스크 창 (Win32)
   → ANGLE → Vulkan ──── Vulkan 원격 스트림 ─────────────────→ 호스트 Vulkan 실행, 결과 표시
 에이전트 ── 앱 목록·알림·Intent·IME ─────────────────────────→ 시작 메뉴·알림 센터·TSF
 HAL 서비스 ── 장치 메시지(proto3, vsock) ─────────────────→ 호스트 장치 (코덱·오디오·전원 …)
```

Linux 호스트:
- 안드로이드는 사용자마다 전용 crosvm VM에서 KVM 위로 돈다. 제어 채널, 로그, 파일 공유, adb는 vsock(vhost-vsock)으로 Hyper-V와 같은 포트를 쓴다.
- crosvm을 고른 이유: ChromeOS와 AVF가 안드로이드 게스트로 검증한 VMM이고, gfxstream을 일급으로 지원하고, virtio-balloon의 빈 페이지 보고로 게스트가 놓은 메모리를 호스트에 돌려준다.
- crosvm은 고정한 업스트림 리비전에서 CI가 빌드하고(gfxstream, balloon, vsock, virtio-net, minijail 샌드박스), DSA의 deb와 rpm 패키지가 그 바이너리를 싣는다. 사용자는 QEMU나 다른 VMM을 설치하지 않는다.
- 메모리(NFR-2): VM은 시작 크기(2 GiB)로 부팅하고, 최대 크기까지의 나머지는 virtio-mem 영역으로 둔다. 업스트림 crosvm에는 virtio-mem이 없어서, 이 저장소가 가진 패치를 빌드 스크립트가 고정 리비전에 적용한다. 게스트가 부족하면 virtio-mem의 요청 크기를 올려 메모리를 더하고, 더 쓰지 않으면 요청 크기를 내려 게스트가 뺀 블록을 호스트에 바로 돌려준다. 정책(풀린 메모리를 다음 확인에서 바로 돌려주는 즉시 반환과 필요할 때의 확장)은 Windows와 같은 `host/core`의 것이다. 게스트 커널은 memory_hotplug, memory hot-remove, virtio-mem, memmap_on_memory를 켜고 더한 메모리를 movable로 자동 온라인한다. 그래서 페이지 구조체는 게스트가 실제로 가진 메모리만큼만 잡힌다.
- 수용 기준(NFR-2, Linux): crosvm 인자는 `--mem`을 시작 크기로, `--virtio-mem`을 최대 크기와의 차이로 주고 `--init-mem`을 쓰지 않는다(`nfr2_the_linux_vm_boots_at_its_base_size_with_the_rest_as_virtio_mem`). `host/core`의 확장과 축소는 virtio-mem 요청 크기를 시작 크기와의 차이로 정하는 제어 소켓 명령이 되고, 첫 차분한 보고에서 바로 줄인다(`nfr2_memory_growth_sets_the_virtio_mem_request`). 게스트 커널 설정에 위 옵션이 있고 Linux 백엔드의 커널 명령줄에 `memory_hotplug.memmap_on_memory=1`이 있다(`test_nfr2_hotplugged_memory_holds_its_own_page_structs`). crosvm 패치의 장치는 요청 크기까지만 꽂기를 받고, 뺀 블록을 응답 전에 호스트에서 해제한다(패치 안의 단위 테스트).
- 네트워크(FR-28): NAT는 passt가 vhost-user로 crosvm에 붙는다. crosvm에는 Linux용 user-mode NAT가 없고 배포판의 passt는 vhost-user가 없을 수 있어서, 고정 리비전의 passt를 함께 빌드해 싣고 GPL 소스를 패키지에 둔다. 고급 네트워킹은 macvtap을 쓴다.
- 크기 조정, 일시 정지와 재개, 종료는 crosvm 제어 소켓 명령(`virtio-mem`, `suspend`, `resume`, `stop`)으로 한다.
- 수용 기준: CI의 KVM 작업이 공개된 안드로이드 이미지를 crosvm으로 부팅하고, 게스트가 vsock 제어 포트로 연결한다.
- 수용 기준(NFR-7): crosvm과 그것이 링크하는 모든 크레이트와 라이브러리가 서드파티 라이선스 목록에 오르고, 배포하는 crosvm 빌드에 GPL, LGPL, AGPL 구성 요소가 있으면 CI가 실패한다.

## 3. 기능 요구사항

### FR-1 커널 빌드 없는 설치 (`Agreed`)
사용자는 커널을 직접 빌드하지 않고 DSA를 설치할 수 있어야 한다.
- 게스트 VM의 커널은 프로젝트가 빌드해 함께 배포하고, binder(binderfs)는 그 커널에 내장한다. 사용자는 커널을 빌드하거나 교체하지 않는다.
- 사용자의 WSL 설정(`.wslconfig`)과 WSL 배포판은 건드리지 않는다.
- 설치는 Windows 설치 파일 하나로 끝난다. 필요한 Windows 기능(가상 머신 플랫폼)이 꺼져 있으면 무엇을 켜야 하는지 알려 준다.
- 수용 기준: 가상 머신 플랫폼만 켜 둔 깨끗한 Windows 11에서 설치 파일 하나를 실행해 FR-2의 세션을 시작할 수 있다. 사용자가 입력하는 명령은 없다. (수동 확인)
- 수용 기준: WSL 배포판이 있는 Windows 11에서 설치 전후로 `.wslconfig`가 같고, 배포판의 `uname -r`이 바뀌지 않는다. (수동 확인)
- 수용 기준: ashmem에 기대지 않는다. ashmem이 없는 커널에서 게스트가 부팅한다.
- 수용 기준: 프로그램을 제거하면 동반 서비스가 내려받은 이미지(FR-14)와 프로그램 설치 파일(FR-15)을 함께 지운다. 사용자의 안드로이드 디스크는 남긴다. (수동 확인)

### FR-2 세션 시작과 종료 (`Agreed`)
동반 서비스는 게스트 VM을 시작하고, 상태를 보고하고, 종료한다.
- 상태는 `Stopped`, `Starting`, `Active`, `Dozing`, `Frozen`, `Stalled`, `Stopping` 중 하나다(FR-10).
- 수용 기준: 시작 요청 뒤 안드로이드 부팅이 끝나고 에이전트가 제어 채널에 연결하면 상태가 `Active`가 된다. 그 전까지는 `Starting`이다. 제어 채널 연결만으로는 안드로이드를 쓸 수 있다는 뜻이 아니기 때문이다.
- 수용 기준: 게스트의 제어 채널 연결이 정해진 시간 안에 오지 않으면 `Stopped`로 돌아가고 원인을 보고한다.
- 수용 기준: 제어 채널은 연결됐지만 부팅 완료나 에이전트 연결이 정해진 시간 안에 오지 않으면 상태가 `Stalled`가 되고 원인을 보고한다. 게스트는 계속 실행되고, 원인이 사라지면 `Active`가 된다.
- 수용 기준: 종료 요청 뒤 게스트의 모든 프로세스가 끝나고(VM이 꺼지고) 상태가 `Stopped`가 된다.

### FR-3 태스크마다 호스트 창 (`Done`)
게스트 앱의 태스크 하나는 호스트 창 하나로 뜬다.
- 게스트는 freeform 모드로 돈다. 커스텀 hwcomposer가 태스크별 레이어 묶음을 합성기에 넘긴다.
- 합성기는 빠른 창 표시를 위해 사용자 세션에서 로그인 시점부터 백그라운드에서 실행되며, 프레임 스트림을 hvsocket으로 게스트에서 직접 받는다(INTENT D19).
- 태스크 창은 호스트의 일반 창이다. 이동, 스냅, 최소화, 최대화, 다중 모니터가 동작한다.
- 수용 기준: 앱 두 개를 실행하면 호스트 창 두 개가 뜨고, 각 창에는 자기 앱의 화면만 보인다.
- 수용 기준: 태스크 창을 닫으면 게스트 태스크도 끝나고, 게스트에서 태스크가 끝나면 태스크 창도 닫힌다.

### FR-4 창 크기 변경과 DPI (`Agreed`)
- 태스크 창 크기를 바꾸면 게스트 태스크 크기가 바뀌고, 앱이 새 크기로 다시 그린다. 창 크기를 바꾸는 동안 창은 앱이 그 크기로 그린 프레임과 함께만 바뀐다. 늘리거나 채우거나 잘라낸 그림을 보이지 않는다. 드래그를 끝낸 크기에 정확히 닿는다.
- 크기 단위는 두 플랫폼의 데스크톱 정의대로 환산한다. 안드로이드는 데스크톱 모니터에서 48 dp 터치 대상을 10.4 mm로 정한다(1 dp = 1/117.2인치, 안드로이드 16의 외부 디스플레이 기본 밀도). Windows의 DIP는 배율 s에서 1/96인치를 s배 한 것이다. 둘을 맞추면 배율 s인 모니터에서 안드로이드의 밀도는 131 × s dpi이고(반올림한 뒤 짝수로 내린다), 1 dp = 0.819 DIP다. 휴대폰 정의(1 dp = 1/160인치)를 쓰면 오브젝트가 지나치게 작아지고, 1 dp = 1 DIP(WSA)이면 터치용 크기 그대로라 지나치게 크다. ChromeOS(0.75), Mac Catalyst(0.77)도 이 범위의 값을 쓴다. WSA보다 나은 쪽을 택한 것이다(2026-11-11 소유자 결정).
- 글자는 오브젝트와 같은 비율을 따른다. 글꼴 배율은 1에 Windows의 텍스트 크기 설정(접근성 > 텍스트 크기)을 곱한 값이고, 글자만 따로 키우지 않는다. 글자만 키우면 dp로 높이를 정한 칸에서 글자가 넘치기 때문이다. 이렇게 하면 본문 16 sp가 약 13 DIP로 Windows와 macOS의 본문 크기와 비슷해진다. Windows의 텍스트 크기를 바꾸면 따라 바뀐다. 글꼴 변화를 직접 처리한다고 밝히지 않은 앱이 열려 있으면, 그 앱을 재시작하지 않도록 새 배율을 그 앱이 모두 닫힌 뒤에 적용한다. Windows에도 다시 시작해야 텍스트 크기를 따르는 앱이 있는 것과 같다. 손가락 터치에 맞춰 큰 안드로이드의 버튼은 Windows 크기로 줄고, 글자는 Windows와 같게 남는다.
- 안드로이드 14부터 1보다 큰 글꼴 배율에는 비선형 곡선이 걸려 큰 글자일수록 덜 커진다. Windows의 텍스트 크기를 100%보다 키웠을 때 제목 크기 글자가 덜 커지는 것은 이 때문이며, 곡선을 끄려면 프레임워크를 고쳐야 하므로 시스템 강제 방식과 함께 프레임워크 빌드가 승인된 뒤에 맞춘다.
- 안드로이드는 주 모니터의 배율에 맞는 밀도로 시작한다. 시작한 뒤 밀도가 바뀌면 그 변화를 처리하지 않는 앱은 안드로이드가 재시작시키므로, 처음부터 맞는 값으로 시작해 앱을 열자마자 재시작되는 일이 없게 하기 위해서다.
- 태스크 창이 배율이 다른 모니터로 가면, Windows의 "높은 DPI 크기 조정 수행 주체"처럼 앱마다 세 방식 중 하나로 맞춘다. 기본값(`auto`)과 시스템 방식은 앱을 재시작하지 않는다.
  - 앱: 그 태스크의 밀도를 새 모니터에 맞춰 바꾸고 앱이 다시 그린다. 매니페스트에 `configChanges`로 밀도 변화를 직접 처리한다고 밝힌 앱이 기본으로 이 방식이다. 처리한다고 밝히지 않은 앱에 사용자가 이 방식을 고르면, 안드로이드가 그 앱의 화면을 다시 만들고 화면 상태(스크롤, 입력한 글자)를 되살린다. Windows의 "응용 프로그램"처럼 늘 선명한 대신, 모니터를 옮길 때 잠깐 다시 그려질 수 있다.
  - 시스템: 태스크의 밀도는 그대로 두고, 호스트 합성기가 그 창의 그림을 새 모니터 배율에 맞게 늘이거나 줄인다. 밀도 변화를 처리한다고 밝히지 않은 앱이 기본으로 이 방식이다. 늘이면 글자가 조금 흐려질 수 있다.
  - 시스템 강제: 밀도 변화를 처리한다고 밝히지 않은 앱에도 재시작 없이 새 밀도를 넘겨 다시 그리게 한다. 안드로이드 프레임워크를 고쳐야 하므로 프레임워크 빌드가 승인된 뒤에 구현한다. 앱에 따라 화면이 깨질 수 있어 기본값으로 쓰지 않는다.
- 사용자는 설정 앱의 앱별 창 설정과 `dsa app-window <package> --dpi-scaling app|system|system-forced|auto`로 앱마다 방식을 고른다. 기본은 `auto`(위의 기본 규칙)다.
- 수용 기준: 창 크기를 바꾸면 새 크기로 그린 앱의 프레임이 창에 보일 때까지의 지연이 95%에서 200 ms 이하다(앱이 크기 구간을 넘어 화면을 다시 만드는 시간은 빼고). 호스트와 게스트 사이의 전송이 크기 변경 한 번에 더하는 몫은 모형 측정으로 CI에서 확인하고, 전체 지연은 실제 PC에서 잰다. 기능은 맞아도 지연이 커지는 회귀를 잡기 위해서다. (`fr4_a_resize_reaches_its_frame_within_budget`)
- 수용 기준: 크기를 끄는 동안 창 안에 빈 영역이 보이지 않는다. (수동 확인, 녹화로 기록)
- 수용 기준: 앱 방식의 앱은 100%와 200% 배율 모니터 사이를 옮겨도 글자가 흐려지지 않는다. (수동 확인)
- 수용 기준: 기본값과 시스템 방식의 앱은 배율이 다른 모니터로 옮길 때 재시작되지 않고, 어떤 앱도 안드로이드가 시작한 직후에 재시작되지 않는다(액티비티가 다시 만들어지지 않는다). 사용자가 앱 방식을 고른 앱은 새 밀도로 그린다. 시스템 방식 앱의 창은 새 모니터에서 같은 실제 크기로 보인다. (`fr4_moving_to_another_scale_never_relaunches_the_app`)
- 수용 기준: 안드로이드는 주 모니터 배율에 맞는 밀도로 시작한다(100%는 130 dpi, 150%는 196 dpi, 250%는 328 dpi처럼)이고, Windows 텍스트 크기 100%에서 글꼴 배율은 1이다. (`fr4_android_starts_at_the_main_monitors_density`)
- 수용 기준: Windows의 텍스트 크기를 바꾸면 안드로이드 앱의 글자 크기가 같은 비율로 바뀐다. 글꼴 변화를 처리하지 않는 앱이 열려 있으면 그 앱은 재시작되지 않고, 새 배율은 그 앱이 모두 닫힌 뒤 적용된다. (`fr4_text_follows_the_windows_text_size`)

### FR-5 포인터 입력 (`Agreed`)
- 마우스, 터치, 펜 입력을 게스트 입력으로 주입한다. 좌표는 태스크 창 기준으로 변환한다.
- Windows 11의 세 손가락, 네 손가락 터치 제스처가 켜져 있으면 Windows가 세 손가락 이상의 터치를 앱보다 먼저 가져간다. 앱이 자기 창에서만 이것을 끄는 공개 API는 없다. 그래서 설정 앱에 "DSA 앱 창에서 Windows 터치 제스처 끄기" 항목을 둔다. 켜면 DSA 태스크 창이 앞에 있는 동안만 그 제스처를 끄고, 다른 창이 앞에 오면 사용자의 원래 값으로 되돌린다. 멀티터치 게임과 그림 앱이 열 손가락까지 받게 하면서, 다른 앱의 제스처는 그대로 두기 위해서다. 기본값은 켬이다.
- DSA가 비정상으로 끝나 제스처가 꺼진 채 남으면, 다음 시작 때 원래 값으로 되돌린다. 제스처를 끄는 호출이 실패하면(문서에 없는 시스템 설정이라 Windows 업데이트로 바뀔 수 있다) 항목을 쓸 수 없게 하고, 이유와 Windows 설정의 터치 화면으로 가는 링크를 보인다. 터치 제스처가 없는 Windows(Windows 10, Server 2022)에서는 항목을 보이지 않는다.
- 수용 기준: 항목을 켜고 태스크 창에 열 손가락을 대면 열 개의 포인터가 태스크에 닿는다. 다른 창을 앞으로 가져오면 제스처 설정이 원래 값으로 돌아오고, 서비스를 강제로 끝낸 뒤 다시 시작해도 원래 값으로 돌아온다. 끄는 호출이 실패하면 항목이 비활성화되고 이유가 보인다. (`fr5_touch_gestures_are_off_only_while_a_task_window_is_in_front`)
- 마우스 휠은 스크롤로, 오른쪽 클릭은 길게 누르기가 아니라 보조 클릭으로 전달한다.
- 뒤로 가기: 마우스의 뒤로와 앞으로 단추는 안드로이드의 뒤로(`KEYCODE_BACK`)와 앞으로(`KEYCODE_FORWARD`)로 보낸다. ESC와, 글자 입력란에 초점이 없을 때의 Backspace는 먼저 앱에 보내고, 앱이 쓰지 않았을 때만 뒤로 가기가 된다. 게임처럼 그 키를 직접 쓰는 앱을 망가뜨리지 않기 위해서다. 그 태스크가 첫 화면(액티비티 쌓기의 맨 아래)에 있으면 ESC와 Backspace는 뒤로 가기를 하지 않는다. 키 하나로 창이 닫히거나 사라지지 않게 하기 위해서다.
- 수용 기준: 마우스 뒤로 단추는 `KEYCODE_BACK`으로, 앞으로 단추는 `KEYCODE_FORWARD`로 주입된다. 앱이 ESC나 Backspace를 쓰면 뒤로 가기가 일어나지 않고, 쓰지 않으면 뒤로 가기가 되며, 태스크가 첫 화면이면 아무 일도 없다. 글자 입력란에 초점이 있으면 Backspace는 글자를 지운다.
- 수용 기준: 태스크 창의 네 모서리를 누르면 게스트 앱이 받은 좌표가 화면 모서리와 2px 안에서 일치한다(모든 배율).
- 클릭 지연은 두 수로 따로 잰다. (가) 누름에서 첫 시각 반응(누름 표시나 리플이 그려진 첫 앱 프레임)이 호스트 창에 보이기까지, (나) 누름에서 다음 화면(새 액티비티의 첫 프레임)이 호스트 창에 보이기까지다. 리플은 Android가 처음 수십 ms 동안 거의 투명하게 그리므로, 하나의 수로는 반응이 늦은지와 화면 전환이 늦은지를 가를 수 없기 때문이다.
- 수용 기준: 설정 앱에서 목록 항목을 20번 클릭했을 때 (가)의 p90이 100 ms 이하이고, (나)의 p90이 300 ms 이하다. 목표는 중급 휴대폰이 내는 값에 맞춘다. 휴대폰의 터치에서 화면 반응까지는 75~168 ms(Agawi TouchMark, 2013), 터치 입력 자체는 10~35 ms(Android Developers Blog, 2021)로 측정되었고, 100 ms는 사용자가 즉시 반응으로 느끼는 한계다(Nielsen, Response Times). 화면 전환은 Material Design의 전환 시간(약 300 ms) 안에 새 화면이 나와야 한다. 측정은 `scripts/input-trace.py`의 `feedback`과 `next screen` 값으로 하고, 측정 환경(CPU, GPU, Windows 빌드, 이미지 버전)을 같이 적는다. (실제 PC에서 확인)

### FR-6 IME (`Agreed`)
- 텍스트 입력은 호스트 IME가 처리한다. 동반 서비스가 TSF로 조합을 받고, 에이전트가 앱의 `InputConnection`에 조합 중인 글자와 확정된 글자를 넣는다. 게스트의 키보드 앱은 쓰지 않는다.
- 조합 창은 게스트 앱의 커서 위치에 뜬다.
- 수용 기준: 한글 조합 체크리스트(조합, 자모 단위 백스페이스, 조합 중 커서 이동, 문장 중간 삽입, 확정 후 되돌리기)가 대표 앱 세 개(일반 `EditText`, Compose `TextField`, WebView 입력창)에서 통과한다. (수동 확인)

### FR-7 시작 메뉴와 작업 표시줄 (`Agreed`)
- 게스트에 설치된 런처 대상 앱마다 시작 메뉴 항목을 만든다. 이름과 아이콘은 게스트의 것을 쓴다.
- 앱마다 고유한 AppUserModelID를 준다. 작업 표시줄에서 앱별로 묶이고 앱의 아이콘으로 보인다.
- 앱을 지우면 시작 메뉴 항목도 지운다.
- 앱 아이콘은 안드로이드 홈 화면이 아니라 데스크톱 운영체제의 방식으로 다룬다. 바탕화면에 앱 바로 가기를 둘 수 있다(설정 앱의 앱 페이지, 앱 창의 작업 표시줄 단추 메뉴). 앱을 지우면 그 바로 가기도 지운다.
- 안드로이드 앱 바로 가기(`ShortcutManager`의 정적, 동적 바로 가기, 예: 메신저의 새 채팅)는 Windows 점프 목록의 작업으로 보인다. 작업 표시줄 단추와 시작 메뉴 항목을 오른쪽 단추로 누르면 나온다. 앱이 바로 가기를 바꾸면 점프 목록도 바뀐다. 앱이 바탕화면 고정을 요청하면(`requestPinShortcut`) 사용자에게 묻고 바탕화면 바로 가기를 만든다. macOS는 Dock 메뉴, Linux는 데스크톱 항목의 동작(`Actions`)으로 같은 것을 보인다.
- 수용 기준: 앱 하나를 설치하면 시작 메뉴에 나타나고, 실행하면 작업 표시줄에 그 앱 아이콘으로 따로 묶이며, 지우면 시작 메뉴에서 사라진다.
- 수용 기준: 앱이 낸 바로 가기가 그 앱의 점프 목록에 이름과 아이콘으로 보이고, 누르면 그 바로 가기의 화면이 태스크 창으로 열린다. 바탕화면 고정 요청은 확인 뒤 바탕화면 바로 가기가 되고, 앱을 지우면 함께 사라진다. (`fr7_app_shortcuts_are_jump_list_tasks_and_desktop_shortcuts`)
- 수용 기준: Windows 검색에 앱 이름을 입력하면 그 앱이 나오고, 누르면 안드로이드가 꺼져 있어도 켜진 뒤 그 앱이 태스크 창으로 뜬다.

### FR-8 알림 (`Agreed`)
- 게스트 알림을 호스트 알림 센터로 보낸다. 제목, 본문, 앱 이름, 아이콘을 싣는다.
- 알림을 누르면 그 알림의 `PendingIntent`를 게스트에서 실행하고, 결과 태스크가 태스크 창으로 뜬다.
- 게스트에서 알림이 지워지면 호스트에서도 지운다.
- 수용 기준: 태스크 창이 하나도 없는 `Dozing` 상태에서 우선순위가 높은 알림이 도착하면 호스트 알림으로 뜨고, 누르면 앱이 열린다.

### FR-9 링크와 파일 연결 (`Agreed`)
- 게스트 앱이 `http`/`https` 링크를 열면 호스트 기본 브라우저로 연다. 사용자가 원하면 게스트 앱으로 열 수도 있다.
- 호스트에서 파일을 게스트 앱으로 열 수 있다(공유와 열기).
- 수용 기준: 게스트 앱에서 웹 링크를 누르면 호스트 기본 브라우저에 그 주소가 열린다.

### FR-10 수명 주기 단계 (`Agreed`)
INTENT D7의 네 단계를 구현한다.
- 안드로이드 태스크 창이 모두 닫히거나 최소화되면 에이전트가 게스트에 화면 꺼짐을 알리고 Doze로 들어가게 한다. 창이 하나라도 다시 보이면 화면 켜짐으로 돌아간다.
- 호스트의 배터리 상태와 절전 상태를 게스트 배터리 상태에 반영한다.
- 호스트의 배터리 절약 모드(Windows의 에너지 절약, macOS의 저전력 모드, Linux의 절전 전원 프로필)가 켜지면 게스트 화면의 갱신 상한을 60Hz로 내린다. 모니터가 60Hz 이하이면 그대로다. 절약 모드가 꺼지면 모니터의 주사율로 돌아간다. 사용자가 모드를 고르지 않아도 호스트의 전원 정책을 따라 배터리를 아끼기 위해서다. 따로 고르는 성능 모드는 두지 않는다. 메모리와 CPU는 이미 상태에 따라 자동으로 늘고 준다.
- freeze는 사용자가 고른 경우나 설정한 시간 동안 쓰지 않은 경우에만 들어간다. 기본값은 freeze를 쓰지 않는 것이다.
- 수용 기준: 창을 모두 닫고 정해진 시간이 지나면 상태가 `Dozing`이 되고, 게스트의 `deviceidle` 상태가 idle이다.
- 수용 기준: `Dozing`에서 창을 열면 1초 안에 상태가 `Active`가 된다.
- 수용 기준: 120Hz 모니터에서 호스트의 배터리 절약 모드를 켜면 1초 안에 게스트 화면의 갱신 상한이 60Hz가 되고, 끄면 120Hz로 돌아온다. 60Hz 모니터에서는 바뀌지 않는다. (`fr10_battery_saver_caps_the_guest_refresh_rate`)
- 절전 상태는 배터리 절약 모드와 호스트의 절전·최대 절전(모던 스탠바이 포함)을 함께 뜻한다. 호스트가 잠들기 직전에 게스트에 알리면, 게스트는 화면을 끄고 Doze로 들어가며 디스크에 쓸 내용을 모두 내려쓴 뒤 준비됐다고 답한다. 호스트는 그 답을 잠깐(최대 2초)만 기다린다. 호스트가 깨어나면 게스트에 호스트의 현재 시각을 보내 게스트 시계를 맞추고, 잠들기 전 화면 상태로 되돌린다. 잠든 동안의 시간은 freeze와 부팅 시한에 세지 않는다. 깨어날 때 게스트가 얼어 있거나 연결이 끊겨 있으면 시각은 녹은 뒤나 다시 연결된 뒤에 보낸다.
- 수용 기준: `Active` 상태에서 호스트가 잠들면 게스트가 화면 꺼짐과 잠듦 알림을 받고, 게스트가 디스크를 내려쓴 답을 보내면 호스트의 대기가 끝난다. 답이 없어도 대기는 2초 안에 끝난다.
- 수용 기준: 호스트가 깨어나면 게스트가 호스트 시각(1초 이내 오차)을 받고, 잠들기 전 `Active`였으면 1초 안에 다시 `Active`, `Dozing`이었으면 `Dozing`으로 남는다. 제어 채널은 그대로 쓰이거나 다시 연결된다.

### FR-11 APK 설치 (`Agreed`)
- 호스트에서 APK 파일을 열거나 동반 앱으로 끌어다 놓으면 게스트에 설치한다. 설치 결과와 실패 이유를 보여 준다.
- 수용 기준: 서명이 올바른 APK를 열면 설치되고 FR-7에 따라 시작 메뉴에 나타난다.
- 탐색기에서 APK 파일을 열거나 동반 앱에 끌어다 놓으면 APK 설치 창이 열린다. 이 창은 설정 앱의 일부가 아니라 따로 된 앱 "APK 설치 관리자"(영어 "APK Installer")의 창이다. 이 앱은 자기 실행 파일, 창 제목, 작업 표시줄 아이콘과 AppUserModelID를 가지며, `.apk` 파일 연결과 "연결 프로그램" 항목이 이 앱을 가리킨다. 이 창의 배치는 Windows의 앱 설치 관리자(MSIX App Installer)를 따른다. 위에서 아래로 다음과 같다. 제목 표시줄에는 왼쪽에 글자만 있고 아이콘은 없다. 왼쪽에 큰 제목 `Install <앱 이름>?`이 있고, 바로 아래에 보통 글자색으로 `Package Name: `, `Publisher: `, `Version: `, `Source: ` 줄이 이 순서로 있다. `Source`는 APK를 받은 곳이다. 파일의 Zone.Identifier에 HostUrl이나 ReferrerUrl이 있으면 그 호스트이고, 없으면 파일이 있는 폴더 경로다. 오른쪽 위에는 앱 아이콘이 옅은 회색을 채운 약 106 px 둥근 타일 안에 있다. 아이콘의 모서리도 둥글고, 투명한 모서리가 검게 보이지 않는다. 그 아래 `Capabilities (개수):`와 처음 세 권한의 회색 글머리표 줄, `More` 링크가 있다. `More`를 누르면 창 안의 스크롤 영역에 나머지가 펼쳐지며, 권한마다 설명과 원래 이름을 보여 주고 "Android가 먼저 묻습니다" 표시도 그 안에 있다. 경고 상자는 App Installer의 InfoBar 모양이다. 굵고 짧은 제목 줄 아래에 본문이 있고, 경고 아이콘은 왼쪽에서 제목 줄에 맞추며, 글자는 한 열로 놓인다. 맨 아래 줄은 구분선과 띠 없이 왼쪽에 "준비되면 실행" 확인란, 오른쪽에 강조색 설치 단추와 취소 단추가 이 순서로 같은 너비로 있다. 구분선과 섹션 머리글 스타일은 어디에도 쓰지 않는다. "앱을 Android에 설치합니다" 같은 덧붙인 문장은 없다. `Install <앱 이름>?`, `Package Name`, `Publisher`, `Version`, `Source`, `Capabilities`, `More`는 모든 언어에서 영어로 둔다. 진행 화면과 완료·실패 화면도 같은 자리에서 바뀐다. 밝은 테마와 어두운 테마, 글꼴, 단추는 Windows 11 스타일을 따른다.
- 창은 안드로이드를 시작하기 전에 호스트에서 APK 파일을 읽어 정보를 채운다. 앱 이름과 아이콘, 패키지 이름, 버전 이름과 버전 코드, 파일 크기, 최소·대상 안드로이드 버전, 요청하는 권한(사람이 읽을 수 있는 이름), 서명 인증서 지문을 보여 준다.
- 같은 패키지가 이미 설치돼 있으면 새 설치인지, 업데이트인지(설치된 버전과 새 버전을 함께 보여 준다), 버전 내림이나 서명 불일치인지 알린다. 서명이 다르면 안드로이드처럼 설치를 막고 이유를 설명한다. 버전 내림도 막는다.
- 단추는 설치(업데이트면 업데이트)와 취소다. 설치가 끝나면 열기(앱의 태스크 창을 연다)와 닫기를 보여 준다. 실패하면 이유를 쉬운 말로 보여 준다.
- 안드로이드가 돌고 있지 않으면 설치 과정에서 시작하고, 그 단계를 창에 보여 준다.
- 수용 기준: 서명이 올바른 APK를 두 번 누르면 설치 창이 열리고, 파일에서 읽은 앱 이름, 아이콘, 버전, 권한을 보여 준다.
- 수용 기준: 설치를 누르면 진행 화면을 거쳐 열기 단추가 있는 완료 화면으로 끝난다.
- 수용 기준: 이미 설치된 앱의 새 버전이면 설치된 버전과 새 버전을 모두 보여 주고 단추가 업데이트다. 서명이 다르거나 버전이 낮으면 설치를 막고 이유를 보여 준다.
- 수용 기준: 설치가 실패하면 실패 화면이 그 이유를 쉬운 말로 보여 준다.
- 분할 APK 묶음도 설치한다. 큰 앱은 분할 APK로만 배포되는 경우가 많기 때문이다. 받는 형식은 `.xapk`(APKPure, `manifest.json`과 OBB를 담기도 한다), `.apks`(bundletool, SAI), `.apkm`(APKMirror)이다. 형식은 확장자만이 아니라 파일 내용으로 알아본다. 탐색기 연결, 끌어 놓기, 명령줄이 모두 같은 형식을 받는다.
  - 묶음 안의 분할 중 이 기기에 맞는 것만 골라 설치 세션 하나로 설치한다. 기본 APK는 늘 넣고, ABI 분할은 FR-25의 x86 우선 규칙으로, 화면 밀도 분할은 기기 밀도에 가장 가까운 것으로, 언어 분할은 기기 언어와 영어로 고른다. 기능 분할은 모두 넣는다.
  - OBB 파일이 있으면 설치 뒤 `Android/obb/<패키지>/`에 복사한다.
  - 창은 기본 APK에서 앱 정보를 읽어 보이고, 고른 분할의 개수와 전체 크기를 함께 보인다. 서명은 모든 분할이 같아야 하고, 다르면 설치를 막고 이유를 보인다.
  - 암호화되어 읽을 수 없는 묶음(일부 옛 `.apkm`)은 그 이유를 보이고 설치하지 않는다.
- Android App Bundle(`.aab`)은 설치하지 않는다. 스토어에 올리는 형식이라 바로 설치할 수 없고, 바꾸려면 다른 키로 다시 서명해야 해서 원래 배포처의 업데이트를 받을 수 없게 되기 때문이다. 열면 그 이유와 APK를 받으라는 안내를 보인다.
- 수용 기준: 가짜 `.xapk`, `.apks`, `.apkm`에서 기본 APK와 이 기기에 맞는 ABI, 밀도, 언어 분할만 골라지고, 서명이 다른 분할이 있으면 거부된다. `.xapk`의 OBB는 정해진 경로로 간다. `.aab`와 암호화된 묶음은 각자의 이유로 거부된다.
- 수용 기준: 실제 PC에서 APKPure의 `.xapk`(예: Chrome)를 두 번 누르면 설치 창이 앱 정보와 분할 개수를 보이고, 설치하면 앱이 열린다. (수동 확인)

### FR-12 바탕화면 위젯 (`Agreed`)
- 에이전트가 `AppWidgetHost`가 되어 사용자가 고른 위젯을 그린다. 위젯 하나는 테두리 없는 호스트 창 하나로, 바탕화면 층에 붙는다.
- 위젯 창 크기를 바꾸면 위젯에 새 크기를 알리고, 위젯이 크기별 레이아웃을 가지면 그에 맞춰 다시 그린다.
- 위젯을 누르면 그 `PendingIntent`를 실행한다.
- 위젯을 꾹 누르면(터치나 펜으로 길게 누르거나, 마우스 왼쪽 단추를 누른 채 0.5초 머물면) 안드로이드 홈 화면처럼 위젯을 편집한다. 위젯이 살짝 들리며 테두리와 크기 조절 손잡이가 보이고, 그대로 끌면 옮기고, 손잡이를 끌면 위젯이 허용하는 크기 안에서 크기를 바꾼다. 함께 뜨는 메뉴는 위젯 설정(위젯이 다시 설정할 수 있다고 밝힌 경우), 크기 조절, 제거다. 위젯 설정은 그 위젯의 설정 화면을 앱 창으로 다시 열고, 마치면 위젯에 반영한다. 바탕화면을 안드로이드 홈 화면처럼 쓰게 하기 위해서다.
- 사용자는 DSA 설정 앱에서 위젯을 골라 바탕화면에 두고, 둔 위젯을 뺀다. 명령줄(`dsa widgets`)만으로 위젯을 다루게 두지 않는다.
- 수용 기준: 시계 위젯 하나를 바탕화면에 두면 `Dozing` 상태에서도 시각이 갱신된다.
- 수용 기준: 설정 앱의 위젯 페이지는 설치된 안드로이드 앱이 제공하는 위젯을 모두 보여 준다. 항목마다 앱 이름, 위젯 이름, 미리 보기 이미지(없으면 앱 아이콘), 기본 크기를 보인다.
- 수용 기준: 위젯을 고르면 바탕화면에 놓인다. 앱이 설정 화면(configure 액티비티)을 가지면 그 화면을 먼저 띄우고, 사용자가 마친 뒤 놓는다.
- 수용 기준: 위젯 페이지는 놓인 위젯을 보여 주고, 거기서 뺄 수 있다.
- 수용 기준: 놓인 위젯 창을 오른쪽 단추로 누르면 제거와 크기 조정 메뉴가 나온다.
- 수용 기준: 위젯을 꾹 누르면 편집 상태가 되어 끌어서 옮기고 손잡이로 크기를 바꿀 수 있고, 다시 설정할 수 있는 위젯은 메뉴의 위젯 설정이 그 설정 화면을 열어 마친 결과가 위젯에 반영된다. 다시 설정할 수 없는 위젯에는 그 항목이 없다. (`fr12_long_pressing_a_widget_edits_it_like_a_home_screen`)
- 수용 기준: 위젯을 두거나 빼면 설정 앱과 바탕화면에 다시 시작하지 않고 반영된다.

### FR-13 클립보드 (`Agreed`)
- 호스트와 게스트의 텍스트 클립보드를 양방향으로 맞춘다. 이미지는 계획 단계다.
- 클립보드 공유는 설정에서 끌 수 있다. 기본값은 켬이다.
- 수용 기준: 호스트에서 복사한 텍스트를 게스트 앱에 붙여 넣을 수 있고, 반대도 된다.

### FR-14 안드로이드 버전 지원과 자동 업데이트 (`Agreed`)
안드로이드 최신 메이저 버전과 그 바로 전 버전, 두 개를 지원하고, 이미지를 자동으로 업데이트한다(INTENT D14).
- 같은 메이저 버전의 보안 업데이트와, 다음 메이저 버전으로의 업그레이드를 동반 서비스가 받아 적용한다. 적용 전후를 사용자에게 알린다.
- 지원이 끝나는 버전을 쓰는 사용자는 다음 지원 버전으로 올린다. 메이저 버전을 내리는 업데이트는 없다(안드로이드가 데이터의 버전 내림을 지원하지 않는다).
- 이미지는 프로젝트 키로 서명하고, 서명을 확인한 뒤에만 적용한다.
- 받은 이미지는 사용자가 다시 시작하지 않아도 적용한다. 열린 앱 창이 없으면(`Dozing`) 바로 안드로이드를 새 이미지로 다시 시작하고, 끝나면 알린다. 앱 창이 열려 있으면 알림으로 묻고 [지금 다시 시작]과 [나중에]를 둔다. 나중에를 고르거나 답하지 않으면, 다음에 창이 모두 닫혀 `Dozing`이 될 때 적용한다. 설정 앱의 업데이트 페이지에도 [지금 다시 시작]을 둔다. 앱을 쓰는 도중에 묻지 않고 끄지 않으면서, 사용자가 손대지 않아도 업데이트가 끝나게 하기 위해서다.
- 설정 앱과 `dsa settings set image-auto-restart on|off`로 자동 다시 시작을 끌 수 있다. 기본은 켬이다. 끄면 받은 이미지는 다음에 사용자가 안드로이드를 시작할 때 적용한다.
- 수용 기준: 서명이 없거나 맞지 않는 이미지, 지원 목록에 없는 버전, 메이저 버전을 내리는 이미지는 적용하지 않고 이유를 보고한다.
- 수용 기준: 새 이미지를 받았을 때 열린 앱 창이 없으면 안드로이드가 새 이미지로 다시 시작하고 알림이 뜬다. 앱 창이 열려 있으면 다시 시작하지 않고 묻는 알림이 뜨며, [지금 다시 시작]을 누르거나 창이 모두 닫혀 `Dozing`이 되면 적용된다. 자동 다시 시작을 끄면 다음 시작까지 적용되지 않는다. (`fr14_a_downloaded_image_is_applied_without_the_user_restarting`)
- 수용 기준: 새 이미지가 정해진 시간 안에 부팅을 마치지 못하면 이전 이미지로 되돌리고 세션을 다시 시작한다.
- 수용 기준: 직전 메이저 버전에서 최신 버전으로 업그레이드한 뒤 설치한 앱과 그 데이터가 남아 있다. (수동 확인)

#### 안드로이드 버전 선택
사용자는 지원하는 두 메이저 버전 가운데 하나를 고른다. 앱이 한쪽 버전에서만 동작하는 경우가 있기 때문이다.
- 지원하는 메이저 버전(지금은 16과 17)은 코드의 한 곳(`dsa/android-versions.json`)에만 적는다. 호스트, 릴리스 도구(이미지 목록을 만드는 워크플로)와 README의 지원 버전 문장이 그 파일을 따르고, 검사가 어긋남을 잡는다.
- 이미지 채널은 메이저 버전마다 하나다. 기본은 "최신 따르기"로, 지금처럼 가장 새 지원 메이저 버전을 따른다. 메이저 버전을 고르면 그 버전의 보안 업데이트만 받는다. 고른 값은 이미지 저장소의 `state.json`에 둔다. 설치 프로그램은 최신 메이저 버전을 넣고 "최신 따르기"로 둔다.
- 설정 앱의 "안드로이드" 페이지와 `dsa android version`은 실행 중인 안드로이드의 메이저 버전, 빌드, 보안 패치 수준, 고른 채널, 지원 버전 목록, 진행 중인 전환을 보인다.
- 설정 앱과 `dsa android use <메이저>`(또는 `latest`)로 버전을 바꾼다. 바꾸면 기존 이미지 업데이트 경로(서명 확인, 내려받기, 해시 확인, 시험 부팅, 실패 시 되돌리기)로 그 버전의 이미지를 받아 다음 시작부터 쓴다. 이미지는 컴퓨터의 모든 사용자가 함께 쓰므로 바꾸기는 관리자만 한다.
- 사용자 데이터는 위로만 옮긴다. 더 낮은 메이저 버전으로 옮기려면 데이터 초기화(FR-31)가 따라야 하고, 설정 앱은 지워지는 것(설치한 앱, 계정, 앱 데이터, 이 컴퓨터의 다른 사용자 데이터 포함)을 적은 확인 창을 거친다. `dsa android use`는 `--erase-data` 없이 낮은 버전을 거부한다. 낮은 이미지로 처음 부팅할 때 더 높은 메이저 버전의 데이터를 가진 디스크는 새 디스크로 바뀐다.
- 새 메이저 버전이 나와 고른 버전이 지원 목록에서 빠지면, 업데이트 서비스가 그 사용자를 다음 지원 메이저 버전으로 올리고 채널도 그 버전으로 바꾸며 알린다.
- 수용 기준: 채널을 한 메이저 버전에 두면 더 높은 메이저 이미지가 있어도 그 버전의 더 새 빌드만 적용한다. "최신 따르기"는 가장 새 지원 메이저로 올린다.
- 수용 기준: 더 높은 메이저를 고르면 다음 확인에서 그 이미지를 받아 시험 부팅에 올린다. 더 낮은 메이저는 데이터 초기화 확인 없이는 거부하고 이유를 보고하며, 확인하면 그 이미지를 받고 다음 부팅 전에 더 높은 버전의 데이터 디스크를 새것으로 바꾼다.
- 수용 기준: 고른 메이저가 지원 목록에서 빠지면 다음 확인이 채널을 다음 지원 메이저로 옮기고 그 이미지를 적용한다.
- 수용 기준: 버전 조회가 실행 중인 이미지의 메이저, 빌드, 보안 패치와 지원 목록을 돌려주고, 관리자가 아닌 호출자의 바꾸기는 거부한다.
- 수용 기준: README의 지원 버전 문장, 이미지 워크플로의 버전 목록과 `inputs.json`이 `dsa/android-versions.json`과 맞지 않으면 검사가 실패한다.
- 수용 기준: 실제 Windows에서 설정 앱으로 16과 17 사이를 오가면, 올릴 때는 앱과 데이터가 남고 내릴 때는 확인 창 뒤 데이터가 초기화된다. (수동 확인)

### FR-15 프로그램 자동 업데이트 (`Agreed`)
동반 서비스가 서명된 프로그램 목록을 확인해 새 버전의 설치 파일을 받아 적용한다(INTENT D18).
- 목록은 프로젝트 키로 서명하고, 설치 파일은 목록에 적힌 크기와 SHA-256이 맞을 때만 실행한다.
- 어떤 사용자의 안드로이드도 돌고 있지 않을 때 적용한다. 돌고 있으면 미루고, 사용자가 `dsa update`로 바로 적용할 수 있다. 적용 전후를 사용자에게 알린다.
- 버전을 내리는 업데이트는 없다. 설정으로 업데이트를 끌 수 있다.
- 업데이트 채널은 정식과 프리릴리스 둘이다(INTENT D18). 설정 앱과 `dsa settings`에서 프리릴리스도 받을지 고른다. 처음 값은 설치한 버전을 따른다. 프리릴리스 설치 파일로 설치했으면 프리릴리스를 받고, 정식 설치 파일로 설치했으면 정식만 받는다. 1.0 전에는 모든 릴리스가 프리릴리스이므로, 처음 값이 지금 사용자의 업데이트를 끊지 않게 하기 위해서다.
- 서명된 프로그램 목록은 채널마다 하나씩 낸다. 정식 채널은 정식 목록만 보고, 프리릴리스 채널은 두 목록 가운데 더 높은 버전을 고른다. 이미지 업데이트(FR-14)는 채널과 상관없다.
- 릴리스 절차는 1.0보다 낮은 버전을 GitHub 프리릴리스로 내고 프리릴리스 목록에만 올린다. 1.0부터는 릴리스할 때 어느 채널로 낼지 고른다.
- 릴리스 워크플로는 실행한 브랜치로 낼 수 있는 채널을 정한다(INTENT D18). `main`은 1.0 전에는 프리릴리스, 1.0부터는 정식이나 프리릴리스를 낸다. `develop`은 프리릴리스만 낸다. 다른 브랜치나 태그에서 실행하면 아무것도 내지 않고 이유를 남긴다.
- Linux에서는 패키지 저장소도 정식과 프리릴리스 두 갈래로 내고, 설정을 바꾸면 패키지가 등록한 저장소 항목이 고른 채널을 가리키도록 바뀐다.
- 수용 기준: 서명이 없거나 맞지 않는 목록, 크기나 해시가 맞지 않는 설치 파일, 지금과 같거나 낮은 버전은 적용하지 않고 이유를 보고한다.
- 수용 기준: 안드로이드가 돌고 있는 사용자가 있으면 적용을 미루고, 모두 멈추면 적용한다. `dsa update`는 기다리지 않고 적용한다.
- 수용 기준: 업데이트를 끈 설정에서는 목록을 확인하지 않는다.
- 수용 기준: 정식 채널에서는 프리릴리스 목록에만 있는 더 높은 버전을 적용하지 않고, 프리릴리스 채널에서는 적용한다. 두 목록에 모두 있으면 높은 쪽을 적용한다.
- 수용 기준: 프리릴리스 채널에서 정식 채널로 바꾸면 지금 버전을 내리지 않고, 정식 목록이 더 높은 버전을 낼 때까지 기다린다.
- 수용 기준: 프리릴리스 설치 파일로 처음 설치하면 채널이 프리릴리스이고, 정식 설치 파일로 설치하면 정식이다. 업그레이드는 사용자가 고른 채널을 그대로 둔다.
- 수용 기준: 릴리스 워크플로는 1.0보다 낮은 버전을 GitHub 프리릴리스로 내고, 그 버전을 프리릴리스 목록에만 올린다.
- 수용 기준: 릴리스 워크플로를 `develop`에서 정식 채널로 실행하거나, `main`과 `develop`이 아닌 브랜치에서 실행하면 게시 전에 실패하고 이유를 남긴다. `main`에서 1.0 이상을 정식으로 실행하면 정식으로 낸다. (`fr15_the_release_branch_decides_the_channel`)
- 수용 기준: 실제 Windows에서 이전 버전을 설치해 두면 서비스가 새 버전으로 올리고 다시 시작한다. 설치가 실패하면 이전 버전이 남고 이유를 보고한다. (수동 확인)

#### macOS 패키지와 업데이트
macOS에서도 서비스가 Windows와 같은 방식으로 프로그램을 올린다(INTENT D18). 지금 macOS에는 프로그램 업데이트가 없어서, 고친 내용이 사용자에게 닿으려면 사용자가 새 pkg를 직접 받아야 하기 때문이다.
- 릴리스는 macOS용 pkg와 dmg를 함께 내고, 채널마다 macOS용 서명된 프로그램 목록을 둔다. 목록은 Windows 목록과 같은 형식(버전, 주소, 크기, SHA-256, 프로젝트 키 서명)이다. 채널, 처음 값, 버전을 내리지 않는 규칙은 위와 같다.
- 사용자의 launchd 에이전트인 서비스가 목록을 확인하고 pkg를 받는다. 목록의 서명, 크기, SHA-256이 맞고, pkg가 프로젝트의 Developer ID 설치 인증서로 서명되고 Apple 공증(notarization)을 거친 것일 때만 설치한다.
- 그 사용자의 안드로이드가 돌고 있지 않을 때 적용한다. 돌고 있으면 미루고, 사용자는 `dsa update`나 설정 앱으로 바로 적용할 수 있다. 설치에는 관리자 권한이 필요하므로, 시스템의 권한 대화상자로 관리자 암호를 묻는다. 사용자가 거절하면 설치하지 않고 다음 확인 때 다시 묻는다. 적용 전후를 알림으로 알린다.
- 설치는 서비스와 따로 떨어진 프로세스가 한다. 설치가 DSA.app을 바꾼 뒤 launchd 에이전트를 다시 띄운다. 설치가 실패하면 이전 DSA.app이 그대로 남고 이유를 알린다.
- 설정으로 업데이트를 끌 수 있고, 끈 동안에는 목록을 확인하지 않는다.
- 배포에는 프로젝트의 Apple Developer ID(응용 프로그램 인증서와 설치 인증서)와 공증 자격이 필요하다. 없으면 Gatekeeper가 받은 pkg를 막으므로, 이 업데이트는 그 자격을 갖춘 뒤 켠다.
- 수용 기준: 서명이 없거나 맞지 않는 목록, 크기나 해시가 맞지 않는 pkg, Developer ID 서명이나 공증이 없는 pkg, 지금과 같거나 낮은 버전은 설치하지 않고 이유를 보고한다.
- 수용 기준: 안드로이드가 돌고 있으면 적용을 미루고, 멈추면 적용한다. `dsa update`는 기다리지 않는다. 관리자 암호를 거절하면 설치하지 않고 이전 버전이 남는다.
- 수용 기준: 정식 채널과 프리릴리스 채널의 목록 선택이 Windows와 같다.
- 수용 기준: 실제 Mac에서 이전 버전을 설치해 두면 서비스가 새 버전을 받아, 관리자 암호를 넣은 뒤 DSA.app을 바꾸고 에이전트를 다시 띄운다. 설치가 실패하면 이전 버전이 남고 이유를 보고한다. (수동 확인)

#### Linux 패키지와 업데이트
Linux에서는 위의 서명된 프로그램 목록 대신 시스템 패키지 관리자가 DSA를 올린다(INTENT D22). Flatpak은 시스템 서비스와 장치 권한을 설치할 수 없어서 내지 않는다.
- 배포는 .deb(Debian, Ubuntu)와 .rpm(Fedora, openSUSE)이다. 파일을 열면 소프트웨어 센터(GNOME 소프트웨어, KDE Discover, gdebi)가 설치한다. 패키지는 소프트웨어 센터가 보여 줄 AppStream 메타데이터를 담는다.
- 패키지는 설치될 때 DSA의 서명된 저장소를 등록한다. .deb는 `/etc/apt/sources.list.d/dsa.sources`를 쓰고 `Signed-By`로 `/usr/share/keyrings/dsa-archive-keyring.gpg`를 가리킨다. .rpm은 `/etc/yum.repos.d/dsa.repo`(zypper가 있으면 `/etc/zypp/repos.d/dsa.repo`도)를 쓰고 `gpgcheck`와 `repo_gpgcheck`를 켜며 `gpgkey`로 `/etc/pki/rpm-gpg/RPM-GPG-KEY-dsa`를 가리킨다. 저장소 항목은 패키지 파일이 아니라 패키지 스크립트가 쓴다. conffile이면 제거 뒤에 남기 때문이다.
- 패키지를 제거하면 저장소 항목과 패키지가 설치한 키 파일을 지운다. 업그레이드(같은 패키지를 다시 설치하는 것 포함)에서는 남긴다.
- 저장소는 무료 GPG 키 하나로 서명한다. apt는 `Release`, `InRelease`, `Release.gpg`, dnf는 `repomd.xml.asc`와 서명된 rpm이다. 릴리스 스크립트가 저장소 시크릿의 키로 저장소를 만들고, GitHub Pages에 올릴 수 있는 폴더로 낸다.
- Linux 호스트는 자기 업데이터를 두지 않는다. `dsa update`는 아무것도 받거나 설치하지 않고, 업데이트가 시스템 패키지 관리자에서 온다고 알린다. `dsa settings`의 프로그램 업데이트 줄도 그렇게 보인다. 안드로이드 이미지 업데이트(FR-14)는 서비스가 그대로 한다.
- 수용 기준: CI에서 일회용 키로 만든 저장소를 로컬에서 내보이고, Ubuntu에서 .deb를 설치하면 `dsa.sources`와 키링이 생기고 `apt-get update`가 서명 오류 없이 저장소를 읽으며 `apt-cache policy`가 그 저장소의 패키지를 보인다. 다시 설치해도 항목이 남고, 제거하면 항목과 키링이 사라진다.
- 수용 기준: Fedora에서 .rpm을 설치하면 `dsa.repo`가 생기고 dnf가 서명된 메타데이터를 검증해 저장소를 읽으며, 저장소의 rpm은 서명 검사를 통과한다. 다시 설치해도 항목이 남고, 제거하면 항목과 키 파일이 사라진다.
- 수용 기준: Linux에서 `dsa update`는 설치할 버전 없이 패키지 관리자를 안내하고, `dsa settings`의 프로그램 업데이트 줄은 패키지 관리자를 가리킨다.
- 수용 기준: 실제 Ubuntu와 Fedora 데스크톱에서 .deb와 .rpm을 열어 소프트웨어 센터로 설치하고, 다음 버전이 저장소에 올라오면 소프트웨어 센터의 업데이트로 온다. (수동 확인)

### FR-16 키 입력 (`Agreed`)
- 포커스를 가진 태스크 창에서 누른 물리 키를 게스트 키 이벤트로 주입한다. 누름, 뗌, 자동 반복을 구분하고 수정 키(Ctrl, Shift, Alt, Meta) 상태를 함께 싣는다.
- 글자 입력은 FR-6(IME)이 맡는다. 이 항목은 방향키, Enter, Backspace, Delete, Tab, Esc, 기능 키와 단축키처럼 조합하지 않는 키를 다룬다.
- 창이 포커스를 잃으면 눌린 채로 남은 키를 모두 뗀 것으로 보낸다.
- 수용 기준: 텍스트 입력란에서 방향키, Enter, Backspace, Delete, Ctrl+A/C/V가 동작한다.
- 수용 기준: 키를 누른 채 다른 창으로 포커스를 옮기면 게스트에서 그 키가 눌린 채로 남지 않는다.

### FR-17 설정 앱 (`Agreed`)
- DSA의 설정과 상태를 한 곳에서 보고 바꾸는 설정 앱을 운영체제마다 둔다(INTENT D23). 화면은 그 운영체제의 설정 앱 스타일을 따른다.
  - Windows: WPF와 WPF-UI로 Windows 11 설정 스타일을 따른다: NavigationView, 설정 카드, Mica 배경, 라이트와 다크 테마, 시스템 강조색.
  - macOS: SwiftUI와 AppKit으로 만든 네이티브 창이고, 시스템 설정 스타일(사이드바와 그룹 목록)을 따른다. 라이트와 다크 모양, 시스템 강조색을 따른다.
  - Linux: GTK4와 libadwaita로 GNOME 설정 스타일(`AdwNavigationSplitView`, `AdwPreferencesGroup`)을 따른다. 라이트와 다크 스타일, 시스템 강조색을 따른다.
- 다루는 것: 안드로이드 시작과 종료, 상태(`Stopped`, `Active`, `Dozing` 등)와 마지막 오류, 메모리 사용 내역(호스트의 VM과 동반 프로세스, 게스트의 커널, 캐시, 시스템, 앱별), 렌더링 GPU 선택(D20), 프로그램과 안드로이드 이미지 업데이트 설정, freeze 사용 여부(기본 끔), 버전 정보와 로그 폴더 열기.
- 설정은 동반 서비스의 로컬 API로 읽고 쓴다. 앱은 설정을 직접 파일에 쓰지 않는다. 세 설정 앱은 같은 로컬 API의 얇은 클라이언트이고, 값의 검사, 저장, 상태 계산을 앱마다 다시 구현하지 않는다.
- 영어와 한국어를 지원하고, 시스템 언어를 따른다.
- 수용 기준: 설정 앱에서 렌더링 GPU를 바꾸면 다음 시작부터 그 GPU에서 렌더링하고, 메모리 화면이 VM과 게스트 내역을 보여 준다. (수동 확인)
- 수용 기준: macOS와 Linux의 설정 앱이 Windows 설정 앱과 같은 항목을 보이고, 바꾼 값이 로컬 API를 거쳐 같은 결과를 낸다. 각 앱의 모양이 그 운영체제의 설정 앱 스타일과 맞는지는 라이트와 다크에서 확인한다. (수동 확인)

#### 브랜드 아이콘
INTENT D23을 따른다. 모든 운영체제가 같은 DSA 상징(모양과 색)을 쓰고, 그것을 그 운영체제의 디자인 언어로 그린다.

- 상징: 둥근 모서리의 앱 창 하나와 그 위로 비스듬히 솟은 안테나 두 개다. 몸체는 짙은 초록 그라데이션(#1c8a63에서 #05392a), 제목 표시줄은 밝은 초록 그라데이션(#9af8c4, #47e08c, #1fb066)과 작은 그림자, 제목 표시줄 오른쪽의 짙은 점 두 개, 몸체 아래쪽의 반투명한 안쪽 판, 두 겹의 그림자로 이루어진다. 위쪽 가장자리의 흰 선은 없다.
- 원본 SVG는 `dsa/brand/`에 있다: 공통 상징 [`symbol.svg`](../dsa/brand/symbol.svg), Windows의 작은 크기 [`symbol-small.svg`](../dsa/brand/symbol-small.svg), Linux [`linux.svg`](../dsa/brand/linux.svg)와 [`linux-symbolic.svg`](../dsa/brand/linux-symbolic.svg), macOS [`macos.svg`](../dsa/brand/macos.svg), 알림 영역과 메뉴 막대의 단색 그림. 같은 폴더의 생성 스크립트가 여기서 아래의 모든 파일과 크기를 만들고, CI가 그것을 돌린다.
- Windows(Fluent 2 스타일, WSA를 베끼지 않고 Microsoft 상표를 쓰지 않는다):
  - 공통 상징을 그대로 쓴다.
  - `.ico`에 16, 20, 24, 32, 40, 48, 64, 256 px를 모두 담는다. 24 px 이하는 손으로 다듬은 단순한 그림이다: 점과 안쪽 판을 빼고 안테나를 굵게 한다.
  - 쓰는 곳: 시작 메뉴, 작업 표시줄, 창 제목 표시줄, 설치 화면(setup.exe)과 MSI(`ARPPRODUCTICON`, 설치된 앱 목록).
  - 알림 영역 아이콘은 단색이고, 밝은 작업 표시줄용과 어두운 작업 표시줄용을 두며, 작업 표시줄 테마가 바뀌면 바로 바꾼다.
- macOS(Apple HIG의 squircle 바탕):
  - 짙은 초록 그라데이션(#14674b에서 #0a3e2e)의 squircle(지수 5의 초타원) 위에 아래쪽 두께가 보이는 흰 창 하나를 둔다. 모든 macOS 버전에 이 아이콘 하나를 쓴다.
  - `.icns`에 16, 32, 64, 128, 256, 512, 1024 px(16에서 512 px까지는 @1x와 @2x)를 담는다. Tahoe의 Liquid Glass용으로 레이어를 나눈 원본(Icon Composer 형식)을 함께 둔다.
  - 쓰는 곳: Dock, Finder와 Launchpad, 설정 창, pkg와 dmg.
  - 메뉴 막대 아이콘은 템플릿 이미지(단색, 투명 바탕)라 밝은 메뉴 막대와 어두운 메뉴 막대에서 시스템이 색을 입힌다.
- Linux(GNOME HIG, Adwaita 스타일):
  - 컬러 아이콘은 아래 두께(#08402f)가 있는 초록 판(#2fd37c) 위에 흰 제목 표시줄과 흰 안테나, 짙은 몸체의 창이다. symbolic 아이콘은 같은 창 모양을 한 색으로 그리고 안쪽 판을 비운다.
  - `hicolor/scalable/apps/`에 컬러 SVG, `hicolor/symbolic/apps/`에 `-symbolic` SVG를 둔다.
  - 쓰는 곳: 앱 그리드와 `.desktop` 항목, 패널 표시기(symbolic, 패널 색을 따른다), 소프트웨어 센터(AppStream 메타데이터의 아이콘).
- 딸린 앱(설정, APK 설치 관리자, 파일)은 운영체제마다 같은 형식과 크기의 아이콘을 가진다. 설정과 파일은 배지 없는 공통 상징이고, APK 설치 관리자는 열린 상자 아이콘이다. 어떤 아이콘에도 배지를 붙이지 않는다.
- 안드로이드 로봇(Bugdroid)은 상징으로 쓰지 않는다. 안드로이드 초록색이나 로봇을 쓰면 Google 브랜드 가이드라인의 조건을 지키고, 그것을 싣는 곳(정보 화면, 서드파티 고지)에 "The Android robot is reproduced or modified from work created and shared by Google and used according to terms described in the Creative Commons 3.0 Attribution License." 문구를 둔다. 상표 표기는 NFR-6을 따른다.
- 수용 기준: CI 검사가 배포하는 아이콘 파일이 모두 있고, 각 파일이 위에서 정한 크기를 모두 담는지 확인한다(`.ico`의 8개 크기, `.icns`의 모든 크기, 컬러 SVG와 symbolic SVG, 알림 영역의 밝은 것과 어두운 것, 딸린 앱마다 같은 목록). 하나라도 빠지면 실패한다.
- 수용 기준: 실제 기기에서 각 운영체제의 쓰는 곳(Windows의 시작 메뉴, 작업 표시줄, 알림 영역, 설치 화면과 설치된 앱 목록, macOS의 Dock, 메뉴 막대, pkg와 dmg, Linux의 앱 그리드, 패널, 소프트웨어 센터)에 아이콘이 보이고, 밝은 테마와 어두운 테마에서 알아볼 수 있다. (수동 확인)

#### 기기 정체성
이미지는 Cuttlefish의 이름(제조사 Google, 모델 `Cuttlefish x86_64 phone 64-bit only`, 기기 `vsoc_x86_64_only`)을 그대로 두지 않는다. 기본값은 안드로이드가 실제로 도는 컴퓨터의 정보다. Windows 설정의 "정보"가 보여 주는 것과 같은 제조사, 모델, 이름을 안드로이드의 앱과 사용자도 보게 하기 위해서다. 사용자는 그 값을 설정에서 바꿀 수 있다. 옛 기기 이름을 확인하는 앱과 호환하기 위해서다.
- 기본값은 호스트가 안드로이드를 시작할 때마다 컴퓨터의 펌웨어 정보(SMBIOS; Windows는 WMI와 `HKLM\HARDWARE\DESCRIPTION\System\BIOS`, Linux는 `/sys/class/dmi/id/`, macOS는 IOKit의 기기 모델)와 운영체제에서 읽는다. 그래서 컴퓨터 이름을 바꾸면 다음 시작부터 따라간다.
  - 제조사와 브랜드: 시스템 제조사. 법인 접미사(`CO., LTD.`, `Inc.`, `Corporation` 같은 것)를 떼고 대소문자를 다듬는다(예: `SAMSUNG ELECTRONICS CO., LTD.`는 `Samsung`).
  - 모델(`Build.MODEL`): 판매 모델 번호. 메인보드 제품명이 시스템 제품명과 같은 계열이면(예: `960XGL`과 `NT960XGP-G72AG`) 메인보드 제품명을, 아니면 시스템 제품명을 쓴다. 제조사마다 판매 모델 번호를 넣는 칸이 달라서다.
  - 모델 이름: 시스템 제품군(예: `Galaxy Book4 Ultra`). 제품군이 비면 시스템 버전이나 제품명을 쓴다.
  - 기기 이름(`Settings.Global.DEVICE_NAME`, 블루투스와 공유 대상에 보이는 이름): 컴퓨터 이름.
  - 칩 제조사와 칩 모델(`Build.SOC_MANUFACTURER`, `Build.SOC_MODEL`): CPU의 제조사와 모델(예: `Intel`, `Core Ultra 7 155H`).
  - 기기와 제품 이름은 `dsa_x86_64`(ARM64 이미지는 `dsa_arm64`), `ro.build.characteristics`는 `tablet`이다. 지문은 `<브랜드>/dsa_x86_64/dsa_x86_64:<릴리스>/<빌드 ID>/<증분>:user/release-keys`다. 기기와 제품 이름을 실제 휴대전화의 것으로 두지 않는 것은, 앱과 Google 서비스가 이 값으로 기기를 판별하기 때문이다. 이미지는 user 빌드이므로 지문의 빌드 유형도 `user`다. 증분에는 이미지마다 붙이는 내용 태그가 그대로 남는다.
  - 값을 읽을 수 없거나 자리 표시 문자열(`To be filled by O.E.M.`, `Default string`, `System Product Name` 같은 것)이면 그 항목은 DSA의 값을 쓴다: 제조사 `thisisthepy`, 브랜드 `DSA`, 모델 `Desktop Subsystem for Android`.
- `tablet`은 AOSP의 태블릿 구성이 쓰는 값이다. 앱의 화면 배치는 이 값이 아니라 창 크기(가장 짧은 너비)로 정해지므로, 큰 화면 배치를 고르게 하면서 휴대전화 전용 앱을 막지 않는다. `phone` 같은 다른 값도 고를 수 있다.
- 이 값은 모든 파티션(system, system_ext, vendor, product, odm, vendor_dlkm과 이미지에 있는 나머지)의 `ro.product.<파티션>.{brand,manufacturer,model,device,name}`, 그것에서 나오는 `ro.product.{brand,manufacturer,model,device,name}`, 파티션마다의 지문, `ro.build.fingerprint`, `ro.build.product`, `ro.build.flavor`, `ro.build.description`에 똑같이 들어간다. `ro.build.display.id`는 user 빌드처럼 빌드 ID만 담는다. 앱이 읽는 `Build.MANUFACTURER`, `Build.BRAND`, `Build.MODEL`, `Build.DEVICE`, `Build.PRODUCT`, `Build.FINGERPRINT`가 이 값이다. 이미지 검사(`check-image.py`)가 이것을 확인한다.
- 설정 앱의 "기기 정보" 페이지와 `dsa settings set device.<항목> <값>`으로 바꾸는 항목: 제조사(`manufacturer`), 브랜드(`brand`), 모델(`model`), 기기(`device`), 제품 이름(`name`), 형태(`characteristics`), 지문. 지문은 구성 요소(`fingerprint.release`, `fingerprint.id`, `fingerprint.incremental`, `fingerprint.type`, `fingerprint.tags`)를 하나씩 바꾸거나, 지문 문자열 전체(`fingerprint`)를 적는다. 전체 문자열을 적으면 그것이 구성 요소보다 앞선다. 적지 않은 구성 요소는 이미지의 값을 쓰고, 브랜드, 제품 이름, 기기는 위의 항목을 따른다.
- "기본값으로 되돌리기" 단추와 `dsa settings reset device`가 모든 항목을, `dsa settings reset device.<항목>`이 한 항목을 기본값으로 되돌린다. 기본값은 위의 컴퓨터 정보다. 페이지는 각 항목의 기본값이 어디서 왔는지(컴퓨터 정보, DSA 값) 보여 준다.
- 수용 기준: 가짜 펌웨어 정보(이 PC처럼 메인보드 제품명에 판매 모델 번호가 있는 경우, 시스템 제품명에만 있는 경우, 자리 표시 문자열, 빈 값)에서 제조사, 브랜드, 모델, 모델 이름, 기기 이름, 칩 정보가 위 규칙대로 나오고, 사용자가 바꾼 값이 그보다 앞선다.
- 수용 기준: 실제 PC에서 안드로이드 설정의 기기 정보와 기기 정보 앱이 Windows 설정의 "정보"와 같은 제조사, 모델, 컴퓨터 이름을 보이고, 컴퓨터 이름을 바꾸고 다시 시작하면 따라간다. (수동 확인)
- 값은 사용자별이고, 동반 서비스가 `settings\users\<SID>.device.json`에 둔다(FR-19). 설정 앱은 이 파일을 직접 쓰지 않는다.
- 바꾼 값은 다음 안드로이드 시작부터 적용된다. `ro.*` 속성은 부팅 중 한 번 정해지면 바꿀 수 없기 때문이다. 페이지는 이것을 알리고, 안드로이드가 실행 중이면 "지금 안드로이드 다시 시작" 단추를 보여 준다.
- 전달 방법: 호스트가 부팅마다 만드는 initrd 복사본에 속성 파일 하나(`/system/etc/ramdisk/build.prop`)를 매번 덧붙인다. 기본값이 컴퓨터마다 다르고 컴퓨터 이름처럼 바뀔 수 있어서, 이미지에 고정해 둘 수 없기 때문이다. 첫 단계 init이 그 파일을 둘째 단계로 넘기고, 이미지의 product `build.prop`이 맨 끝에서 그 파일의 정체성 속성만 가져온다. 속성 서비스가 `ro.*`를 잠그기 전에 init 자신이 읽으므로 SELinux 정책을 넓히지 않는다. 이미지에 든 값(DSA의 값)은 호스트가 속성 파일을 붙이지 못한 경우에만 쓰인다.
- 입력을 검사한다. 제조사와 모델은 1~64자의 인쇄 가능한 ASCII이고 앞뒤 공백이 없다. 브랜드, 기기, 제품 이름은 1~32자의 영문자, 숫자, `.`, `_`, `-`이고 영문자나 숫자로 시작한다. 형태는 쉼표로 나눈 소문자, 숫자, `_`의 낱말이고 64자 이하다. 지문은 `브랜드/제품/기기:릴리스/ID/증분:유형/태그` 꼴이고 256자 이하이며, 유형은 `user`, `userdebug`, `eng` 중 하나다. 틀린 값은 아무것도 바꾸지 않고 이유와 함께 거부한다.
- 페이지는 지문이나 모델을 바꾸면 앱 호환성(기기를 확인하는 앱, 결제와 무결성 검사)에 영향을 줄 수 있다고 경고한다. 정체성을 바꾸면 패키지 관리자가 다음 부팅을 업데이트로 보고 앱을 한 번 다시 검사한다.
- 수용 기준: 이미지 검사가 모든 `build.prop`에서 위의 기본값을 확인하고, 정체성 속성에 Cuttlefish의 이름(`Cuttlefish`, `vsoc_`, `aosp_cf_`)이나 지문의 `userdebug`가 남아 있으면 실패한다.
- 수용 기준: 기본값과 다른 정체성이 있으면 부팅용 initrd 끝(bootconfig 앞)에 그 값을 담은 속성 파일이 붙고, 모두 기본값이면 붙지 않는다. 지문 구성 요소와 전체 문자열이 위의 규칙대로 합쳐진다.
- 수용 기준: 틀린 값(허용하지 않는 문자, 길이 초과, 형식이 틀린 지문)은 거부되고 저장된 값이 바뀌지 않는다.
- 수용 기준: 설정 앱이나 CLI로 값을 바꾸고 안드로이드를 다시 시작하면, 앱이 읽는 `Build.MANUFACTURER`, `Build.BRAND`, `Build.MODEL`, `Build.DEVICE`, `Build.PRODUCT`, `Build.FINGERPRINT`와 `ro.build.characteristics`가 설정과 같고, 기본값으로 되돌리고 다시 시작하면 기본값으로 돌아온다. (수동 확인)

### FR-18 접근성 (`Agreed`)
태스크 창 안의 안드로이드 UI를 호스트의 접근성 트리로 내보낸다. 지금은 앱 내용이 호스트에게 그림 한 장이어서, 스크린 리더가 읽지 못하고 UI 자동화 도구도 항목을 찾지 못하기 때문이다.
- 에이전트가 게스트의 접근성 노드(역할, 이름, 값, 상태, 위치, 가능한 동작)를 읽어 제어 채널로 보낸다. 호스트는 이것을 태스크 창의 접근성 트리로 내보낸다. Windows에서는 UI Automation 트리, Linux에서는 AT-SPI 트리다. 같은 안드로이드 UI를 어느 호스트의 스크린 리더로도 읽을 수 있게 하기 위해서다.
- 트리는 그 창의 태스크에 속한 노드만 담는다. 호스트의 접근성 도구가 트리를 요청하지 않는 동안에는 게스트가 노드를 보내지 않는다. 쓰지 않는 사용자가 메모리와 CPU를 치르지 않게 하기 위해서다.
- 호스트 쪽의 호출(Invoke, 값 설정, 스크롤, 포커스)은 해당 노드의 접근성 동작으로 게스트에 전달한다.
- 이 경로는 터치 입력과 화면 표시를 거치지 않는다. 따라서 입력 지연과 그리기 품질(FR-4, FR-5)을 재는 수단이 되지 못하고, 그 측정을 대신하지 않는다.
- 수용 기준: UI Automation 클라이언트로 설정 앱 창의 트리를 읽으면 목록 항목의 역할, 이름, 화면 위치가 앱이 보여 주는 것과 맞다.
- 수용 기준: 그 클라이언트로 목록 항목에 Invoke를 호출하면 커서를 움직이지 않고 해당 화면이 열리고, 트리도 새 화면으로 바뀐다.
- 수용 기준: 창 내용이나 크기가 바뀌면 호스트가 UI Automation 변경 이벤트를 내고, 트리가 1초 안에 새 상태를 보여 준다.
- 수용 기준: 접근성 클라이언트가 없는 동안 게스트의 접근성 서비스가 노드를 읽지 않는다.
- 수용 기준: 내레이터로 설정 앱의 목록 항목을 차례로 옮겨 가면 각 항목을 읽어 준다. (수동 확인)
- 수용 기준: Linux에서 AT-SPI 클라이언트로 설정 앱 창의 트리를 읽으면 목록 항목의 역할, 이름, 화면 위치가 앱이 보여 주는 것과 맞고, 목록 항목에 기본 동작(Activate)을 부르면 커서를 움직이지 않고 해당 화면이 열린다. 제목 표시줄의 뒤로 단추와 캡션 단추도 이름이 있는 단추로 트리에 드러난다.
- 수용 기준: Linux에서 접근성 클라이언트가 없는 동안 게스트의 접근성 서비스가 노드를 읽지 않는다.
- 수용 기준: Orca로 설정 앱의 목록 항목을 차례로 옮겨 가면 각 항목을 읽어 준다. (수동 확인)

### FR-19 저장 위치 (`Agreed`)
DSA가 실행 중에 만드는 파일은 정해진 두 루트 아래 정해진 자리에만 둔다. 기능마다 경로를 따로 정하면 파일이 흩어지고, 제거할 때 무엇을 지울지 알 수 없기 때문이다.
- 루트는 둘뿐이다. 기계 전체의 루트는 `%ProgramData%\DSA`(설치할 때 데이터 폴더를 다른 곳으로 고르면 그 폴더)이고, 사용자별 루트는 그 사용자의 `%LOCALAPPDATA%\DSA`다.
- 경로는 Windows 호스트의 경로 모듈 하나가 만들고, 동반 서비스, 창 관리자, 앱 창, CLI가 모두 그것을 쓴다. 설정 앱(C#)과 설치 프로그램(WiX)은 아래 표를 그대로 따른다. `dsa/host/core`는 경로를 만들지 않고 주입받는다.

기계 루트(`%ProgramData%\DSA`): SYSTEM과 Administrators만 쓸 수 있다.

| 자리 | 담는 것 | 이유 |
|---|---|---|
| `dsa-hostd.json` | 동반 서비스 구성 | 설치 프로그램이 쓰고 서비스가 읽는다 |
| `images\` | 안드로이드 이미지 저장소 | 모든 사용자의 VM이 같은 이미지로 부팅한다 |
| `updates\` | 내려받은 프로그램 설치 파일과 업데이트 상태 | 서비스가 SYSTEM으로 실행하므로 사용자가 바꿀 수 없어야 한다 |
| `settings\` | `machine.json`, `users\<SID>.json`, `users\<SID>.device.json`(기기 정체성), 위젯 배치 | 사용자가 설정 앱에서 바꾸는 값. 서비스만 쓴다 |
| `logs\` | `dsa-hostd.log`, `android-<SID>.log`(게스트 콘솔) | 서비스와 안드로이드의 로그 |
| `tmp\` | VM 부팅마다 만드는 initrd 같은 피할 수 없는 임시 파일 | 아래 임시 파일 규칙 |

사용자 루트(`%LOCALAPPDATA%\DSA`): 그 사용자, SYSTEM, Administrators만 읽고 쓴다.

| 자리 | 담는 것 | 이유 |
|---|---|---|
| `android.vhdx` | 그 사용자의 안드로이드 디스크 | 사용자의 데이터다. 제거해도 남는다 |
| `android.image-version` | 그 디스크가 담은 이미지의 버전 | 디스크를 어느 이미지에서 올릴지 판단한다. 디스크와 함께 남는다 |
| `pstore.vhd` | 게스트 커널이 마지막 로그(커널 메시지와 pmsg)를 남기는 고정 크기 디스크(4 MiB) | VM은 패닉이나 재설정 때 끝나므로 메모리에 둔 기록은 남지 않는다. 크기가 정해져 있어 커지지 않고, 사용자 데이터가 아니므로 제거하면 지운다 |
| `apps\<package>\` | 앱마다 만든 창 프로그램과 그 기록 | 앱 이름과 아이콘을 단 실행 파일 |
| `notifications\` | 알림에 쓰는 앱 아이콘 | Windows 알림이 파일 경로로 아이콘을 읽는다 |
| `logs\` | `dsa-wm.log`, `dsa-app-window.log` | 사용자 세션에서 도는 프로세스의 로그 |
| `compositor.json` | 설정 앱 이전에 고른 렌더링 GPU | 이전 선택을 이어받기 위해 읽기만 한다 |
| `monitors.txt` | 모니터 배치 기록 | 창 관리자의 사용자별 상태 |
| `start-menu.json` | 창 관리자가 만든 시작 메뉴 바로 가기의 목록 | 자기가 만든 것만 고치고 지우기 위해서다 |
| `tmp\` | 사용자 프로세스의 피할 수 없는 임시 파일 | 아래 임시 파일 규칙 |

- DSA 폴더 밖에는 다음만 둔다: 시작 메뉴 바로 가기(설정 앱, 그리고 앱마다 창 관리자가 만든 것), 설치 프로그램의 레지스트리 키(`HKLM\SOFTWARE\thisisthepy\DSA`), 로그인 때 창 관리자를 시작하는 `Run` 값, `.apk` 연결과 파일 상황에 맞는 메뉴 항목, Hyper-V 소켓 서비스 등록(`GuestCommunicationServices`), 알림을 누르면 실행되는 URL 프로토콜 키(`HKCU\Software\Classes\io.github.thisisthepy.dsa-notification`), 알림에 쓰는 앱별 AppUserModelId 키(`HKCU\Software\Classes\AppUserModelId\Thisisthepy.DSA.<package>`), Windows 설치된 앱 목록에 안드로이드 앱을 올리는 앱별 제거 키(`HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\Thisisthepy.DSA.<package>`). 이 밖에는 아무것도 두지 않는다.
- 이름은 Microsoft와 IETF의 관례를 따른다. URL 프로토콜 이름은 다른 프로그램과 겹치지 않도록 프로젝트가 가진 도메인(`thisisthepy.github.io`)을 뒤집어 앞에 붙인다(RFC 7595 3.8절). 패키지 앱의 프로토콜 이름 규칙(소문자, 39자 이하)에도 맞는다. AppUserModelID는 `CompanyName.ProductName.SubProduct` 꼴(`Thisisthepy.DSA.<package>`)이고 128자를 넘지 않는다. 예전 이름(`dsa-notification`, `DSA.<package>`)의 키는 업그레이드 뒤 창 관리자가 처음 시작할 때와 제거할 때 지운다.
- 제거하면 알림 프로토콜 키, AppUserModelId 키, 앱별 제거 키는 지우고, `android.image-version`은 안드로이드 디스크와 함께 남긴다.
- 임시 파일은 되도록 만들지 않고 데이터를 메모리나 파이프로 넘긴다. 피할 수 없으면 해당 루트의 `tmp\` 안에만, 프로세스마다 겹치지 않는 이름으로 만들고, 쓴 쪽이 다 쓰면 지운다. 서비스는 시작할 때 이전 실행이 남긴 것을 지운다. 기계 루트의 `tmp\`는 SYSTEM과 Administrators만 쓸 수 있다. 제품 코드는 시스템이나 사용자의 `%TEMP%`, `std::env::temp_dir()`, `Path.GetTempPath()`를 쓰지 않는다(테스트는 예외).
- 로그는 둘로 나눈다. SYSTEM으로 도는 서비스와 안드로이드(게스트 콘솔)의 로그는 기계 루트의 `logs\`에, 사용자 세션에서 도는 창 관리자와 앱 창의 로그는 사용자 루트의 `logs\`에 둔다. 설정 앱은 두 폴더를 모두 보여 주고 열 수 있다.
- 추적 스위치(`input-trace`, `resize-trace`)는 설정 값이다. 빈 표시 파일로 켜지 않는다. 업그레이드할 때 예전 표시 파일이 있으면 그 값을 설정으로 옮기고 파일을 지운다.
- 수용 기준: `dsa/host`의 제품 코드가 경로 모듈 밖에서 `LOCALAPPDATA`, `ProgramData`, 임시 폴더로 경로를 만들면 실패하는 테스트가 있고, 통과한다.
- 수용 기준: 제거하면 안드로이드 디스크(`android.vhdx`와 `android.image-version`)를 뺀 DSA의 파일, 폴더, 레지스트리 키, 바로 가기가 모든 사용자 프로필에서 사라진다. (수동 확인)
- 수용 기준: 예전 위치에 파일이 있는 PC에 설치하면 파일이 새 위치로 옮겨지고, 사용자의 안드로이드 디스크를 그대로 쓴다. 옮기기 전에 확인하고, 안드로이드 디스크는 지우거나 덮어쓰지 않으며, 옮기지 못하면 예전 위치에 두고 로그에 남긴다.

### FR-20 개발자 모드와 adb (`Agreed`)
개발자가 게스트를 adb로 살펴볼 수 있게 한다. WSA처럼 adb는 릴리스 이미지에 들어 있고, 사용자가 설정에서 개발자 모드를 켤 때만 열린다. 게스트에는 SystemUI가 없어 기기 화면에서 adb 연결을 승인할 수 없으므로 승인을 요구하지 않는다. 제어 메시지는 adb로 보내지 않는다(INTENT D3). adb는 개발에만 쓴다.
- 이미지는 user 빌드 그대로다(`ro.debuggable=0`). adbd는 `ro.adb.secure=0`으로 기기 승인 없이 연결을 받고, TCP 대신 vsock으로만 듣는다.
- 개발자 모드는 사용자별 설정이고 기본값은 끔이다. 설정 앱의 고급 항목과 `dsa settings set developer-mode on|off`로 바꾼다. 바꾸면 이미지를 다시 설치하거나 안드로이드를 다시 시작하지 않고 바로 적용된다.
- 켜져 있으면 호스트가 `127.0.0.1`에만 묶인 포트(기본 58526, 설정으로 바꿀 수 있다)를 열고, 그 연결을 hvsocket으로 게스트의 adbd에 잇는다. 제어 채널로 게스트에 adbd를 켜라고 알린다. 설정 앱은 쓸 주소(`adb connect 127.0.0.1:58526`)를 보여 준다.
- 꺼져 있으면 호스트는 그 포트를 듣지 않고, 게스트의 adbd는 멈춰 있다.
- 자동 연결: 개발자 모드가 켜져 있는 동안 호스트는 이 PC의 adb 서버(`127.0.0.1:5037`, `ANDROID_ADB_SERVER_PORT`가 있으면 그 포트)를 지켜보다가, 서버가 떠 있고 DSA가 기기 목록에 없으면 adb 서버 프로토콜의 `host:connect:127.0.0.1:<포트>` 요청으로 DSA를 붙인다. 그래서 사용자가 `adb connect`를 치지 않아도 Android Studio와 `adb devices`에 DSA가 나타나고, adb 서버나 PC를 다시 시작해도 다시 붙는다. adb 실행 파일을 찾거나 실행하지 않고 서버 소켓에 직접 말한다. 사용자가 `adb disconnect`로 끊으면 그 adb 서버가 다시 시작될 때까지 다시 붙이지 않는다. 개발자 모드를 끄면 `host:disconnect`로 뗀다. 설정에서 자동 연결만 끌 수 있고, 기본값은 켬이다.
- 같은 PC 안의 도구가 찾을 수 있도록, 켜져 있는 동안 adb의 mDNS 서비스 이름(`_adb._tcp`)으로도 알린다. 알림은 루프백 주소만 담고, 다른 기기가 접속할 수 있는 주소는 알리지 않는다.
- 수용 기준: 가짜 adb 서버에 대해, 개발자 모드가 켜지면 `host:connect` 요청이 가고, 서버가 다시 뜨면 다시 가며, 사용자가 끊은 뒤에는 서버가 다시 시작될 때까지 가지 않고, 개발자 모드를 끄면 `host:disconnect`가 간다. 자동 연결을 끄면 아무 요청도 가지 않는다.
- 수용 기준: 실제 PC에서 개발자 모드를 켜고 Android Studio를 열면 `adb connect` 없이 기기 목록에 DSA가 나타나 앱을 실행하고 디버그할 수 있다. (수동 확인)
- 수용 기준: 새로 설치한 상태에서 개발자 모드는 꺼져 있고, 호스트의 adb 포트에 연결할 수 없으며 게스트의 adbd가 돌지 않는다.
- 수용 기준: 개발자 모드를 켜면 `adb connect 127.0.0.1:<포트>` 뒤 `adb shell`이 아무 승인 없이 셸을 연다.
- 수용 기준: 개발자 모드를 끄면 호스트 포트가 닫히고 게스트의 adbd가 멈춘다.
- 수용 기준: 호스트 포트는 루프백(`127.0.0.1`)에만 묶이고, 다른 주소로는 연결되지 않는다.
- 수용 기준: 실제 Windows에서 설정 앱으로 개발자 모드를 켜고 `adb connect`, `adb shell`, `adb logcat`, `adb install`이 동작하며, 끄면 연결이 끊긴다. (수동 확인)

### FR-21 게스트 로그 스트림과 진단 수집 (`Agreed`)
안드로이드의 로그는 파일로 쌓지 않고, 읽는 쪽이 있을 때만 흘려 보낸다. 지금처럼 logcat을 직렬 콘솔로 보내면 한 부팅 안에서도 로그 파일이 계속 커지고(8 MB까지 보았다), 직렬 포트의 바이트마다 VM 밖으로 트랩이 나가기 때문이다.
- 원본은 logd의 메모리 안 링 버퍼다. 게스트는 로그를 파일로 쓰지 않는다.
- 호스트는 읽는 쪽이 붙어 있을 때만 게스트 로그를 구독한다. 읽는 쪽은 CLI `dsa logcat`(버퍼, 우선순위, 태그 필터와 `-d` 덤프)과 설정 앱의 실시간 보기 화면(필터와 일시 정지)이다.
- 로그 레코드는 전용 hvsocket 포트로 보낸다. 로그가 많아도 입력과 창 메시지가 늦어지지 않게 하기 위해서다. 구독, 구독 해제, 필터, 수집 요청은 제어 채널로 보낸다. 메시지와 레코드 형식은 프로토콜 정의에서 생성한다.
- 게스트 쪽 다리는 구독 중에만 logd에 붙는다. 보낼 큐는 크기가 정해져 있고, 넘치면 버린 레코드 수를 알리는 레코드를 대신 보낸다.
- 호스트는 최근 기록을 위해 작은 메모리 안 링(약 1 MB)만 두고, 로그 파일을 쓰지 않는다. 형식이 틀린 레코드는 로그 스트림만 끊고, 동반 서비스는 계속 돈다.
- 읽는 쪽이 없으면 로그 경로의 비용은 거의 0이다: 게스트 다리는 logd를 읽지 않고, 전용 포트로 아무것도 보내지 않는다.
- 진단 수집은 요청할 때만 한다. `dsa logs collect -o <zip>`과 설정 앱의 "진단 정보 저장" 단추가 게스트 로그 링 전체, tombstone, ANR 트레이스, dropbox, pstore, dumpsys 요약, 그리고 호스트 로그를 하나의 zip으로 모은다. 게스트는 아카이브를 스트림으로 보내고 게스트 디스크에 임시 파일을 남기지 않는다.
- 커널은 디스크에 쓰는 pstore(pstore/blk)를 켠다. 게스트가 죽어도 마지막 커널 로그와 안드로이드의 마지막 로그(pmsg)가 다음 부팅에 남게 하기 위해서다. VM은 패닉이나 재설정 때 끝나므로 메모리(ramoops)에 둔 기록은 남지 않는다. 기록은 사용자별 고정 크기 디스크(`pstore.vhd`, FR-19)에 두고, 디스크가 정해진 크기를 넘지 않는다. 디스크와 영역 크기를 고른 이유, 패닉 순간에 무엇이 남고 무엇이 남지 않는지는 커널 구성 문서에 적는다.
- 진단 수집이 pstore 기록을 호스트로 보내고 나면 게스트는 그 기록을 지운다. 같은 기록이 다음 수집에 다시 들어가지 않고, 새 기록이 들어갈 자리가 남게 하기 위해서다.
- 직렬 콘솔은 커널의 초기 부팅과 패닉 출력만 나른다. 콘솔 로그 파일은 한 부팅 안에서도 크기 상한을 둔다.
- 로컬 API의 로그 엔드포인트는 호출한 사용자의 안드로이드 로그만 준다.
- 수용 기준: 구독하지 않은 상태에서 게스트 다리는 logd에 연결하지 않고 로그 포트로 아무 바이트도 보내지 않는다. 구독하면 필터에 맞는 레코드만 오고, 구독을 해제하면 다시 멈춘다.
- 수용 기준: 보낼 큐가 넘치면 레코드를 버리고, 버린 수를 담은 레코드가 순서대로 온다.
- 수용 기준: 호스트 링은 정한 크기를 넘지 않고 가장 오래된 레코드부터 버린다. 형식이 틀린 레코드는 로그 스트림만 닫고 제어 채널과 서비스는 계속 동작한다.
- 수용 기준: 버퍼, 우선순위, 태그 필터와 `-d` 덤프가 정한 대로 레코드를 고른다. 보기 화면의 필터와 일시 정지가 정한 대로 동작한다.
- 수용 기준: 게스트 이미지에 logcat을 직렬 콘솔로 보내는 서비스가 없고, 콘솔 로그 파일이 한 부팅 안에서 상한을 넘지 않는다.
- 수용 기준: 실제 PC에서 `dsa logcat`이 실시간 로그를 보여 주고, `dsa logs collect -o diag.zip`과 설정 앱의 단추가 위의 항목을 담은 zip을 만들며, 게스트를 패닉시킨 뒤 다음 부팅의 수집에 pstore 기록이 들어 있다. (수동 확인)

### FR-22 통합 제목 표시줄 (`Agreed`)
태스크 창의 제목 표시줄은 투명하고, 앱 화면이 그 아래까지 이어진다. 요즘 Windows 앱처럼 앱의 색이 창 맨 위까지 닿게 하고, 앱 위에 따로 놓인 회색 띠를 없애기 위해서다.
- 호스트는 태스크 창의 비클라이언트 영역을 클라이언트 영역으로 넓히고(DWM 프레임 확장), 캡션 단추(최소화, 최대화, 닫기)를 직접 그린다. 크기 조절 테두리, 끌어 옮기기, 두 번 눌러 최대화, 시스템 메뉴(Alt+Space, 오른쪽 클릭), Windows 11 스냅 레이아웃(최대화 단추에 머무르기)은 Windows의 기본 제목 표시줄과 같게 동작한다.
- 제목 표시줄 높이는 창의 DPI에서 Windows가 쓰는 캡션 높이(`SM_CYCAPTION`과 테두리 패딩)다. 태스크의 픽셀은 창의 픽셀이므로 호스트는 이 높이를 픽셀로 게스트에 보내고(앱에게는 태스크 밀도에서 같은 높이의 dp가 된다), 게스트는 그 태스크의 위쪽 시스템 바 인셋(`WindowInsets.Type.statusBars()`, `systemBars()`, `captionBar()`)으로 앱에 준다. 앱의 툴바는 캡션 단추 아래에 놓이고, 상태 표시줄 배경은 투명한 제목 표시줄 뒤에 그려진다.
- 에이전트는 앱이 상태 표시줄에 대해 시스템에 알린 것(`APPEARANCE_LIGHT_STATUS_BARS`, 상태 표시줄 색)을 읽어, 바뀔 때마다 제어 채널로 보낸다. 호스트는 밝은 상태 표시줄 위에는 어두운 글리프를, 어두운 상태 표시줄 위에는 밝은 글리프를 그린다. 머무르기와 누르기 색은 Windows와 같게 하고, 닫기 단추는 머무를 때 빨간색이 된다. 값이 바뀌어도 깜빡이지 않도록 다음 그리기에서 한 번에 바꾼다.
- 제목 표시줄 영역의 포인터는 Windows의 것이다. 캡션 단추 위는 단추로, 나머지 띠는 끌어 옮기기 영역으로 처리하고 게스트에 주입하지 않는다. 앱은 이 띠를 시스템 바 인셋으로 받으므로 그 안에 조작할 것을 두지 않고, 띠 일부만 앱에 주면 같은 자리를 눌러도 끌기와 클릭이 섞여 예측하기 어렵기 때문이다. 띠 아래의 좌표 변환은 FR-5와 같고, 창 좌표와 게스트 좌표는 띠를 포함한 창 전체에서 같은 원점을 쓴다.
- 제목 표시줄 왼쪽에는 앱의 아이콘과 이름을 그린다. Windows 11 앱처럼 창이 무슨 앱인지 제목 표시줄에서 바로 알 수 있게 하기 위해서다. 아이콘은 앱의 런처 아이콘이다. 적응형 아이콘이 있는 앱은 배경판을 빼고 전경 레이어만 그려, 작은 크기에서도 앱 모양이 뚜렷하고 앱 화면 위에 네모난 판이 생기지 않게 한다. 적응형 아이콘이 없는 앱은 아이콘 전체를 쓴다. 작업 표시줄과 시작 메뉴는 배경판이 있는 아이콘을 그대로 쓴다. macOS 호스트의 창 제목 표시줄에는 아이콘을 그리지 않는다. macOS 앱 창의 제목 표시줄에는 아이콘이 없고, 아이콘을 붙이면 문서 창처럼 끌어 옮기는 파일 아이콘과 경로 메뉴가 함께 생기기 때문이다. macOS에서 앱 아이콘은 Dock이 보여 준다. 아이콘은 Windows 11이 캡션 아이콘에 쓰는 크기(`SM_CXSMICON`, 100%에서 16px)를 창의 DPI에 맞는 크기로 읽어 100%부터 200% 넘는 배율까지 흐려지지 않는다. 이름은 Segoe UI Variable 캡션 글꼴(100%에서 12px)로 쓰고, 세로 가운데는 캡션 단추 글리프와 같다. 왼쪽 여백은 WinUI 3 제목 표시줄과 같다(100%에서 아이콘 앞 16px, 아이콘과 이름 사이 16px).
- 이름이 길면 말줄임표로 줄여, 캡션 단추 밑으로 들어가지 않게 한다. 이름과 아이콘은 캡션 글리프와 같은 규칙으로 색을 정한다(밝은 앱에는 어두운 색, 어두운 앱에는 밝은 색). 창이 비활성이면 Windows처럼 이름과 아이콘을 흐리게 그리고, 앱이 테마를 바꾸면 다음 그리기에서 바로 바뀐다. 이름은 창의 제목이므로 UI Automation에 창 이름으로 드러난다.
- 아이콘 위의 점은 시스템 메뉴 히트 테스트 값(`HTSYSMENU`)을 돌려주어, 아이콘을 누르면 시스템 메뉴가 열린다. 이름 위는 끌어 옮기기 영역 그대로라 끌기, 두 번 눌러 최대화, 오른쪽 클릭 시스템 메뉴, Alt+Space, 스냅 레이아웃은 바뀌지 않는다.
- 시스템 메뉴에는 Windows의 항목(복원, 이동, 크기 조정, 최소화, 최대화, 닫기) 뒤에 구분선을 두고, 안드로이드 데스크톱 창의 창 메뉴(아이콘 옆 단추로 여는 메뉴)가 주는 항목을 더한다. Windows 사용자에게 익숙한 자리에서 같은 기능을 쓰게 하고, 제목 표시줄에 칸을 더 쓰지 않기 위해서다. 항목은 다음과 같다. 창 모드(전체 화면, 화면 분할)는 Windows의 최대화와 스냅 레이아웃이 맡으므로 더하지 않는다. 같은 앱의 창 관리는 작업 표시줄의 창 묶음이 맡으므로 더하지 않는다.
  - 새 창: 앱이 여러 창을 지원할 때만 보이며, 그 앱의 새 태스크를 새 창으로 연다.
  - 스크린샷: 그 창의 앱 화면(제목 표시줄 제외)을 클립보드에 넣고 사진 폴더의 스크린샷 폴더에 저장한다. Windows 캡처 도구와 같은 자리다.
  - 화면 비율: 앱의 화면 비율을 바꾸는 안드로이드 설정(사용자 화면 비율 재정의)을 연다. 큰 창에서 늘어나 보이는 앱을 고치기 위해서다.
  - 링크 열기 설정: 그 앱이 지원하는 링크를 브라우저 대신 앱으로 열지 정한다.
  - 앱 정보: DSA 설정의 그 앱 페이지(FR-23)를 연다.
- 수용 기준: 태스크 창의 시스템 메뉴에 Windows 항목 뒤 구분선과 위의 항목이 이 순서로 있고, 새 창은 여러 창을 지원하지 않는 앱에서 빠진다. 각 항목을 고르면 위의 동작이 일어난다. (`fr22_the_system_menu_carries_the_android_window_menu`)
- 뒤로 단추: 태스크에 돌아갈 곳이 있으면(첫 화면이 아니면) 제목 표시줄의 아이콘 자리에 아이콘 대신 뒤로 화살표를 그린다. 마우스만 쓰는 사용자도 화면에서 뒤로 갈 수 있게 하기 위해서다. 아이콘 칸의 크기와 자리는 그대로라, 바뀔 때 이름이 밀리지 않고, 앱이 그리는 제목 표시줄에서도 앱에 알린 영역이 바뀌지 않아 앱 화면이 움직이지 않는다. 앱이 무엇인지는 작업 표시줄 아이콘과 창 이름이 계속 보여 준다.
  - 화살표를 누르면 그 태스크에 뒤로(`KEYCODE_BACK`)를 보낸다. 머무르기와 누르기 모양은 캡션 단추와 같고, 색은 캡션 글리프와 같은 규칙을 따른다.
  - 첫 화면으로 돌아오면 다시 아이콘을 그리고, 아이콘 칸은 위와 같이 시스템 메뉴를 연다. 화살표가 있는 동안에도 시스템 메뉴는 제목 표시줄 오른쪽 클릭과 Alt+Space로 열린다.
  - 화살표는 UI Automation에 이름이 "뒤로"인 단추로 드러난다.
- 수용 기준: 태스크가 첫 화면이면 아이콘 칸에 아이콘이, 아니면 뒤로 화살표가 그려지고, 칸의 크기와 자리, 앱에 알린 캡션 영역은 둘 사이에서 같다. 화살표를 누르면 게스트에 `KEYCODE_BACK`이 주입되고, 아이콘을 누르면 시스템 메뉴가 열린다. (`fr22_the_icon_becomes_a_back_button_when_the_task_can_go_back`)
- 제목 표시줄은 언제나 앱 맨 위의 색을 따른다. 앱이 띠 뒤를 그리지 않아 띠가 비거나 검게 남으면(시스템 바 배경을 그리지 않는 옛 테마의 앱), 호스트는 띠 바로 아래 앱의 색으로 띠를 채우고, 글리프와 이름의 색도 그 색의 밝기로 정한다. 앱이 그 색을 바꾸면 띠도 따라 바뀐다.
- 고대비 모드에서는 캡션 단추를 시스템 색(`COLOR_BTNTEXT`, `COLOR_HIGHLIGHT`)으로 그린다. 캡션 단추는 UI Automation에 단추로 드러나며 이름(최소화, 최대화, 복원, 닫기)을 가진다.
- 수용 기준: 100%, 150%, 200% 배율에서 게스트 앱이 받은 위쪽 상태 표시줄 인셋(px)이 호스트 창의 제목 표시줄 높이(px)와 1px 안에서 같다.
- 수용 기준: 밝은 상태 표시줄(`APPEARANCE_LIGHT_STATUS_BARS`)을 쓰는 앱의 창은 어두운 캡션 글리프를, 어두운 상태 표시줄을 쓰는 앱의 창은 밝은 글리프를 그리고, 앱이 테마를 바꾸면 글리프도 바뀐다.
- 수용 기준: 제목 표시줄 띠의 점은 캡션 단추 위에서 단추 히트 테스트 값을, 나머지에서 캡션 히트 테스트 값을 돌려주고, 띠 아래의 점은 게스트에 FR-5와 같은 좌표로 주입된다.
- 수용 기준: 제목 표시줄 그림은 왼쪽 여백 뒤에 아이콘과 이름을 글리프의 색으로 담고, 비활성 창에서는 더 흐리며, 긴 이름은 캡션 단추 앞에서 끝난다. 아이콘 위의 점은 시스템 메뉴 히트 테스트 값을 돌려준다. (`fr22_the_title_bar_shows_the_apps_icon_and_name_at_its_left`, `fr22_a_long_name_ends_before_the_caption_buttons`, `fr22_the_icon_opens_the_system_menu`)
- 수용 기준: 띠가 비거나 검고 띠 아래가 한 색인 프레임에서는 띠가 그 색으로 채워지고 글리프 색이 그 색의 밝기를 따르며, 앱이 띠를 직접 그리면 채우지 않는다. (`fr22_an_app_that_leaves_the_band_empty_gets_its_top_colour_there`)
- 수용 기준: 실제 PC에서 최대화 단추에 머무르면 스냅 레이아웃이 뜨고, 띠를 끌면 창이 옮겨지며, 두 번 누르면 최대화와 복원이 된다. 밝은 앱과 어두운 앱 창의 캡처를 기록한다. (수동 확인)
- 앱이 그리는 제목 표시줄: 안드로이드 데스크톱 창의 방식대로, 앱이 제목 표시줄 배경을 직접 그리겠다고 시스템에 알리면(투명한 캡션 바 배경을 요청하면) 앱 화면이 창 맨 위 띠까지 차지한다. Chrome의 탭 줄처럼 앱의 조작 요소가 제목 표시줄에 놓일 수 있게 하기 위해서다. 이때 호스트는 이름을 그리지 않고, 캡션 단추와 아이콘 칸만 앱 화면 위에 겹쳐 그린다. 게스트는 캡션 바 인셋과 함께 캡션 단추와 아이콘 칸이 차지하는 영역을 앱에 알려, 앱이 그 자리를 비워 두게 한다. 띠 안에서 앱의 조작 요소 위의 포인터는 앱에 주입하고, 캡션 단추와 아이콘 칸은 위와 같이 호스트가 처리하며, 앱의 조작 요소가 없는 곳(앱이 끌기 영역으로 알린 곳 포함)은 끌어 옮기기 영역이다. 스냅 레이아웃, 두 번 눌러 최대화, 시스템 메뉴는 그대로 동작한다. 앱이 요청하지 않으면 위의 기본 동작 그대로다.
- 수용 기준: 적응형 아이콘이 있는 앱의 제목 표시줄 아이콘에는 전경 레이어만 그려지고, 적응형 아이콘이 없는 앱은 아이콘 전체가 그려진다. (`fr22_the_title_bar_icon_is_the_adaptive_foreground`)
- 수용 기준: 투명한 캡션 바 배경을 요청한 앱에는 캡션 바 인셋과 캡션 단추, 아이콘 칸의 영역이 전해지고, 호스트는 이름을 그리지 않으며, 띠 안의 앱 조작 요소 위의 포인터는 앱에, 빈 곳은 끌어 옮기기로, 캡션 단추 위는 단추로 처리된다. 요청을 거두면 기본 제목 표시줄로 돌아간다.
- 수용 기준: 실제 PC에서 Chrome이나 Chromium 창의 탭이 제목 표시줄 줄에 놓이고, 탭을 누르면 탭이 바뀌며, 탭 사이 빈 곳을 끌면 창이 옮겨지고, 최대화 단추에서 스냅 레이아웃이 뜬다. (수동 확인)

### FR-23 설치된 앱 관리 (`Agreed`)
사용자가 게스트에 설치된 안드로이드 앱을 보고, 열고, 지울 수 있게 한다. 지금은 설치된 앱을 볼 방법이 없고, WSA는 설정의 "앱 관리"와 Windows의 설치된 앱 목록 두 곳에서 이것을 제공했기 때문이다.
- 에이전트가 사용자에게 보이는 설치된 앱(런처 대상 앱)마다 패키지 이름, 이름, 아이콘, 버전 이름과 버전 코드, 크기(앱, 데이터, 캐시), 처음 설치한 시각과 마지막 업데이트 시각, 시스템 앱 여부를 보고한다. 메시지 형식은 프로토콜 정의에서 생성한다.
- 지우기는 에이전트가 `PackageInstaller` 세션으로 한다. 시스템 앱은 지울 수 없고, 요청하면 이유와 함께 거절한다. 사용자가 설치한 앱만 지운다.
- 설정 앱에 앱 화면을 둔다. 앱마다 아이콘, 이름, 패키지 이름, 버전, 크기, 설치 날짜를 보여 주고, 검색할 수 있다. 앱마다 열기(태스크 창), 앱 정보(안드로이드의 앱 정보 화면을 태스크 창으로 연다. 권한, 저장 공간, 알림을 거기서 바꾼다), 제거(확인을 받은 뒤)가 있다. 화면은 다른 설정 화면과 같은 Fluent 설정 카드를 따른다.
- 앱 화면에 "앱 관리" 항목을 둔다. 안드로이드 설정의 앱 목록을 태스크 창으로 연다.
- 창 관리자는 시작 메뉴 항목을 맞출 때 함께 앱마다 Windows 설치된 앱 목록의 항목(`HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\Thisisthepy.DSA.<package>`)을 만든다. 값은 `DisplayName`(앱 이름), `DisplayIcon`(`%LOCALAPPDATA%\DSA\apps\<package>\`의 그 앱 창 프로그램), `DisplayVersion`, `Publisher`, `InstallDate`, `EstimatedSize`(KB), `UninstallString`(설정 앱의 제거 창 `DsaSettings.exe --uninstall-app <package>`를 부른다), `NoModify`, `NoRepair`다. 앱을 설치, 업데이트, 제거하면 맞춘다. 창 관리자는 자기가 만든 키만 고치고 지운다.
- Windows 설치된 앱에서 제거를 누르면 DSA의 제거 창이 앱 정보와 진행을 보여 주며 바로 제거하고, 결과를 보여 준다. 다시 묻지 않으며 콘솔 창은 뜨지 않는다. 제거 창은 `dsa apps uninstall <package>`를 숨겨서 실행하고, 성공하면 스스로 닫히며, 실패하면 이유를 쉬운 말로 보여 준다. Windows 설정이 제거 전에 이미 묻기 때문이다.
- CLI는 `dsa apps list`, `dsa apps info <package>`, `dsa apps uninstall <package>`를 둔다. 안드로이드가 꺼져 있으면 켜고 처리한다.
- 수용 기준: 에이전트의 앱 목록 응답이 런처 대상 앱만 담고, 각 앱의 이름, 아이콘, 버전, 크기, 설치 시각, 시스템 앱 여부를 담는다.
- 수용 기준: 사용자 앱을 지우라고 하면 지워지고 결과가 성공이다. 시스템 앱이나 없는 패키지를 지우라고 하면 지우지 않고 이유를 담은 실패를 돌려준다.
- 수용 기준: 창 관리자가 앱 목록을 맞추면 앱마다 제거 키가 위의 값으로 생기고, 목록에서 빠진 앱의 키는 지워지며, 자기가 만들지 않은 키는 건드리지 않는다.
- 수용 기준: `dsa apps list`가 앱 목록을, `dsa apps info <package>`가 한 앱의 정보를 보여 주고, `dsa apps uninstall <package>`가 앱을 지운다.
- 수용 기준: 설정 앱의 앱 화면이 목록, 검색, 열기, 앱 정보, 확인 뒤 제거, 앱 관리를 보여 주며, 밝은 테마와 어두운 테마, 영어와 한국어의 화면 캡처가 CI에서 나온다.
- 수용 기준: 실제 Windows에서 APK를 설치하면 Windows 설정의 설치된 앱에 이름, 아이콘, 버전, 게시자와 함께 나타나고, 거기서 제거하면 콘솔 창 없이 DSA의 제거 창이 다시 묻지 않고 진행과 결과를 보여 주며, 게스트에서 지워지고 목록과 시작 메뉴에서 사라진다. DSA를 제거하면 이 항목이 모두 사라진다. (수동 확인)

### FR-24 백그라운드에서 도는 앱 (`Agreed`)
창을 모두 닫아도 포그라운드 서비스로 계속 도는 앱(음악 재생, 내려받기, VPN 등)은 사용자 눈에 보여야 하고, 사용자가 멈출 수 있어야 한다. 창이 없으면 사용자는 그 앱이 아직 돌며 메모리와 CPU를 쓰는지 알 수 없기 때문이다.
- 에이전트는 포그라운드 서비스의 시작과 끝, 그 서비스의 진행 중(ongoing) 알림, 미디어 세션을 관찰해 제어 채널로 보낸다. 메시지 형식은 프로토콜 정의에서 생성한다.
- 포그라운드 서비스를 돌리는 앱마다 Windows 알림 영역(시스템 트레이)에 아이콘 하나를 둔다. 아이콘은 앱의 아이콘이고, 도구 설명은 진행 중 알림의 제목과 본문이다. 아이콘의 정체성은 앱마다 고정된 GUID로 정해, Windows가 앱마다 표시 설정을 따로 기억하게 한다. 아이콘은 창 관리자(`dsa-wm`)가 가진다.
- 아이콘을 왼쪽 단추로 누르면 앱의 태스크 창을 연다. 오른쪽 단추 메뉴는 열기, 진행 중 알림의 동작(미디어라면 일시 정지, 다음 등이며 그 `PendingIntent`를 게스트에서 실행한다), 중지다. 메뉴는 Windows 11의 메뉴 모양(둥근 모서리, 그림자, 테마와 강조색, 아이콘과 간격)을 따른다. 기본 Win32 팝업 메뉴는 쓰지 않는다.
- 중지는 그 앱의 패키지를 강제 중지한다. 처음에는 확인을 묻고, "다시 묻지 않음"을 고르면 다음부터 묻지 않는다. 이 선택은 설정 값이고 동반 서비스가 저장한다.
- 아이콘은 포그라운드 서비스가 시작되면 나타나고, 서비스가 끝나거나 앱이 중지되면 사라진다.
- 진행 중 알림은 반복되는 토스트로 띄우지 않고 트레이 아이콘으로만 보인다. 일반 알림은 FR-8대로 토스트로 띄운다.
- 미디어 세션을 가진 앱은 Windows 미디어 컨트롤(SystemMediaTransportControls)에 연결한다. 제목, 아티스트, 앨범 아트와 재생 상태가 Windows 미디어 플라이아웃에 보이고, 재생, 일시 정지, 다음, 이전 키를 누르면 게스트 미디어 세션의 해당 동작을 실행한다. 그 앱의 창이 열려 있으면 작업 표시줄 미리보기에 이전, 재생 또는 일시 정지, 다음 단추(썸네일 도구 모음)를 두고, 재생 상태와 세션이 허용하는 동작에 따라 바꾼다.
- DSA 설정 앱은 "백그라운드에서 실행 중" 항목에 같은 목록(앱 아이콘, 이름, 알림 제목)과 앱마다 중지 단추를 보여 준다.
- 수용 기준: 게스트 앱이 포그라운드 서비스를 시작하면 에이전트가 그 패키지, 알림 제목, 본문, 동작을 보내고, 서비스가 끝나면 끝났다고 보낸다. 진행 중 알림은 토스트로 가지 않는다.
- 수용 기준: 창 관리자는 포그라운드 서비스를 돌리는 앱마다 트레이 아이콘을 정확히 하나 두고, 같은 앱에는 늘 같은 GUID를 쓰며, 서비스가 끝나거나 앱이 중지되면 아이콘을 지운다.
- 수용 기준: 메뉴의 중지는 처음에 확인을 묻고, "다시 묻지 않음" 뒤에는 묻지 않으며, 확인하면 게스트에 그 패키지의 강제 중지를 요청한다.
- 수용 기준: 미디어 세션을 가진 앱의 창 미리보기에 이전, 재생 또는 일시 정지, 다음 단추가 있고, 누르면 게스트 세션의 그 동작이 실행되며, 재생 상태가 바뀌면 단추 모양이 따라 바뀐다. (`fr24_the_taskbar_preview_has_media_buttons`)
- 수용 기준: 트레이 아이콘의 오른쪽 단추 메뉴가 Windows 11 메뉴 모양으로 열리고 기존 항목과 동작이 같다. (`fr24_the_tray_menu_looks_like_windows_11`)
- 수용 기준: 미디어 세션의 재생 상태와 메타데이터가 SystemMediaTransportControls에 반영되고, 미디어 키가 게스트 세션의 재생, 일시 정지, 다음, 이전으로 전달된다.
- 수용 기준: 설정 앱의 "백그라운드에서 실행 중" 항목이 같은 목록을 보이고, 중지 단추가 그 앱을 멈추며 목록에서 지운다.
- 수용 기준: 실제 PC에서 음악 재생을 시작하고 그 창을 닫으면 제목을 단 트레이 아이콘이 나타나고, 미디어 키가 재생을 제어하며, 중지를 누르면 재생이 멈추고 아이콘이 사라지며 그 앱의 메모리가 돌아온다. (수동 확인)

### FR-25 ARM 앱 번역 계층 플러그인 (`Agreed`)
대부분의 안드로이드 앱은 ARM용 네이티브 라이브러리만 담고 있어 x86_64 게스트에서 설치되지 않거나 멈춘다. 배포할 수 있는 번역기는 아직 없으므로(RESEARCH R9), 사용자나 DSA가 준 번역기(네이티브 브리지)를 끼울 수 있는 구조를 둔다.
- 번역 묶음은 디렉터리 하나다. `arm-translation.json`(이름, 버전, 브리지 라이브러리 파일 이름, ABI 목록, 라이선스)과 `system.img`(erofs, 안에 `system/lib64`, `system/bin`, `system/etc` 아래 놓일 파일)를 담는다. 브리지 라이브러리 이름은 영숫자, `.`, `_`, `-`로 된 `.so` 파일 이름이다. 이미지는 브리지를 `system/lib64/libdsa_native_bridge.so`라는 이름으로도 담는다(링크). 이미지의 속성이 번역기와 상관없이 이 이름을 가리키기 때문이다. ABI는 `arm64-v8a`만 받는다. 게스트는 64비트 전용이라 `armeabi-v7a`를 돌릴 zygote가 없기 때문이다.
- `dsa arm-translation status|install <경로>|remove`. install은 묶음을 검사하고 erofs 이미지로 만들어 호스트의 추가 구성 요소 디스크에 둔다. 안드로이드가 꺼져 있으면 켜고 처리한다. remove는 그것을 지운다. 둘 다 다음 안드로이드 시작부터 적용되고, 그것을 알린다.
- 동반 서비스는 설치된 묶음의 설명을 사용자 설정에 두고, 설정 `arm-translation`(`on`, `off`, 기본 `on`)이 켜져 있고 묶음이 있을 때만 부팅 bootconfig에 `androidboot.dsa.arm_translation=on`을 넣는다.
- 게스트는 그 값이 있을 때만 `ro.dalvik.vm.native.bridge`(`libdsa_native_bridge.so`), `ro.dalvik.vm.isa.arm64=x86_64`, `ro.enable.native.bridge.exec=1`을 정하고, `ro.product.cpu.abilist`와 `abilist64`에 `arm64-v8a`를 덧붙이며, `system.img`(erofs)를 마운트하고 그 안의 각 부분을 이미지가 미리 마련한 빈 자리에 연결(bind mount)한 뒤 binfmt_misc 처리기를 등록한다. 시스템의 `lib64`, `bin`, `etc` 전체 위에는 아무것도 얹지 않는다. 그 폴더의 프로그램이 제 SELinux 도메인으로 시작하지 못해 부팅이 깨지기 때문이다. 값이 없으면 이미지는 `x86_64`만 알리고 아무것도 마운트하지 않는다.
- 제어 데몬은 연결할 때마다 묶음이 있는지, 얹혔는지, 패키지 관리자가 보는 ABI 목록(`ro.product.cpu.abilist`)을 호스트에 보고한다.
- 설정 앱에 "ARM 앱" 항목을 둔다. ARM 앱을 돌릴 수 있는지, 설치된 번역기의 이름, 버전, 라이선스, 지금의 ABI 목록, 켜고 끄는 스위치, 제거 단추, 다시 시작이 필요하다는 안내를 보여 준다.
- 배포할 수 있는 오픈 소스 번역기가 생기면 CI가 스크립트로 받아 빌드하고 기본 묶음으로 넣는다. 그때까지 저장소는 후보(Digitalis)를 받아 묶음을 만드는 스크립트를 둔다.
- 번역기는 사용자가 고른다. 어느 것도 강제하지 않는다. 고를 수 있는 것은 셋이다. 사용자가 가진 묶음(Digitalis 같은 오픈 소스 번역기로 만든 것), 위의 기본 묶음(생기면), 그리고 Google의 ARM 번역기다. Google 것을 쓰지 않아도 다른 둘로 같은 기능을 쓸 수 있어야 한다.
- 기본 묶음이 있는 x86_64 이미지는 처음부터 그 묶음으로 번역한다. 사용자가 Google 것이나 자기 묶음으로 바꾼 뒤에도 설정 앱에서 기본 묶음으로 되돌릴 수 있다. ARM64 이미지에는 기본 묶음이 없다(FR-27).
- x86 우선: 앱이 x86_64 코드를 가지면 번역 없이 x86_64로 돌리고, 그럴 수 없을 때만 arm64로 번역한다. 번역은 느리고 메모리를 더 쓰기 때문이다.
  - ABI 목록은 번역이 켜져 있어도 `x86_64`가 앞이다. 그래서 패키지 관리자와 스토어는 x86_64 라이브러리를 가진 앱을 x86_64로, ARM 라이브러리만 가진 앱만 arm64로 설치한다.
  - 호스트가 설치하는 APK(FR-11의 설치 관리자, 끌어 놓기, 명령줄)는 설치 전에 `lib/` 아래 ABI별 라이브러리 이름을 비교한다. 분할 APK는 분할을 합쳐 비교한다. `x86_64` 쪽이 `arm64-v8a` 쪽에 있는 라이브러리를 빠뜨렸고 번역기가 켜져 있으면 `arm64-v8a`로 설치한다. 일부만 담긴 x86_64 라이브러리로 설치되면 앱이 실행 중에 라이브러리를 찾지 못해 끝나기 때문이다.
  - 설정 앱의 앱 페이지에 앱마다 "ARM으로 실행" 스위치를 둔다. 기기에 그 앱의 arm64 라이브러리를 담은 APK가 있고 번역기가 켜져 있을 때만 켤 수 있다. 바꾸면 그 ABI로 다시 설치한다. 데이터를 지킨 채 다시 설치할 수 없으면 확인 창에서 데이터가 지워진다고 알린다.
  - 에이전트는 앱이 네이티브 라이브러리를 읽지 못해 끝나면(`UnsatisfiedLinkError`, `dlopen failed`) 호스트에 알린다. 호스트는 그 앱을 arm64로 다시 설치할 수 있으면 그것을 제안하는 알림을 띄운다.
- Google의 ARM 번역기는 사용자가 고를 때만 받는다. DSA는 그 파일을 싣거나 다시 배포하지 않는다. 사용자의 PC가 게스트와 같은 안드로이드 버전의 Google x86_64 에뮬레이터 이미지(Google APIs)를 Google의 SDK 저장소에서 직접 받고, 호스트가 그 안에서 번역기에 필요한 파일(`libndk_translation.so`와 그것이 쓰는 라이브러리, 실행 파일, 설정 파일)만 꺼내 위의 묶음 형식으로 만들어 설치한다. 받은 이미지의 해시는 저장소 목록의 값과 맞아야 하고, 다 쓴 이미지는 지운다. 받기 전에 출처와 Google의 약관(Android SDK 라이선스)을 확인 창으로 알린다. `dsa arm-translation fetch google`과 설정 앱 "ARM 앱" 항목의 단추가 이 일을 한다. 번역이 필요 없는 ARM64 호스트(FR-27)에서는 보이지 않는다.
- 수용 기준: 가짜 SDK 저장소 목록과 가짜 이미지에서 게스트와 같은 버전의 이미지를 고르고, 번역기 파일만 꺼낸 묶음이 묶음 검사를 통과한다. 해시가 목록과 다르거나 맞는 버전이 없으면 거부되고 저장된 상태가 바뀌지 않는다.
- 수용 기준: 실제 PC에서 Google 번역기를 받아 설치하고 다시 시작하면 `arm64-v8a` 전용 앱(APKPure)이 열린다. 사용자 묶음으로 바꿔도 같은 일이 된다. 기본 묶음으로 되돌려도 같은 일이 된다. (수동 확인)
- 수용 기준: 가짜 APK(x86_64와 arm64 라이브러리가 모두 있음, x86_64 쪽이 일부 빠짐, arm64만 있음, 네이티브 라이브러리 없음, 분할 APK)에서 고르는 ABI가 각각 `x86_64`, `arm64-v8a`, `arm64-v8a`, 지정 없음, 분할을 합친 결과다. 번역기가 꺼져 있으면 `arm64-v8a`를 고르지 않는다.
- 수용 기준: 에이전트가 가짜 꺼짐 기록에서 네이티브 라이브러리 오류로 끝난 앱만 골라 알리고, "ARM으로 실행" 스위치의 뷰모델이 켤 수 없는 조건에서 꺼진 채 이유를 보인다.
- 수용 기준: 실제 PC에서 x86_64와 arm64를 모두 가진 앱이 번역 없이 x86_64로 돌고(`dumpsys package`의 `primaryCpuAbi`), "ARM으로 실행"을 켜면 arm64로 다시 설치되어 번역기로 돈다. (수동 확인)
- 수용 기준: 묶음이 없거나 설정이 꺼져 있으면 bootconfig에 번역 값이 없고, 있고 켜져 있으면 들어간다.
- 수용 기준: 이미지 검사가 어떤 `build.prop`도 스스로 네이티브 브리지를 켜지 않고(`ro.dalvik.vm.native.bridge`가 없거나 `0`), product `build.prop`이 번역 값에 따라 속성 파일을 가져오는 줄로 끝나며, 번역 값이 있을 때만 묶음을 얹는 init 스크립트가 있음을 확인한다.
- 수용 기준: 설명 파일이 없거나 틀린 묶음(허용하지 않는 라이브러리 이름, `arm64-v8a`가 아닌 ABI, erofs가 아닌 `system.img`)은 거부되고 저장된 상태가 바뀌지 않는다.
- 수용 기준: `dsa arm-translation install`, `status`, `remove`가 로컬 API를 거쳐 묶음을 보내고, 상태를 보이고, 지운다.
- 수용 기준: ARM 번역이 켜진 x86_64 게스트에서, arm64-v8a 네이티브 코드만 가진 앱은 multiArch 여부나 targetSdk와 상관없이 arm64-v8a로 설치되어 번역으로 실행된다. Google Play 설치와 호스트 설치(설치 창, 끌어 놓기, `dsa install`)가 모두 해당한다. x86_64 코드가 arm64-v8a 라이브러리를 모두 포함하는 앱은 x86_64로 설치된다. 32비트 코드만 가진 앱은 번역 여부와 상관없이 거부된다. ARM 번역이 꺼져 있으면 arm64-v8a 전용 앱(그 코드가 분할 APK에만 있는 번들 포함)은 안드로이드에 보내기 전에 거부되고, 사용자에게 ARM 번역이 꺼져 있으니 "ARM 앱"에서 켜고 안드로이드를 다시 시작한 뒤 다시 설치하라는 이유를 알린다. 이미지 검사는 이 동작에 필요한 이미지 편집이 빠진 이미지를 거부한다.
- 수용 기준: 설정 앱의 "ARM 앱" 항목이 묶음이 없을 때와 있을 때, 꺼져 있을 때의 상태 문구, ABI 목록, 다시 시작 안내를 보여 주고, 스위치와 제거 단추가 CLI와 같은 일을 한다. 뷰모델 테스트가 이것을 확인하고, 밝은 테마와 어두운 테마, 영어와 한국어의 모양은 수동으로 확인한다.
- 수용 기준: 실제 PC에 번역 묶음을 설치하고 안드로이드를 다시 시작하면 `getprop ro.product.cpu.abilist`가 `x86_64,arm64-v8a`이고, `arm64-v8a` 전용 APK가 설치되어 열린다. 묶음을 지우고 다시 시작하면 `x86_64`로 돌아오고 같은 APK는 ABI가 맞지 않는다며 설치되지 않는다. (수동 확인)

### FR-26 호스트 장치: 마이크, 카메라, 위치, 센서, 인쇄 (`Agreed`)
WSA가 안드로이드 앱에 준 장치(카메라 앞뒤, 마이크, 위치와 GPS, 인쇄)를 모두 제공하고, PC에 있는 센서를 더한다. 각 장치는 PR-4의 호스트 HAL로 게스트와 잇는다. 장치마다 Windows 개인 정보 설정과 안드로이드 런타임 권한이 둘 다 적용되어야 한다. 한쪽만 적용하면 사용자가 Windows에서 끈 장치를 안드로이드 앱이 쓰게 되거나, 안드로이드에서 거절한 앱이 장치를 쓰게 되기 때문이다.
- 소리 크기: 소리 크기는 Windows 하나로 조절한다. 안드로이드 안의 스트림 볼륨은 소리를 줄이지 않고(0 dB) 그대로 호스트로 보낸다. 안드로이드 볼륨과 Windows 볼륨이 겹쳐 소리가 이중으로 작아지지 않게 하기 위해서다. 앱마다 Windows 볼륨 믹서에 자기 이름과 아이콘의 줄이 생기고, 앱이 자기 볼륨을 바꾸거나 안드로이드 볼륨 키가 눌리면 그 줄의 볼륨이 바뀐다. Windows에서 바꾼 앱 볼륨과 음소거는 안드로이드 앱이 읽는 볼륨 값에도 반영된다. macOS와 Linux는 그 운영체제의 앱별 볼륨(PulseAudio와 PipeWire의 스트림 볼륨, macOS는 앱 볼륨이 없으므로 시스템 볼륨)을 같은 방식으로 쓴다.
- 수용 기준: 안드로이드 미디어 볼륨과 상관없이 호스트로 가는 PCM이 앱이 낸 그대로이고, 앱이 볼륨을 바꾸면 호스트의 그 앱 세션 볼륨이 바뀌며, 호스트에서 바꾼 앱 볼륨이 안드로이드 볼륨 값으로 돌아온다. (`fr26_volume_is_controlled_on_the_host_only`)
- 마이크: 오디오 HAL의 입력 스트림이 Windows 기본 녹음 장치(WASAPI 공유 모드)에서 소리를 받는다. 출력 스트림(PR-4)과 같은 포트와 전송 방식을 쓴다.
- 카메라: 카메라 공급자 AIDL HAL이 Windows Media Foundation 카메라를 안드로이드 카메라로 보인다. 패널 위치가 앞인 카메라는 `LENS_FACING_FRONT`, 뒤는 `LENS_FACING_BACK`, 알 수 없거나 외장은 `LENS_FACING_EXTERNAL`이다. 미리 보기, 사진, 동영상에 쓸 해상도와 프레임 속도를 장치가 지원하는 형식에서 고르고, 센서 방향을 알린다.
- 위치: GNSS AIDL HAL이 Windows 위치 API(`Windows.Devices.Geolocation`)의 위치를 `GpsLocationProvider`로 보낸다. 정확도, 고도, 속도, 방향이 있으면 같이 보낸다.
- 센서: 센서 AIDL HAL이 `Windows.Devices.Sensors`의 가속도계, 자이로스코프, 방향(회전 벡터), 조도 센서를 안드로이드 센서로 보인다. PC에 없는 센서는 목록에 넣지 않는다.
- 인쇄: 게스트의 인쇄 서비스가 문서를 PDF로 호스트에 넘기고, 호스트는 Windows 인쇄 대화 상자로 프린터를 고르게 해 인쇄한다.
- Windows가 그 장치를 막았으면(개인 정보 설정에서 꺼짐, 장치 없음) HAL은 장치가 없거나 사용할 수 없다고 알리고, 앱은 안드로이드의 정상적인 실패 경로를 탄다. 호스트 프로세스는 죽지 않는다.
- 호스트가 장치를 쓰는 동안 Windows 작업 표시줄의 사용 중 표시가 DSA에 대해 나타난다. 쓰지 않을 때는 장치를 열어 두지 않는다.
- 수용 기준: 가짜 녹음 장치가 주는 PCM이 오디오 HAL 입력 스트림의 `read`로 같은 순서와 형식으로 나오고, 녹음 장치가 막혔으면 스트림 열기가 오류를 돌려준다.
- 수용 기준: 가짜 카메라 목록(앞, 뒤, 외장)이 카메라 공급자에서 올바른 방향과 형식 목록의 장치로 보이고, 요청한 스트림 형식에 맞는 프레임이 결과로 나오며, 막힌 카메라는 목록에서 빠진다.
- 수용 기준: 가짜 위치 공급자의 위치가 GNSS HAL 콜백으로 같은 값으로 나오고, 위치 권한이 거부되면 위치를 보내지 않고 상태를 알린다.
- 수용 기준: 가짜 센서 목록에서 있는 센서만 안드로이드 센서 목록에 나오고, 읽은 값이 안드로이드 단위(m/s², rad/s, lux)로 바뀌어 이벤트로 나온다.
- 수용 기준: 게스트가 보낸 PDF가 호스트의 인쇄 작업으로 넘어가고, 사용자가 취소하면 게스트 인쇄 작업이 취소로 끝난다.
- 수용 기준: 실제 PC에서 녹음 앱, 카메라 앱, 지도 앱, 센서 확인 앱, 인쇄로 각 장치가 동작하고, Windows에서 그 장치를 끄면 앱이 오류를 보이며 DSA는 계속 돈다. (수동 확인)

### FR-27 ARM64 Windows 호스트 (`Agreed`)
Snapdragon PC 같은 ARM64 Windows에서도 x64와 같은 DSA를 쓸 수 있게 한다. 게스트는 ARM64 안드로이드라서 ARM 앱이 번역 계층 없이 그대로 돈다. 32비트 ARM(`armeabi-v7a`) 앱은 지원하지 않는다. 최근 ARM64 SoC가 32비트 실행을 뺐고, 게스트를 64비트 전용으로 두면 이미지와 메모리가 작아지기 때문이다.
- 게스트 이미지는 `aosp_cf_arm64_only_phone` 공개 빌드에서 만든다. 지원하는 안드로이드 버전마다 x86_64와 같은 방식으로 빌드 ID와 SHA-256을 고정한다. DSA의 게스트 바이너리(channeld, hwcomposer, codec2, 전원과 배터리 HAL, 오디오 HAL, 에이전트)는 arm64로도 빌드한다.
- 커널은 WSL 커널을 arm64로 빌드하고 DSA의 설정 조각과 패치를 그대로 적용한다. Hyper-V ARM64의 vmbus, 메모리 반환, hvsocket, 합성 장치를 쓴다.
- 호스트 프로그램(`aarch64-pc-windows-msvc`), 설정 앱(`win-arm64`), 그래픽 렌더러, 설치 파일은 ARM64용을 따로 만든다. 렌더러는 기기의 Vulkan 드라이버를 쓴다.
- HCS VM 구성은 호스트 아키텍처에 맞춘다. 두 아키텍처의 차이는 플랫폼 계층 안에 둔다.
- 수용 기준: CI가 ARM64 설치 파일, ARM64 게스트 이미지, arm64 커널을 x64 것과 함께 만든다.
- 수용 기준: ARM64 설치 파일은 ARM64 Windows에만 설치되고, x64 설치 파일과 같은 파일 구성과 기능을 가진다. ARM64 러너에서 설치 시험이 돈다.
- 수용 기준: 이미지 검사기가 arm64 이미지의 커널 형식(`Image`), 파티션, 게스트 바이너리의 아키텍처를 확인한다.
- 수용 기준: 실제 ARM64 PC에서 `arm64-v8a`만 담은 APK가 설치되고 번역 계층 없이 돈다. 그 밖의 기능은 x64 호스트와 같다. (수동 확인)

### FR-28 네트워크 (`Agreed`)
WSA처럼 안드로이드 앱이 인터넷과 로컬 네트워크를 쓸 수 있게 한다. 지금 VM에는 네트워크 장치가 없어서 앱이 아무 데도 연결하지 못한다.
- 기본은 NAT다. 호스트 네트워크 서비스(HCN)로 VM 전용 NAT 네트워크를 만들고, VM에 합성 네트워크 어댑터를 붙인다. 게스트 커널은 `hv_netvsc`를 내장하고, 게스트는 DHCP로 주소를 받으며 호스트가 알려 준 DNS를 쓴다. 사용자의 WSL 네트워크와 Hyper-V 가상 스위치 설정은 건드리지 않는다.
- 안드로이드는 이 연결을 와이파이처럼 보인다(인터넷 있음, 데이터 요금 없음). 앱이 `ConnectivityManager`로 연결 상태와 바뀜을 받는다.
- 호스트가 네트워크를 잃거나 바꾸면(와이파이 변경, VPN 연결, 절전 해제) 게스트의 연결이 끊기지 않고 따라간다. 호스트 VPN을 거치는 트래픽은 VPN을 통해 나간다.
- IPv6가 호스트에 있으면 게스트도 IPv6로 나간다.
- 고급 네트워킹(WSA의 "Advanced networking"): 설정에서 켜면 게스트가 호스트와 같은 LAN에 보이게 해 LAN의 기기가 게스트에, 게스트가 LAN 기기에 직접 닿는다. 기본은 끔이다. 끄면 NAT만 쓴다.
- 호스트에서 게스트로: `localhost`가 아닌 게스트 주소로 호스트 프로그램이 게스트의 서버에 닿는다. adb(FR-20)는 지금처럼 loopback에만 연다.
- DNS: 게스트의 DNS 질의는 호스트의 해석기가 답한다(제어 채널이나 hvsocket으로 넘기고, 호스트는 운영체제 해석기 API로 푼다). 호스트의 DNS 필터, VPN의 분할 DNS, 호스트 파일, 회사의 이름 해석 규칙이 안드로이드 앱에도 Windows 앱과 같게 적용되게 하기 위해서다. NAT 게이트웨이나 공용 DNS로 직접 묻지 않는다.
- 신뢰 인증서: 호스트 운영체제가 신뢰하는 루트 인증서 가운데 사용자나 관리자가 더한 것(Windows의 컴퓨터와 사용자 "신뢰할 수 있는 루트 인증 기관" 저장소에서 운영체제 기본 목록에 없는 것, 그룹 정책으로 배포된 것, macOS 키체인과 Linux 시스템 저장소에서 같은 것)을 안드로이드가 시스템 인증서로 신뢰한다. 호스트에서 인증서를 더하거나 빼면 다시 시작하지 않고 따라간다. 인터넷 필터(NetFree, Techloq 같은 것)와 회사 프록시가 HTTPS를 검사하려고 설치한 인증서를 안드로이드 앱도 믿어야 그 컴퓨터에서 앱이 인터넷을 쓸 수 있기 때문이다. 안드로이드 기본 목록은 그대로 두고 더하기만 한다. 설정 앱의 네트워크 페이지에 가져온 인증서의 이름과 출처를 보이고, 이 기능을 끌 수 있다(기본은 켬).
- 설정 앱에 네트워크 페이지를 두고 상태(주소, DNS, 모드)와 고급 네트워킹 스위치를 보인다.
- 수용 기준: HCS VM 문서에 네트워크 어댑터가 있고, HCN NAT 네트워크와 엔드포인트가 VM마다 만들어지고 VM이 멈추면 지워진다. 같은 이름의 네트워크가 남아 있으면 다시 쓴다.
- 수용 기준: 커널 설정에 `hv_netvsc`가 내장되고, 이미지 검사기가 게스트 네트워크 설정(DHCP, DNS)을 확인한다.
- 수용 기준: 호스트 해석기에만 있는 이름(가짜 해석기나 hosts 항목)을 안드로이드 앱이 같은 주소로 풀고, 호스트 해석기가 막은 이름은 안드로이드에서도 풀리지 않는다. (`fr28_android_resolves_names_through_the_host`)
- 수용 기준: 호스트 저장소에 가짜 루트 인증서를 더하면 그 인증서로 서명한 서버에 안드로이드 앱이 HTTPS로 연결되고, 인증서를 빼거나 기능을 끄면 연결이 거부된다. 운영체제 기본 목록의 인증서는 가져오지 않는다. (`fr28_android_trusts_the_root_certificates_the_host_added`)
- 수용 기준: 실제 PC에서 브라우저 앱이 웹 페이지를 열고, 호스트 와이파이를 바꾸거나 절전 뒤 깨어나도 다시 연결하며, 고급 네트워킹을 켜면 LAN의 다른 기기가 게스트에 닿는다. (수동 확인)

### FR-29 파일 공유 (`Agreed`)
WSA처럼 Windows 사용자 폴더를 안드로이드 앱이 쓰고, 안드로이드 파일을 Windows에서 볼 수 있게 한다.
- 폴더 공유: 설정에서 켜면 Windows 사용자 폴더(문서, 다운로드, 사진, 음악, 동영상, 바탕 화면)가 안드로이드 공유 저장소에 보인다. 호스트가 hvsocket 위의 파일 서버(9P 또는 virtiofs)로 내보내고, 게스트가 마운트한다. 기본은 켬이고 설정에서 끌 수 있다. 공유할 폴더를 고를 수 있다.
- 안드로이드 쪽 권한은 안드로이드 저장소 권한을 그대로 따른다. 호스트 파일 시스템의 ACL은 DSA 서비스가 아니라 로그인한 사용자 권한으로 적용한다.
- 안드로이드 파일 보기: 안드로이드 공유 저장소를 여는 "DSA Files" 항목은 Windows 탐색기 탐색 창의 "Android"로만 노출하고, WSL의 "Linux" 항목 바로 아래에 둔다. 시작 메뉴와 Windows 검색에는 나타나지 않는다. 설치와 업그레이드는 이전 버전이 남긴 시작 메뉴 항목을 지우고, 제거 후에는 아무것도 남지 않는다.
- 끌어 놓기: Windows 탐색기에서 파일을 안드로이드 앱 창에 끌어 놓으면 그 파일이 앱에 공유된다(`ACTION_SEND` 또는 앱이 받는 드래그 앤 드롭). APK를 끌어 놓으면 설치(FR-11)로 간다.
- 수용 기준: 공유를 켜면 게스트에서 호스트 폴더의 파일을 읽고 쓰며, 끄면 마운트가 사라진다. 경로 밖으로 나가는 요청(`..`, 심볼릭 링크)은 거절된다.
- 수용 기준: 작업 창의 드롭 대상이 파일 목록을 게스트로 넘기고, 게스트가 받은 파일 내용이 원본과 같다.
- 끌어 내기: 안드로이드 앱이 콘텐츠 URI를 담아 끌기를 시작하면(`View.startDragAndDrop`에 `DRAG_FLAG_GLOBAL`과 URI 읽기 권한), 포인터가 작업 창을 벗어날 때 그 끌기가 파일을 담은 호스트의 기본 끌기가 된다. 탐색기, 바탕 화면, 다른 호스트 앱에 놓을 수 있다.
- 수용 기준: 안드로이드 앱이 콘텐츠 URI로 시작한 끌기를 탐색기에 놓으면 파일이 원래 이름으로 복사되고 내용이 원본과 같다. 텍스트 끌기는 텍스트를 넘긴다. 끌기를 취소하면 호스트에도 게스트에도 남는 것이 없다. 파일 내용은 adb가 아니라 제어 채널로 흘려 보내고, 끌기에 담긴 콘텐츠 밖의 경로는 드러나지 않는다.
- 수용 기준: 실제 PC에서 갤러리 앱이 Windows 사진 폴더의 사진을 보이고, 탐색기의 "안드로이드 파일"에서 앱이 저장한 파일이 보이며, 파일을 앱 창에 끌어 놓아 보낼 수 있다. (수동 확인)

### FR-30 시스템 설정 동기화와 입력 장치 (`Agreed`)
안드로이드가 Windows의 설정을 따르고, PC의 입력 장치를 쓴다.
- 시간대, 언어, 지역 형식: 세션이 시작될 때와 Windows에서 바뀔 때 안드로이드의 시간대, 시스템 언어, 지역 형식을 Windows와 같게 맞춘다. 사용자가 안드로이드에서 따로 바꾸지는 않는다.
- 테마: 안드로이드의 다크 모드가 Windows 앱 모드(밝게, 어둡게)를 따른다. Windows의 강조 색이 안드로이드 강조 색(Material You의 시드 색)으로 간다.
- 게임패드: Windows가 아는 게임패드(XInput, GameInput)를 안드로이드 게임패드 입력 장치로 보인다. 단추, 스틱, 트리거, 연결과 끊김이 앱에 닿는다. 진동이 있으면 보낸다.
- 앱별 창 호환: 세로 고정 앱은 세로 창으로 열린다. F11이나 앱이 요청한 전체 화면은 그 창을 전체 화면으로 만든다. 앱이 PIP를 요청하면 항상 위에 있는 작은 창이 된다. 설정의 앱 페이지에서 앱마다 크기 조절 허용과 시작 크기를 바꿀 수 있다.
- 수용 기준: 가짜 Windows 설정이 바뀌면 게스트에 시간대, 언어, 다크 모드, 강조 색 메시지가 가고, 게스트 에이전트가 그 값을 시스템에 적용한다.
- 수용 기준: 가짜 게임패드의 상태가 게스트 uinput 게임패드 이벤트로 같은 값으로 나온다.
- 수용 기준: 세로 고정 작업은 높이가 너비보다 큰 창으로 열리고, 전체 화면 요청은 창을 모니터 크기로 만들며, PIP 요청은 항상 위 창이 된다.
- 수용 기준: 실제 PC에서 Windows 테마를 바꾸면 열려 있는 앱이 따라 바뀌고, 게임패드로 게임을 할 수 있다. (수동 확인)

### FR-31 데이터 초기화 (`Agreed`)
- 데이터 초기화: 설정 앱에서 안드로이드 데이터를 지울 수 있다. 확인 창을 거친 뒤 세션을 멈추고 사용자 데이터 디스크를 새 디스크로 바꾼다. 설치한 앱, 계정, 앱 데이터가 지워진다는 것을 확인 창에 적는다. 시스템 이미지와 DSA 설정은 그대로 둔다.
- 수용 기준: 초기화 뒤 데이터 디스크가 새것이고 다음 시작에서 설치된 사용자 앱이 없으며, 시스템 이미지와 설정 파일은 바뀌지 않는다.

### FR-32 Google Play 설치 도구 (`Agreed`)
DSA는 Google Play 서비스와 스토어를 싣지 않는다(C6). 대신 사용자가 설정 앱에서 고르면 공개 GApps 패키지를 받아 설치한다. 설치하지 않는 것이 기본이고, 설치하지 않아도 DSA의 다른 기능은 그대로 쓴다.
- 패키지는 LiteGapps의 Core 구성이다. Play 서비스, Play 스토어, 서비스 프레임워크에 더해 계정 동기화 같은 핵심 구성 요소를 담는다. Lite 구성은 동기화 구성 요소가 없어 Play에서 받은 캘린더와 주소록이 동기화되지 않을 수 있어서 쓰지 않는다. 게스트의 안드로이드 버전(API 36, 37)과 아키텍처(x86_64, arm64)에 맞는 최신 파일을 LiteGapps 배포처에서 받고, zip 구조와 공개된 체크섬(있으면)을 검사한다.
- 호스트는 패키지의 시스템 파일(앱, 권한 목록, 설정 파일, 프레임워크 파일)을 erofs 이미지로 만들어 호스트의 추가 구성 요소 디스크에 둔다. 다음 시작부터 그 이미지를 마운트하고, `/product`와 `/system_ext`의 앱, 시스템 앱, 프레임워크, 권한과 설정 폴더에만 겹친다. 파티션 전체에는 겹치지 않는다. 그 파티션의 `bin`에 있는 서비스가 시작하지 못해 부팅이 깨지기 때문이다. 시스템 이미지는 바꾸지 않는다.
- 추가 구성 요소 디스크: 사용자가 설치한 추가 구성 요소(Google 앱 FR-32, ARM 번역기 FR-25, Widevine FR-37)의 erofs 이미지는 사용자마다 하나인, 호스트가 VM에 읽기 전용으로 붙이는 디스크에 담는다. 게스트는 그 이미지들을 이 디스크에서 직접 마운트한다. 공개된 패키지라 암호화할 까닭이 없고, 암호화된 `/data`에 두면 파일 페이지가 두 번 캐시되어 메모리를 수백 MiB 더 쓰기 때문이다. 디스크 내용은 호스트만 바꾼다. 추가 구성 요소를 설치하거나 지우면 다음 안드로이드 시작부터 적용된다. 이미 `/data`에 있던 이미지는 처음 시작할 때 이 디스크로 옮긴다.
- 수용 기준: 추가 구성 요소의 이미지가 읽기 전용 디스크에서 loop 장치 없이 마운트되고, `/data`에는 그 이미지가 남지 않는다. (`fr32_addons_mount_from_the_read_only_addon_disk`)
- `dsa gapps status|install|remove`. 안드로이드가 꺼져 있으면 켜고 처리한다. 둘 다 다음 안드로이드 시작부터 적용되고, 그것을 알린다.
- 설정 앱에 "Google Play" 항목을 둔다. 설치 상태, 버전, 받은 곳, 설치와 제거 단추, 다시 시작 안내를 보인다. Google 앱은 Google의 약관을 따르고 DSA가 배포하는 것이 아니라는 점과, 인증되지 않은 기기를 등록하는 방법을 알린다.
- 제거하면 다음 시작부터 Google 앱이 사라진다.
- 데스크톱에서 쓸모없는 Play 서비스의 상주 구성 요소(재난 문자, 긴급 위치 전송, 멀미 방지, 근처 기기 존재 알림, Cast 추천, 원격 제스처, AR 위치 같은 것)는 끈다. Play 서비스가 업데이트되면 끈 상태를 다시 적용해, 업데이트가 되살린 구성 요소가 남지 않게 한다. 상주 메모리를 줄이기 위해서다.
- ARM 번역기(FR-25)가 켜져 있어도 ABI 목록에서 `x86_64`가 앞에 온다. Play가 Play 서비스 같은 시스템 구성 요소의 ARM판을 내려 주지 않게 하기 위해서다.
- 수용 기준: 가짜 패키지에서 만든 이미지가 정해진 경로의 파일만 담는다. 허용하지 않는 경로(`..`, 절대 경로)를 담거나 게스트와 아키텍처, 안드로이드 버전이 다른 패키지는 거부되고 저장된 상태가 바뀌지 않는다.
- 수용 기준: `dsa gapps install`, `status`, `remove`가 로컬 API를 거쳐 이미지를 보내고, 상태를 보이고, 지운다.
- 수용 기준: 이미지 검사가 설치 표시가 있을 때만 init이 GApps 이미지를 얹는 것을 확인한다.
- 수용 기준: 설정 앱의 "Google Play" 항목이 설치 전, 설치 뒤, 다시 시작 대기 상태의 문구를 보이고, 단추가 CLI와 같은 일을 한다. 뷰모델 테스트가 이것을 확인한다.
- 수용 기준: 정해 둔 Play 서비스 구성 요소가 꺼져 있고, Play 서비스 업데이트를 흉내 내 구성 요소가 다시 켜지면 곧 다시 꺼진다. (`fr32_desktop_irrelevant_play_services_stay_off_after_updates`)
- 수용 기준: 실제 PC에서 설치하고 다시 시작하면 Play 스토어가 열려 로그인되고, Google 캘린더와 주소록을 받아 동기화된다. ARM 번역기를 켜도 Play 서비스는 x86_64판으로 남는다. 제거하면 Google 앱이 사라진다. (수동 확인)
### FR-33 폰 VM 백엔드 (`Agreed`, 구현은 M9 뒤)
USB로 연결한 안드로이드 폰 안의 VM에서 DSA 안드로이드를 돌리고, 그리기와 창은 PC가 맡는다(INTENT D26). PC의 자원을 아끼고 ARM 앱을 번역 없이 돌리기 위해서다.
- 사용자가 설정 앱과 `dsa backend`에서 실행 위치를 PC VM과 연결된 폰 중에서 고른다. PC VM이 기본이다. 폰을 고르면 DSA는 폰이 비보호 VM을 지원하는지, USB 디버깅이 허용되었는지 확인하고, 안 되면 이유(칩, 권한, 연결)를 알린다.
- 폰 쪽 실행기는 USB 디버깅 권한으로 게스트 VM을 만들고, 폰이 잠기고 화면이 꺼져도 VM이 멈추지 않게 깨우기 잠금을 잡는다. 루팅을 요구하지 않는다. 폰의 앱, 계정, 데이터에는 닿지 않는다.
- 그래픽은 gfxstream 명령으로 PC에 와서 PC의 GPU가 그린다. 화면을 동영상으로 압축해 보내지 않는다. 창, 입력, IME, 셸 통합은 PC VM 백엔드와 같고, 이 문서의 다른 요구사항은 백엔드와 상관없이 적용된다.
- USB가 끊기면 창은 마지막 화면을 보이며 다시 연결을 기다린다. 폰의 VM은 계속 돌고, 다시 연결되면 이어진다.
- 수용 기준: 지원 폰 하나(Pixel 8 이후 또는 Exynos 2600 폰)에서 폰을 잠그고 화면을 끈 채 설정 앱이 PC 창으로 열리고, 30분 동안 멈추지 않는다. 폰의 잠금 화면은 그대로다. (실제 폰에서 확인)
- 수용 기준: 같은 폰에서 설정 앱 목록 스크롤의 프레임 시간과 앱 시작 시간을 USB 3과 USB 2에서 재어, 측정 환경과 함께 기록한다. (실제 폰에서 확인)
- 수용 기준: 비보호 VM을 지원하지 않는 폰이나 USB 디버깅이 허용되지 않은 폰을 고르면, 이유를 알리고 PC VM 백엔드는 그대로 남는다.

### FR-34 시스템 화면 디자인 (`Agreed`)
안드로이드 시스템이 그리는 화면을 One UI 계열 모양으로 그린다(INTENT D27). 앱이 자기 테마로 그리는 화면은 바꾸지 않는다.
- 대상: 설정 앱, 파일 선택기(DocumentsUI), 권한 컨트롤러, 패키지 설치 관리자, 공유 시트, 프레임워크 대화상자와 토스트.
- 큰 제목 영역: 화면 맨 위에 화면 제목을 크게 쓰고, 목록을 스크롤하면 보통 툴바 높이로 접힌다. 창 높이가 600dp보다 낮으면 처음부터 접혀 있다. 데스크톱 창에서 세로 공간을 아끼기 위해서다.
- 목록: 항목을 둥근 카드로 묶고, 카드 사이에 간격을 둔다. 구분선은 카드 안에만 그린다.
- 글꼴과 색: 제목은 굵게 쓴다. 강조색은 파랑 계열이다. 밝은 테마와 어두운 테마를 모두 갖춘다.
- 대화상자: 모서리가 둥글고, 버튼을 아래에 나란히 둔다.
- 방법: 이미지에 정적 리소스 오버레이로 넣는다. 오버레이는 각 이미지의 framework-res와 대상 앱에 맞춰 빌드하고 플랫폼 키로 서명한다. 오버레이로 안 되는 부분만 코드를 고친다.
- 자원: 삼성의 글꼴, 아이콘, 그림을 쓰지 않는다. 글꼴과 그림은 모두 오픈 라이선스이고 NFR-7의 구성 목록에 오른다. "One UI"라는 이름을 화면과 사용자 문서에 쓰지 않는다.
- 수용 기준: 이미지 검사가 대상 패키지마다 오버레이가 있고 그 이미지의 framework-res로 빌드되었는지 확인하고, 없으면 이미지를 거부한다.
- 수용 기준: 높이 800dp 창에서 설정 앱 첫 화면을 열면 큰 제목 영역이 펼쳐져 있고, 목록을 스크롤하면 접힌다. 높이 600dp보다 낮은 창에서는 처음부터 접혀 있다.
- 수용 기준: 설정 앱 목록의 항목이 둥근 카드로 묶여 그려진다. (이미지 테스트의 화면 캡처로 확인)
- 수용 기준: 밝은 테마와 어두운 테마에서 설정 앱, 파일 선택기, 권한 대화상자가 같은 모양 규칙을 따른다. (수동 확인)

### FR-35 관리자 권한 상승 (`Agreed`)
안드로이드 앱이 필요할 때만 호스트의 관리자 승인을 받아 루트로 명령을 실행한다(INTENT D28). 평소에는 게스트에 루트의 흔적이 없다.
- 설정 앱과 `dsa settings set root-elevation on|off`로 기능 전체를 켜고 끈다. 기본은 끔이다. 켜면 다음 안드로이드 시작부터 적용되고, 설정 화면은 이것을 알린다. 끄면 실행 중인 안드로이드에도 바로 적용되어, 다시 시작하지 않아도 모든 앱에서 `su`가 사라지고 승인 요청을 받지 않는다. 끄는 쪽이 더 안전하므로 기다릴 이유가 없어서다. 켜는 것은 호스트 관리자만 할 수 있다.
- 앱마다 수준을 정한다. 설정 앱의 앱 페이지와 `dsa apps root <package> off|ask|remember`로 바꾼다.
  - 요청 불가(`off`, 기본): 그 앱에게 `su`는 없다.
  - 요청할 때 묻기(`ask`): 그 앱이 `su`를 부르면 호스트 관리자 승인을 받는다.
  - 기억(`remember`): 묻지 않고 승인한다. 이 수준으로 바꾸는 일 자체를 호스트 관리자 승인으로 한다.
- 요청 불가 앱에게는 `su`가 경로 탐색, 실행, `stat`, `access`, `/proc` 어디로도 보이지 않는다. 없는 파일과 같은 결과(ENOENT)를 돌려준다.
- 묻기 앱이 `su`를 부르면 호스트가 그 앱의 창 프로그램으로 관리자 승인을 요청한다. 승인 창에는 그 앱의 이름과 아이콘이 나온다. 승인되면 그 명령이나 셸이 uid 0으로 돌고, 거부되거나 1분 안에 답이 없으면 `su`는 실패 코드와 이유로 끝난다.
- 유예: 승인된 뒤 같은 앱은 15분 동안 다시 묻지 않는다. Linux sudo의 기본값과 같다. 유예는 앱마다 따로이고, 기능을 끄거나, 그 앱의 수준을 바꾸거나, 안드로이드가 다시 시작하면 사라진다.
- 같은 사용자 ID를 함께 쓰는 앱(`android:sharedUserId`)은 한 묶음으로 다룬다. 커널은 사용자 ID로만 요청한 쪽을 알아서 묶음 안의 앱을 구별할 수 없고, 요청한 쪽이 밝힌 패키지 이름은 믿을 수 없기 때문이다. 승인 창은 묶음 안의 앱을 모두 보이고 사용자 ID를 함께 쓴다는 점을 알린다. 수준과 유예는 묶음에 적용하고, 설정 앱도 그 앱들을 묶어 보인다. 묶음 안의 앱 하나라도 요청 불가이면 묶음 전체가 요청 불가다.
- 수용 기준: 사용자 ID를 함께 쓰는 두 앱 중 하나를 묻기로 두면 둘 다 `su`를 볼 수 있고, 승인 창에 두 앱이 함께 나온다. 하나를 요청 불가로 두면 두 앱 모두 `su`를 볼 수 없다. (`fr35_apps_sharing_a_user_id_are_approved_as_one_group`)
- `su`는 루트 앱이 흔히 쓰는 형식을 받는다: 대화형 셸(pty), `su -c <명령>`, 표준 입력으로 명령 넘기기, 종료 코드 돌려주기.
- 운영체제마다 승인 수단: Windows는 UAC, macOS는 Authorization Services의 관리자 권한 창, Linux는 polkit이다. Windows에서 UAC가 꺼져 있으면 DSA가 자기 확인 창을 띄우고, 사용자가 관리자 그룹에 없으면 거절한다.
- 기록: 요청한 앱, 시각, 승인 여부, 실행한 명령을 DSA 로그(FR-21)에 남긴다.
- 개발자 모드(FR-20)가 켜져 있으면 `adb shell`도 앱과 같은 방식으로 `su`를 쓴다. 설정 앱과 `dsa apps root`에서 "adb 셸"이라는 항목으로 수준을 고르고, 기본은 묻기다. 승인 창에는 "adb 셸"과 실행할 명령이 나온다. 개발자 모드가 꺼져 있으면 adb 자체가 열리지 않으므로 이 항목도 쓰이지 않는다.
- 기능을 켜도 이미지 파일, 빌드 속성(release-keys, `ro.debuggable=0`), SELinux 강제 모드는 바뀌지 않는다. 루트로 도는 프로세스는 승인된 명령이 도는 동안에만 있다.
- 수용 기준: 기능을 켜도 요청 불가 앱의 프로세스에서 `PATH`의 `su` 탐색, `/system/bin/su`·`/system/xbin/su`·`/sbin/su`의 `stat`과 `access`, `su` 실행이 모두 없는 파일로 끝나고, 빌드 속성과 SELinux 상태가 기능을 끈 때와 같다. (`fr35_an_app_not_allowed_sees_no_su`)
- 수용 기준: 묻기 앱이 `su -c id`를 부르면 호스트 승인 요청이 그 앱의 이름으로 오고, 승인하면 `uid=0`이 출력되며, 거부하면 실패 코드로 끝난다. 승인 뒤 15분 안의 두 번째 요청은 묻지 않고, 15분이 지나거나 안드로이드가 다시 시작하면 다시 묻는다. 다른 앱의 유예는 따로다.
- 수용 기준: 기능을 끄고 안드로이드를 다시 시작하면 모든 앱에서 `su`가 없고, 커널 장치와 중계 데몬이 돌지 않는다.
- 수용 기준: 안드로이드가 도는 중에 기능을 끄면 다시 시작하지 않아도 1초 안에 모든 앱에서 `su`가 보이지 않고, 그 뒤의 승인 요청은 거부된다. (`fr35_turning_the_feature_off_hides_su_at_once`)
- 수용 기준: 요청과 결과가 DSA 로그에 남는다.
- 수용 기준: 기능과 개발자 모드가 켜져 있으면 `adb shell su -c id`가 "adb 셸" 이름으로 승인을 요청하고, 승인하면 `uid=0`이 나오며, 거부하면 실패한다. (`fr35_adb_shell_asks_for_root_like_an_app`)
- 수용 기준: 실제 Windows에서 묻기 앱이 `su`를 부르면 UAC 창에 그 앱의 이름과 아이콘이 나오고, 표준 사용자는 관리자 암호를 넣어야 승인된다. 루트 백업 앱 하나로 루트 작업이 된다. (수동 확인)

### FR-36 호스트 시스템 서비스 (`Agreed`)
안드로이드가 게스트 안에서 따로 돌리거나 Google Play 서비스에 기대는 시스템 서비스를 호스트 운영체제의 같은 기능으로 제공한다. 게스트에 엔진과 데이터를 따로 두지 않아 메모리가 줄고, 결과가 호스트의 다른 앱과 같아진다. 각 서비스는 안드로이드의 공식 확장점으로 게스트에 보이고, 백엔드는 PR-4의 제어 채널로 잇는다. Google Play가 설치되어 있어도 동작한다. 2026-11-10 소유자가 정했다.
- 네트워크 위치: 네트워크 위치 제공자(`LocationProviderBase`)가 FR-26의 호스트 위치를 `network` 제공자로도 보인다. 주소 변환(`Geocoder`)은 Google Play가 없을 때만 DSA가 맡고, 있으면 Google의 것을 그대로 쓴다. DSA의 주소 변환은 호스트에 둔 행정 경계 데이터로 좌표를 시, 구, 동 수준의 주소로 바꾼다. 서버와 키가 필요 없고 위치가 밖으로 나가지 않는다. 번지 단위 주소와 주소를 좌표로 바꾸는 것은 하지 않는다. Windows의 주소 변환 API는 유료 키가 필요한 Bing Maps에 기대고 그 서비스가 끝나 가고, 공개 Nominatim 서버는 많은 사용자의 기본값으로 쓰지 말라는 사용 정책이 있기 때문이다.
- 음성 합성: TTS 엔진(`TextToSpeechService`)이 호스트 음성 합성(Windows `Windows.Media.SpeechSynthesis`, macOS `AVSpeechSynthesizer`, Linux Speech Dispatcher)의 음성 목록을 보이고, 합성한 소리를 돌려준다. 기본 TTS 엔진이다.
- 맞춤법 검사: 맞춤법 검사 서비스(`SpellCheckerService`)가 호스트 맞춤법 검사기(Windows `ISpellChecker`, macOS `NSSpellChecker`, Linux Enchant)로 답한다. 기본 맞춤법 검사기다. 지금 이미지에는 맞춤법 검사기가 없다.
- 공유: 안드로이드의 공유 시트에 "PC에서 공유"를 두어, 고른 내용(글, 링크, 파일)을 호스트의 공유 창(Windows 공유와 근처 공유, macOS 공유 메뉴, Linux는 xdg-desktop-portal)으로 넘긴다.
- 음성 인식: 음성 인식 서비스(`RecognitionService`)가 호스트 음성 인식으로 답한다. 마이크는 FR-26의 권한 규칙을 따른다.
- 백업: 백업 전송(`BackupTransport`)이 앱 데이터 백업을 사용자 프로필 아래 DSA 백업 폴더에 암호화해 저장하고, 데이터 초기화(FR-31)나 다른 PC로 옮긴 뒤 복원한다. 암호화 키는 호스트의 자격 증명 저장소(Windows DPAPI, macOS 키체인, Linux Secret Service)에 둔다. 백업은 사용자가 설정 앱이나 `dsa backup`으로 켤 때만 한다. 기본은 끔이다. 백업은 앱의 사용자 데이터를 PC 디스크에 한 벌 더 두는 것이라, 쓸지는 사용자가 정할 일이기 때문이다.
- 패스키: 자격 증명 제공자(`CredentialProviderService`)가 호스트 패스키(Windows Hello WebAuthn, macOS 패스키)로 패스키를 만들고 쓴다. 앱이 요청한 신뢰 당사자(rpId)가 그 앱의 서명과 Digital Asset Links로 확인될 때만 호스트에 넘긴다. 확인 없이 넘기면 아무 앱이나 다른 사이트의 패스키를 얻기 때문이다.
- 키 보호: 게스트 KeyMint의 루트 키를 호스트 TPM으로 봉인한다. TPM이 없거나 쓸 수 없는 호스트에서만 자격 증명 저장소로 봉인하고, 그 사실을 설정 앱에 알린다. 게스트 디스크를 복사하는 것만으로는 키를 꺼낼 수 없게 하기 위해서다.
- 호스트에 그 기능이 없거나 사용자가 호스트 개인 정보 설정에서 껐으면, 서비스는 사용할 수 없다고 알리고 앱은 안드로이드의 정상 실패 경로를 탄다. 호스트 프로세스는 죽지 않는다.
- 수용 기준: 가짜 호스트 위치가 `network` 제공자의 위치로 나오고, Google Play가 없을 때 알려진 좌표가 `Geocoder`의 `Address`로 그 행정 구역(시, 구, 동)으로 나오고, Google Play가 있으면 DSA는 주소 변환 제공자로 나서지 않는다. (`fr36_network_location_and_geocoder_come_from_the_host`)
- 수용 기준: 가짜 호스트 음성의 목록이 TTS 엔진의 음성으로 보이고, 합성 요청이 호스트에 같은 글과 음성으로 가며 돌아온 소리가 `SynthesisCallback`으로 나온다. (`fr36_tts_speaks_through_the_host`)
- 수용 기준: 가짜 맞춤법 검사기가 틀렸다고 한 단어가 안드로이드의 맞춤법 검사 결과에 제안과 함께 나온다. (`fr36_spell_checking_comes_from_the_host`)
- 수용 기준: 공유 시트에서 "PC에서 공유"를 고르면 글, 링크, 파일이 같은 내용으로 호스트 공유 요청이 된다. (`fr36_sharing_hands_content_to_the_host_share_ui`)
- 수용 기준: 가짜 호스트 음성 인식의 결과가 `RecognitionService`의 결과로 나오고, 마이크가 막혔으면 오류로 끝난다. (`fr36_speech_recognition_comes_from_the_host`)
- 수용 기준: 앱 데이터를 백업하고 데이터를 초기화한 뒤 복원하면 같은 데이터가 돌아오고, 백업 파일은 키 없이 읽을 수 없다. 백업을 켜지 않은 사용자에게는 백업 파일이 생기지 않는다. (`fr36_backup_survives_a_data_reset`)
- 수용 기준: 서명과 Digital Asset Links가 맞는 앱의 패스키 요청만 호스트에 가고, 맞지 않는 rpId는 거절된다. (`fr36_passkeys_only_for_verified_relying_parties`)
- 수용 기준: 봉인된 루트 키는 같은 호스트 사용자에서만 열리고, 디스크를 다른 사용자나 PC로 옮기면 열리지 않는다. (`fr36_keymint_root_key_is_sealed_by_the_host`)
- 수용 기준: 실제 PC에서 지도 앱의 주소 검색, 읽어 주기 앱, 메모 앱의 맞춤법 표시, 공유에서 근처 공유, 음성 검색이 동작한다. (수동 확인)

### FR-37 보호된 콘텐츠 재생 (`Agreed`)
WSA가 제공한 Widevine L3를 제공한다. DSA는 Google 바이너리를 싣지 않으므로(C1, C6), Google ARM 번역기(FR-25)와 Google Play(FR-32)처럼 사용자가 고르면 Google 서버에서 받아 설치한다. 2026-11-10 소유자가 정했다.
- 설정 앱과 `dsa drm widevine install|status|remove`로 설치한다. 호스트는 그 게스트와 같은 안드로이드 버전과 아키텍처의 Google 에뮬레이터 시스템 이미지(`dl.google.com`)에서 Widevine APEX(`com.google.android.widevine`)를 그대로 꺼내 추가 구성 요소 디스크(FR-32)에 둔다. Google이 Widevine을 APEX 하나로만 배포하므로 그 형태 그대로 쓴다. APEX의 내용은 바꾸지 않는다. 다른 출처(제3자 저장소의 추출본)는 쓰지 않는다. 출처와 라이선스를 확인할 수 없기 때문이다.
- 게스트는 부팅 때 apexd가 그 APEX를 활성화하게 한다(vendor APEX로, apexd가 APEX를 읽기 전에 보이는 자리에 둔다). APEX의 서명은 apexd가 Google 키로 확인한다. SELinux 정책(`hal_drm_widevine`, `/data/vendor/mediadrm`)은 DSA 이미지에 미리 둔다. 기기 인증서는 처음 쓸 때 안드로이드의 프로비저닝으로 받는다.
- 보안 수준은 L3이다. 스트리밍 서비스는 L3 기기에 표준 화질(SD)까지만 보낼 수 있으므로, 설정 앱의 이 항목과 사용자 안내는 고화질은 호스트의 브라우저나 앱에서 보라고 알린다.
- Google 이미지에 그 버전의 Widevine이 없으면 설치는 이유를 알리고 실패한다. 이미지에 아무것도 남기지 않는다.
- 수용 기준: 가짜 에뮬레이터 이미지에서 Widevine APEX만 바이트 그대로 꺼내고, 다른 아키텍처나 다른 안드로이드 버전의 APEX면 거절한다. (`fr37_widevine_apex_is_taken_unchanged`)
- 수용 기준: 설치한 게스트에서 `MediaDrm.isCryptoSchemeSupported`가 Widevine UUID에 참을 돌려주고 보안 수준이 L3로 보인다. 설치하지 않은 게스트는 거짓이다. (`fr37_widevine_is_offered_only_when_installed`)
- 수용 기준: 실제 PC에서 설치하고 다시 시작하면 Widevine을 쓰는 스트리밍 앱이 재생된다. (수동 확인)

### FR-38 필터 호환 모드 (`Agreed`, 구현은 나중)
안드로이드 앱의 네트워크 통신을 그 앱의 호스트 프로그램이 대신 보내게 해, 호스트의 인터넷 필터, 방화벽, VPN, 프록시가 안드로이드 앱 하나하나에 Windows 앱과 똑같이 적용되게 한다. 기기에 설치하는 인터넷 필터(Techloq, GenTech 같은 것)는 프로그램 단위로 통신을 거르는데, VM의 NAT 통신은 그 필터가 보지 못하는 경로로 나가 걸러지지 않는 우회로가 되므로, 이런 필터는 DSA를 막거나 지원하지 않는다. 2026-11-11 소유자가 정했다.
- 설정 앱과 `dsa settings set network-mode nat|per-app`으로 고른다. 기본은 NAT(FR-28)다.
- 게스트는 앱의 연결(TCP, UDP)을 앱의 uid로 가려 받아 호스트로 넘긴다. 사용자의 VPN 앱이 쓰는 `VpnService` 자리는 쓰지 않는다.
- 호스트는 그 앱의 창 프로그램(FR-3) 프로세스가 운영체제의 일반 소켓으로 연결을 연다. 창이 없을 때 나가는 통신(푸시, 동기화)은 그 앱의 창 프로그램을 창 없이 띄워 보낸다. 그래서 필터와 방화벽에는 앱 이름의 프로그램이 보인다.
- 이 모드에서 VM에는 외부로 나가는 직접 출구가 없다. 출구가 남으면 필터는 그것을 우회로로 보기 때문이다. 고급 네트워킹(LAN 노출)과 게스트로 들어오는 연결은 이 모드에서 쓸 수 없고, 설정 앱이 그것을 알린다.
- 호스트의 시스템 프록시와 PAC는 호스트 쪽에서 목적지마다 따른다.
- 필터 회사가 DSA를 허용 목록에 올릴 수 있도록, 창 프로그램은 서명을 지닌 채 고정된 위치에 있어야 한다. 서명 방식은 FR-39에서 정한다.
- 수용 기준: 이 모드에서 게스트에는 외부로 나가는 경로가 없고, 앱의 TCP와 UDP 연결이 그 앱의 창 프로그램 프로세스에서 나가며, 호스트 방화벽에서 그 프로그램을 막으면 그 앱만 연결되지 않는다. (`fr38_each_app_reaches_the_network_through_its_own_host_program`)
- 수용 기준: 실제 PC에서 프로그램 단위 필터를 켜고 안드로이드 앱이 필터의 허용과 차단을 그대로 따른다. (수동 확인)

### FR-39 창 프로그램의 코드 서명 (`Draft`, 미확정)
인터넷 필터와 보안 프로그램이 DSA의 창 프로그램(FR-3)을 게시자 서명과 고정된 위치로 허용할 수 있게 한다. 지금 창 프로그램은 앱마다 아이콘을 넣어 고쳐 만든 실행 파일이라 앱마다 해시가 다르고 서명이 없으며, 사용자 폴더에 있다. 소유자가 방식을 아직 정하지 않았다(2026-11-11). 아래는 후보다.
- 안드로이드 앱의 서명은 쓸 수 없다. Windows가 신뢰하는 코드 서명 인증서가 아니고, 그 앱 개발자의 개인 키도 없기 때문이다.
- 후보 1: DSA가 서명한 창 프로그램 원본 하나를 고치지 않고 앱 이름으로 복사해 쓴다. 서명은 파일 이름을 덮지 않아 복사본도 유효하다. 실행 파일 자체의 아이콘은 공통 아이콘이 되고, 작업 표시줄과 시작 메뉴는 바로 가기와 AppUserModelID로 앱 아이콘을 보인다.
- 후보 2: 네트워크는 서명된 공용 프로세스 하나가 맡는다. 필터가 앱별로 허용할 수는 없게 된다.
- 서명 인증서를 어디서 얻을지(오픈소스 무료 서명 SignPath Foundation, 유료 인증서)와 창 프로그램의 위치(Program Files 아래의 고정 경로)도 정해야 한다.

## 4. 비기능 요구사항

### NFR-1 대기 메모리 (`Agreed`)
- 제안 목표: 셸을 걷어내고 Google 서비스 계열이 없는 구성에서, `Dozing` 상태의 전체 메모리(게스트 VM이 쓰는 몫과 동반 서비스의 합)가 800MB 이하다.
- 측정 방법: 세션 시작 10분 뒤 게스트 메모리를 상주분(PSS에서 SwapPss를 뺀 값)과 zram이 실제로 차지하는 크기(SwapPss를 측정한 압축률로 나눈 값)의 합으로, Google Play 서비스가 설치되어 있으면 그 몫을 따로, 게스트 VM의 `vmmem` 프로세스 사용량, 동반 서비스 프로세스의 작업 집합을 함께 기록한다. 측정 환경(RAM, CPU, Windows 빌드)을 같이 적는다. `dumpsys meminfo`의 총 PSS는 zram에 압축된 메모리를 압축 전 크기로 세어 실제 비용보다 크게 나오므로 기준으로 쓰지 않는다.
- 앱을 연 상태의 목표: 단순한 앱 하나(Settings)를 연 `Active` 상태에서 DSA 호스트 프로세스 전체(VM, 창 관리자, 앱 창, 서비스)의 private 작업 집합 합이 단기 400 MiB 이하, 최종 250 MiB 이하다. 앱을 하나 더 열 때마다 늘어나는 몫은 80 MiB 이하다. `Dozing` 목표는 위와 같다.
- 측정 방법: 앱을 연 뒤 1분 동안 손대지 않고 `dsa memory`와 각 프로세스의 private 작업 집합을 기록한다. 다른 앱(예: Electron 앱)을 함께 재지 않는다.

### NFR-2 메모리 반환 (`Agreed`)
- 세션을 종료하면 게스트가 쓰던 메모리가 호스트로 돌아간다.
- 호스트 메모리 압박이 오면 게스트의 캐시 프로세스가 먼저 정리된다.
- 수용 기준: 앱 다섯 개를 열었다 닫고 세션을 종료한 뒤, 정해진 시간 안에 게스트 VM의 `vmmem` 프로세스가 차지한 메모리가 호스트로 돌아온다.
- 안드로이드에 고정된 메모리 상한을 두지 않는다. VM은 작게(2 GiB) 시작하고, 게스트가 메모리가 부족하면 실행 중에 메모리를 더한다(핫애드). 더할 수 있는 최대는 호스트의 물리 메모리에서 Windows 몫(물리 메모리의 10%와 2 GiB 중 큰 값)을 뺀 값이다. 처음부터 큰 VM을 만들지 않는 이유는 커널이 VM 최대 크기의 약 1.6%를 페이지 기록으로 늘 잡기 때문이다. 게스트가 더한 메모리를 더 쓰지 않으면 시작 크기까지 되돌려 준다. VM은 게스트가 쓰는 만큼만 잡는다(지연 커밋, 빈 페이지 보고, 차가운 페이지 회수). zram 크기와 lmkd 기준은 실제 크기에 맞춘다. 상한을 두고 싶은 사용자를 위해 `dsa settings`에 고급 설정으로 상한을 둔다. 3 GiB에서 2 GiB로 줄인 것은 쓰지 않는 메모리를 관리하는 페이지 구조가 쉴 때도 메모리를 차지하기 때문이다(2026-11-11 소유자 결정). Google Play가 있으면 부팅 직후 한두 번 메모리를 더한다.
- 핫애드가 그 PC에서 되지 않으면 VM은 시작 크기를 유지하고 그 사실과 이유를 로그에 남긴다. 그 경우 다른 크기로 대신 시작할지는 따로 정한다.
- 수용 기준: 앱을 여럿 열어 게스트가 부족해지면 서비스 로그에 VM이 커졌다는 줄이 남고 게스트의 `MemTotal`이 늘어난다. 앱을 닫고 1분 안에 VM이 시작 크기 쪽으로 줄고 `vmmem` 상주 메모리가 줄어든다. 32 GB PC에서 `Dozing`의 `vmmem` 상주 메모리와 부팅 시간이 3 GiB 고정일 때와 비교해 눈에 띄게 늘지 않는다. (수동 확인, `measure.ps1 -Part grow`로 수치를 기록한다)
- 앱을 닫으면 캐시로 남기지 않는다. 한 패키지의 마지막 태스크가 사라지면 에이전트가 그 패키지의 프로세스를 바로 끝내고, 풀린 메모리와 페이지 캐시를 회수해 호스트로 돌려준다. 배치된 위젯이 있거나 포그라운드 서비스가 돌고 있는 앱은 끝내지 않는다. 캐시 프로세스 수의 상한은 데스크톱에 맞게 낮춘다. 에이전트는 "closed <package>: returned N MiB in T ms"를 로그에 남긴다.
- 수용 기준: 앱 창을 닫고 몇 초 안에 그 패키지의 프로세스가 없어지고, 위 로그 줄이 남으며, `vmmem` 상주 메모리가 줄어든다. 위젯을 배치한 앱과 포그라운드 서비스가 있는 앱은 남는다.
- 창이 없이 쉬는 프로세스도 메모리 부족을 기다리지 않고 정리한다. 안드로이드는 메모리가 넉넉하면 일을 마친 프로세스(Play 스토어의 예약 작업, Play 서비스의 앱 검증 등)를 캐시로 계속 남기기 때문이다. 에이전트는 캐시 상태로 30초 넘게 쉬고, 액티비티가 없으며, 그 패키지에 태스크 창과 포그라운드 서비스가 없는 프로세스를 끝낸다. 곧 다시 뜨는 프로세스는 기다리는 시간을 두 배씩 늘린다(최대 8분). 끝낼 때 예약 작업, 알람, 알림을 지우지 않고 패키지를 중지 상태로 만들지 않는다. 푸시 알림을 받는 Google Play 서비스의 주 프로세스, 시스템, 상주(persistent) 프로세스, 에이전트는 끝내지 않는다.
- 수용 기준: Play 스토어나 Play 서비스가 일을 마치고 캐시로 남은 프로세스(`com.android.vending`, `com.google.android.gms.unstable` 등)는 1분 안에 없어지고, `com.google.android.gms` 주 프로세스는 남는다. 창이 열려 있어도 다른 패키지의 쉬는 프로세스는 같은 기준으로 정리된다. 포그라운드 서비스가 있는 앱은 남는다. (`nfr2_cached_play_processes_end_after_their_work_and_the_core_stays`, `nfr2_google_play_services_core_is_never_ended_even_when_cached`, `nfr2_an_app_with_a_foreground_service_keeps_its_cached_processes`)

### NFR-3 대기 CPU (`Agreed`)
- 제안 목표: `Dozing` 상태 10분 평균 CPU 사용률(게스트와 동반 서비스 합)이 논리 코어 하나의 1% 이하다.

### NFR-4 창 표시 시간 (`Agreed`)
- 제안 목표: `Dozing` 상태에서 시작 메뉴로 앱을 실행하면 1초 안에 첫 프레임이 태스크 창에 보인다. `Stopped`에서 시작하는 콜드 스타트 시간은 측정해서 기록한다.

### NFR-5 장애 격리 (`Agreed`)
- 게스트가 죽거나 제어 채널이 끊겨도 동반 서비스는 죽지 않는다. 열린 태스크 창을 닫고, 상태를 `Stopped`로 보고하고, 사용자가 다시 시작할 수 있다.
- 잘못된 메시지를 받으면 그 메시지를 버리고 오류를 기록한다. 프로세스를 끝내지 않는다.
- 수용 기준: 게스트 VM을 강제로 끝내도 동반 서비스가 살아 있고, 다시 시작하면 정상 동작한다.
- 호스트 GPU 장치 손실(INTENT D24): 렌더러는 장치 손실이나 게스트가 일으킬 수 있는 어떤 조건(잘못된 명령, 메모리 부족, 너무 큰 자원)에서도 호스트 프로세스를 끝내지 않는다. 장치를 잃으면 새 장치를 만들고, 잃은 자원에 대한 게스트의 호출에 장치 손실을 돌려주며, 그 사실과 원인을 로그에 남긴다.
- 게스트의 SurfaceFlinger와 HWUI는 장치 손실에서 복구한다. GPU 자원과 버퍼를 다시 만들고 모든 창을 다시 그린다. 안드로이드 프레임워크는 다시 시작하지 않고, 열려 있던 앱과 창은 그대로 남는다.
- 고친 SurfaceFlinger와 `libhwui`는 고정한 AOSP 소스 커밋에서 공개 CI 러너로 빌드하고, 지원하는 안드로이드 버전마다 이미지의 같은 파일을 바꾼다. 이미지 검사가 바뀐 파일이 그 빌드 결과물과 같음을 확인한다.
- 렌더러 프로세스(INTENT D25): 그래픽 렌더러는 창 관리자와 다른 프로세스 하나(Windows `dsa-gfx.exe`, 작업 관리자 이름 "Android용 그래픽 렌더러", 영어 "Graphics renderer for Android")에서 돈다. 렌더러가 끝나도 창 관리자와 앱 창은 끝나지 않고 마지막 화면을 보이며, 창 관리자가 렌더러를 다시 띄워 게스트의 그래픽 연결을 다시 잇는다. 태스크 프레임은 GPU 공유 텍스처로 창 관리자에 넘어가고 CPU를 거치지 않는다.
- 수용 기준: 렌더러 프로세스를 강제로 끝내면 창 관리자와 앱 창 프로세스가 살아 있고, 창은 마지막 화면을 보이며, 렌더러가 다시 떠서 몇 초 안에 창이 다시 그려진다. 시험이 Windows, Linux, macOS 러너에서 이를 확인한다.
- 수용 기준: 실제 PC의 작업 관리자에서 "Android용 그래픽 렌더러"가 창 관리자와 따로 보이고, 앱 창을 연 채 그 프로세스를 끝내도 창이 사라지지 않는다. (수동 확인)
- 수용 기준: 렌더러 시험에서 장치 손실을 흉내 내면(가짜 장치가 `VK_ERROR_DEVICE_LOST`를 돌려줌) 호스트 프로세스가 살아 있고, 새 장치를 만들며, 게스트 쪽 호출이 장치 손실을 받는다.
- 수용 기준: 실제 PC에서 앱 창 여러 개(설정, 시계, 브라우저)를 연 채 GPU를 리셋하면(`dxcap -forcetdr` 또는 드라이버의 TDR) 몇 초 안에 모든 창이 다시 그려지고, system_server의 pid가 바뀌지 않으며, 앱의 화면 상태(스크롤 위치, 입력한 글자)가 남는다. (수동 확인)

## 5. 경계와 프로토콜 요구사항

### PR-1 전송 계층 (`Done`)
- 제어 채널은 게스트의 vsock과 호스트의 hvsocket으로 잇는다. 호스트 코드는 전송 계층을 추상화해서 Linux(유닉스 소켓)와 macOS(vsock)를 같은 인터페이스로 붙일 수 있게 한다.
- 수용 기준: 같은 프로토콜 테스트가 실제 전송 계층과 메모리 안 가짜 전송 계층에서 모두 통과한다.

### PR-2 프로토콜 단일 소스 (`Done`)
- 제어 채널의 메시지는 한 곳에 정의하고, Rust(동반 서비스), Kotlin 또는 Java(에이전트), C++(합성기의 그래픽 부분)의 타입과 코덱을 생성한다. 손으로 쓴 직렬화 코드를 두지 않는다.
- 연결할 때 프로토콜 버전과 스키마 해시를 교환한다. 다르면 연결을 거부하고 이유를 보고한다.
- 수용 기준: 정의를 바꾸고 한쪽만 다시 생성하면 연결이 거부된다.
- 수용 기준: 체크인한 프로토콜 벡터(메시지와 그 바이트열)를 세 언어의 코덱이 똑같이 인코딩하고 디코딩한다.

### PR-3 그래픽 경로 (`Agreed`)
- 게스트의 OpenGL ES 드라이버는 모든 앱에서 ANGLE이다.
- Vulkan은 원격 방식으로 호스트에서 실행한다. gfxstream을 출발점으로, 전송 계층을 PR-1에 맞춘다.
- 호스트 렌더러는 기본으로 주 모니터를 구동하는 GPU에서 렌더링한다(INTENT D20). 다른 GPU에 연결된 모니터의 태스크 창도 이 GPU가 렌더링한다. 사용자는 설정으로 `integrated`(내장 GPU), `discrete`(외장 GPU), 또는 장치 이름의 일부를 고를 수 있다. 맞는 GPU가 없으면 gfxstream의 기본 순위로 고르고, 합성기 로그에 어느 GPU에서 렌더링하는지와 그 이유를 남긴다.
- 수용 기준: Vulkan CTS의 정해진 부분 집합과 OpenGL ES 앱 하나, Vulkan 앱 하나가 태스크 창에 올바르게 그려진다.
- 수용 기준: 활성 디스플레이 목록이 주어지면, 설정이 없거나 `display`일 때 주 모니터 어댑터의 LUID를 고르고, `integrated`, `discrete`, 장치 이름은 각각 그 규칙이 되며, 주 모니터를 찾지 못하면 기본 순위로 돌아간다. 잘못된 설정은 거부되고 기본값으로 돌아간다.
- 수용 기준: 렌더러는 요청한 규칙에 맞는 Vulkan 장치를 고르고, 맞는 장치가 없으면 기본 순위로 고르며, 어느 쪽이었는지 알려 준다.
- 측정 기준: 일반 앱 스크롤, OpenGL ES 게임, Vulkan 게임 세 가지로 프레임 시간, CPU 사용률, 게스트와 호스트 메모리를 기록한다. dxg 대안 경로를 실험하면 같은 세 가지로 비교한다.

### PR-4 호스트 HAL (`Agreed`)
- 호스트로 옮기는 HAL은 게스트에 안드로이드 HAL 서비스로 두고, 장치 일은 제어 채널과 같은 프로토콜 정의(PR-2)로 만든 메시지로 vsock(Windows는 hvsocket)을 거쳐 호스트가 맡는다. 연결할 때 프로토콜 버전과 스키마 해시를 확인한다. 처음 대상은 동영상 코덱, 오디오, 전원과 배터리다.
- 수용 기준: 게스트의 H.264 동영상이 호스트 하드웨어 디코더로 재생되고, 게스트의 오디오가 호스트 기본 출력 장치로 나온다.

### PR-5 로컬 API (`Done`)
동반 서비스(권한이 필요한 쪽)와 사용자 세션의 앱 사이의 API다(INTENT D15).
- Windows는 named pipe, Linux와 macOS는 유닉스 소켓으로 잇고, 제어 채널과 같은 프레이밍과 전송 추상화를 쓴다.
- 메시지는 한 곳에 정의하고 코덱을 생성하며, 연결할 때 프로토콜 버전과 스키마 해시를 확인한다(PR-2와 같은 규칙).
- 호출자는 운영체제가 확인한 사용자로 정해진다. 메시지에 적힌 사용자 정보는 믿지 않는다.
- 수용 기준: 같은 API 테스트가 메모리 안 가짜 전송과 실제 전송(Windows의 named pipe, Linux와 macOS의 유닉스 소켓)에서 모두 통과한다.
- 수용 기준: 다른 사용자의 프로세스는 로컬 API에 연결하지 못하거나, 연결해도 그 사용자의 안드로이드만 다룬다.

### PR-6 제어 채널 상호 인증 (`Done`)
게스트 앱이 그래픽 포트용 vsock 경로를 통해 호스트 제어 채널 포트에 무단 연결해 에이전트를 사칭하지 못하도록 부팅 단위 비밀값으로 인증한다.
- 호스트는 세션을 시작할 때마다 256비트 난수 비밀값을 만들어 게스트의 `bootconfig`로 넘긴다.
- 게스트 제어 데몬은 일반 앱이 읽을 수 없는 `/proc/bootconfig`에서 비밀값을 읽고, 호스트가 보낸 난수(nonce)에 대한 HMAC-SHA256 증명으로 핸드셰이크를 마친다. 비밀값 자체는 소켓으로 보내지 않는다.
- 수용 기준: 비밀값을 모르는 프로세스나 잘못된 비밀값, 호스트가 보낸 난수와 다른 값으로 계산한 HMAC은 `HelloRejected`로 거부되고 연결이 끊긴다.
- 수용 기준: 이전 부팅 세션의 HMAC을 재전송하면 새 부팅 세션에서 거부된다.

- FR-1 제거 후 내려받은 이미지와 설치 파일이 지워지고 사용자의 안드로이드 디스크는 남는다
- FR-4 크기를 끄는 동안 창 크기와 내용이 어긋난 프레임이 없고(녹화), 손을 뗀 크기에 정확히 멈춘다, 배율 간 이동
- FR-6 한글 IME 체크리스트
- FR-10 앱 창을 연 채로 PC를 절전(가능하면 최대 절전과 모던 스탠바이도)으로 보냈다가 깨우면, 창이 그대로 그려지고 입력을 받으며, 게스트 시각(`adb shell date` 또는 시계 위젯)이 호스트 시각과 맞고, `dsa status`가 잠들기 전 상태(`Active` 또는 `Dozing`)를 보인다
- FR-11 실제 Windows에서 APK를 두 번 눌러 설치 창의 정보, 설치, 열기, 업데이트, 실패 화면을 밝은 테마와 어두운 테마에서 확인
- FR-12 실제 Windows에서 설정 앱의 위젯 페이지로 시계 위젯과 설정 화면이 있는 위젯을 하나씩 두고, 오른쪽 단추 메뉴로 크기를 바꾸고 빼며, 밝은 테마와 어두운 테마, 한국어와 영어에서 페이지를 확인
- FR-14 메이저 버전 업그레이드 뒤 앱과 데이터 유지
- FR-15 실제 Windows에서 이전 버전을 새 버전으로 올리기와 실패 시 이전 버전 유지
- FR-15 실제 Ubuntu와 Fedora 데스크톱에서 .deb와 .rpm을 열어 소프트웨어 센터로 설치하고, 저장소에 올린 다음 버전이 소프트웨어 센터의 업데이트로 오며, 제거하면 저장소 항목이 사라진다
- FR-17 실제 Windows에서 설정 앱의 기기 정보 페이지로 모델, 브랜드, 지문을 바꾸고 안드로이드를 다시 시작하면 기기 정보를 보여 주는 앱이 새 값을 보이고, 기본값으로 되돌리고 다시 시작하면 기본값을 보이며, 페이지를 밝은 테마와 어두운 테마, 한국어와 영어에서 확인
- FR-17 실제 macOS와 Linux에서 설정 앱이 그 운영체제의 설정 앱 스타일과 맞는지 라이트와 다크에서 확인하고, 운영체제마다 아이콘이 쓰는 곳에 모두 보이며 밝은 테마와 어두운 테마에서 알아볼 수 있는지 확인
- FR-18 내레이터로 앱 항목 읽기
- FR-19 이전 버전 위에 설치하면 예전 위치의 파일이 옮겨지고 안드로이드 디스크가 그대로 쓰이며, 제거하면 모든 사용자 프로필에서 안드로이드 디스크만 남는다
- FR-20 실제 Windows에서 설정 앱으로 개발자 모드를 켜고 `adb connect 127.0.0.1:58526`, `adb shell`, `adb logcat`, `adb install`이 승인 없이 동작하고, 끄면 포트가 닫힌다
- FR-21 실제 PC에서 `dsa logcat`, `dsa logs collect`, 설정 앱의 로그 보기와 진단 정보 저장, 패닉 뒤 pstore 기록 확인
- FR-22 실제 Windows에서 100%, 150%, 200% 배율의 밝은 앱과 어두운 앱 창: 투명 제목 표시줄, 앱 아이콘과 이름(선명함, 말줄임, 비활성 흐림), Calendar 창의 띠 색, 글리프 색, 닫기 단추 빨간 머무르기, 스냅 레이아웃, 끌기, 두 번 눌러 최대화, 고대비 모드
- FR-23 실제 Windows에서 설정 앱의 앱 화면으로 열기, 앱 정보, 제거, 앱 관리를 확인하고, Windows 설정의 설치된 앱에 앱이 이름, 아이콘, 버전, 게시자와 함께 나오며, 거기서 제거하면 콘솔 창 없이 DSA의 제거 창이 다시 묻지 않고 앱 정보와 진행, 결과를 보여 주고(성공하면 스스로 닫힌다) 게스트와 시작 메뉴에서 사라지고, DSA를 제거하면 항목이 모두 사라진다
- FR-24 실제 PC에서 음악 앱으로 재생을 시작하고 창을 닫으면 제목을 단 트레이 아이콘이 나타나고, 키보드 미디어 키와 Windows 미디어 플라이아웃이 재생을 제어하며, 트레이 메뉴의 중지(처음에는 확인, "다시 묻지 않음" 뒤에는 바로)와 설정 앱의 중지 단추가 앱을 멈추고, 아이콘이 사라지며 VM 메모리가 줄어든다
- FR-26 실제 PC에서 마이크 녹음, 앞뒤 카메라 미리 보기와 사진과 동영상, 지도 앱의 현재 위치, 센서 확인 앱의 가속도계와 자이로스코프와 조도, 문서 인쇄를 확인하고, Windows 개인 정보 설정에서 각각을 끄면 앱이 권한 오류를 보이며 작업 표시줄에 사용 중 표시가 나타났다 사라지는지 확인
- FR-27 실제 ARM64 Windows PC(예: Snapdragon X)에서 ARM64 설치 파일을 깨끗이 설치하고, `arm64-v8a`만 담은 APK를 설치해 창으로 열고 입력, IME, 소리, 알림, 절전 뒤 복귀가 x64와 같게 동작하며, 대기 메모리가 반환되는지 확인
- PR-3 화면이 내장 GPU에 연결된 하이브리드 노트북에서 합성기 로그가 내장 GPU를 렌더링 GPU로 적고, `discrete`로 바꾸고 합성기를 다시 시작하면 외장 GPU를 적는다
