# SPEC

이 문서는 Desktop Subsystem for Android의 요구사항과 수용 기준을 정의한다. 근거는 [INTENT.md](INTENT.md)에 있다.

- 상태 표기: `Draft`(합의 전), `Agreed`(구현 가능), `Done`(수용 기준 통과)
- 요구사항 ID는 한 번 부여하면 재사용하지 않는다. 폐기할 때는 `Withdrawn`으로 남긴다.
- 처음 판(2026-10-16)의 요구사항은 모두 `Draft`다. 소유자가 합의하면 `Agreed`가 되고, 그때부터 구현한다.
- 수치 목표는 실측 전 제안값이다. 측정 방법을 함께 적고, 실측 결과로 소유자가 확정한다.

## 1. 용어

| 용어 | 정의 |
|---|---|
| 호스트 | 사용자의 데스크톱 OS. 처음 대상은 Windows 11이다 |
| 게스트 | 전용 경량 VM에서 도는 안드로이드. Windows에서는 HCS로 만든 VM이다 |
| 동반 서비스 | 호스트에서 도는 DSA 프로세스. 세션 관리, 셸 통합, 합성기, 호스트 쪽 HAL 서비스를 맡는다 |
| 합성기 | 동반 서비스 안에서 게스트 태스크마다 호스트 창을 만들고 화면을 올리는 부분 |
| 에이전트 | 게스트의 시스템 앱. 앱 목록, 알림, Intent, 화면 상태, 입력 주입을 맡는다 |
| 제어 채널 | 동반 서비스와 에이전트 사이의 소켓 연결. 메시지는 PR-2의 프로토콜을 따른다 |
| 태스크 창 | 안드로이드 태스크 하나에 대응하는 호스트 창 |
| 세션 | 게스트 VM이 시작해서 종료할 때까지의 기간 |

## 2. 아키텍처

게스트 안드로이드는 64비트 전용(x86_64)으로 구성하며, 32비트 앱은 지원하지 않는다.

```
[안드로이드 전용 VM: 게스트]                       [Windows 호스트: 동반 서비스]
 앱 → SurfaceFlinger
   → 커스텀 hwcomposer ── 창 제어·입력 ──(vsock ↔ hvsocket)── 합성기: 태스크 창 (Win32)
   → ANGLE → Vulkan ──── Vulkan 원격 스트림 ─────────────────→ 호스트 Vulkan 실행, 결과 표시
 에이전트 ── 앱 목록·알림·Intent·IME ─────────────────────────→ 시작 메뉴·알림 센터·TSF
 HAL 클라이언트 ── RPC Binder ─────────────────────────────→ 호스트 HAL 서비스 (코덱·오디오·전원 …)
```

## 3. 기능 요구사항

### FR-1 커널 빌드 없는 설치 (`Agreed`)
사용자는 커널을 직접 빌드하지 않고 DSA를 설치할 수 있어야 한다.
- 게스트 VM의 커널은 프로젝트가 빌드해 함께 배포하고, binder(binderfs)는 그 커널에 내장한다. 사용자는 커널을 빌드하거나 교체하지 않는다.
- 사용자의 WSL 설정(`.wslconfig`)과 WSL 배포판은 건드리지 않는다.
- 설치는 Windows 설치 파일 하나로 끝난다. 필요한 Windows 기능(가상 머신 플랫폼)이 꺼져 있으면 무엇을 켜야 하는지 알려 준다.
- 수용 기준: 가상 머신 플랫폼만 켜 둔 깨끗한 Windows 11에서 설치 파일 하나를 실행해 FR-2의 세션을 시작할 수 있다. 사용자가 입력하는 명령은 없다. (수동 확인)
- 수용 기준: WSL 배포판이 있는 Windows 11에서 설치 전후로 `.wslconfig`가 같고, 배포판의 `uname -r`이 바뀌지 않는다. (수동 확인)
- 수용 기준: ashmem에 기대지 않는다. ashmem이 없는 커널에서 게스트가 부팅한다.
- 수용 기준: 프로그램을 제거하면 동반 서비스가 내려받은 이미지(FR-14)와 프로그램 설치 파일(FR-15)을 함께 지운다. 사용자의 안드로이드 디스크는 남긴다. (수동 확인)

### FR-2 세션 시작과 종료 (`Agreed`)
동반 서비스는 게스트 VM을 시작하고, 상태를 보고하고, 종료한다.
- 상태는 `Stopped`, `Starting`, `Active`, `Dozing`, `Frozen`, `Stalled`, `Stopping` 중 하나다(FR-10).
- 수용 기준: 시작 요청 뒤 안드로이드 부팅이 끝나고 에이전트가 제어 채널에 연결하면 상태가 `Active`가 된다. 그 전까지는 `Starting`이다. 제어 채널 연결만으로는 안드로이드를 쓸 수 있다는 뜻이 아니기 때문이다.
- 수용 기준: 게스트의 제어 채널 연결이 정해진 시간 안에 오지 않으면 `Stopped`로 돌아가고 원인을 보고한다.
- 수용 기준: 제어 채널은 연결됐지만 부팅 완료나 에이전트 연결이 정해진 시간 안에 오지 않으면 상태가 `Stalled`가 되고 원인을 보고한다. 게스트는 계속 실행되고, 원인이 사라지면 `Active`가 된다.
- 수용 기준: 종료 요청 뒤 게스트의 모든 프로세스가 끝나고(VM이 꺼지고) 상태가 `Stopped`가 된다.

### FR-3 태스크마다 호스트 창 (`Done`)
게스트 앱의 태스크 하나는 호스트 창 하나로 뜬다.
- 게스트는 freeform 모드로 돈다. 커스텀 hwcomposer가 태스크별 레이어 묶음을 합성기에 넘긴다.
- 합성기는 빠른 창 표시를 위해 사용자 세션에서 로그인 시점부터 백그라운드에서 실행되며, 프레임 스트림을 hvsocket으로 게스트에서 직접 받는다(INTENT D19).
- 태스크 창은 호스트의 일반 창이다. 이동, 스냅, 최소화, 최대화, 다중 모니터가 동작한다.
- 수용 기준: 앱 두 개를 실행하면 호스트 창 두 개가 뜨고, 각 창에는 자기 앱의 화면만 보인다.
- 수용 기준: 태스크 창을 닫으면 게스트 태스크도 끝나고, 게스트에서 태스크가 끝나면 태스크 창도 닫힌다.

### FR-4 창 크기 변경과 DPI (`Agreed`)
- 태스크 창 크기를 바꾸면 게스트 태스크 크기가 바뀌고, 앱이 새 크기로 다시 그린다. 새 프레임이 오기 전에는 마지막 프레임을 늘려 보여 주고, 빈 영역이나 깜빡임을 보이지 않는다.
- 태스크 창이 DPI가 다른 모니터로 가면 게스트 화면 밀도를 그 모니터에 맞춘다.
- 수용 기준: 크기를 끄는 동안 창 안에 빈 영역이 보이지 않는다. (수동 확인, 녹화로 기록)
- 수용 기준: 100%와 200% 배율 모니터 사이를 옮겨도 글자가 흐려지지 않는다. (수동 확인)

### FR-5 포인터 입력 (`Agreed`)
- 마우스, 터치, 펜 입력을 게스트 입력으로 주입한다. 좌표는 태스크 창 기준으로 변환한다.
- 마우스 휠은 스크롤로, 오른쪽 클릭은 길게 누르기가 아니라 보조 클릭으로 전달한다.
- 수용 기준: 태스크 창의 네 모서리를 누르면 게스트 앱이 받은 좌표가 화면 모서리와 2px 안에서 일치한다(모든 배율).
- 클릭 지연은 두 수로 따로 잰다. (가) 누름에서 첫 시각 반응(누름 표시나 리플이 그려진 첫 앱 프레임)이 호스트 창에 보이기까지, (나) 누름에서 다음 화면(새 액티비티의 첫 프레임)이 호스트 창에 보이기까지다. 리플은 Android가 처음 수십 ms 동안 거의 투명하게 그리므로, 하나의 수로는 반응이 늦은지와 화면 전환이 늦은지를 가를 수 없기 때문이다.
- 수용 기준: 설정 앱에서 목록 항목을 20번 클릭했을 때 (가)의 p90이 100 ms 이하이고, (나)의 p90이 300 ms 이하다. 목표는 중급 휴대폰이 내는 값에 맞춘다. 휴대폰의 터치에서 화면 반응까지는 75~168 ms(Agawi TouchMark, 2013), 터치 입력 자체는 10~35 ms(Android Developers Blog, 2021)로 측정되었고, 100 ms는 사용자가 즉시 반응으로 느끼는 한계다(Nielsen, Response Times). 화면 전환은 Material Design의 전환 시간(약 300 ms) 안에 새 화면이 나와야 한다. 측정은 `scripts/input-trace.py`의 `feedback`과 `next screen` 값으로 하고, 측정 환경(CPU, GPU, Windows 빌드, 이미지 버전)을 같이 적는다. (실제 PC에서 확인)

### FR-6 IME (`Agreed`)
- 텍스트 입력은 호스트 IME가 처리한다. 동반 서비스가 TSF로 조합을 받고, 에이전트가 앱의 `InputConnection`에 조합 중인 글자와 확정된 글자를 넣는다. 게스트의 키보드 앱은 쓰지 않는다.
- 조합 창은 게스트 앱의 커서 위치에 뜬다.
- 수용 기준: 한글 조합 체크리스트(조합, 자모 단위 백스페이스, 조합 중 커서 이동, 문장 중간 삽입, 확정 후 되돌리기)가 대표 앱 세 개(일반 `EditText`, Compose `TextField`, WebView 입력창)에서 통과한다. (수동 확인)

### FR-7 시작 메뉴와 작업 표시줄 (`Agreed`)
- 게스트에 설치된 런처 대상 앱마다 시작 메뉴 항목을 만든다. 이름과 아이콘은 게스트의 것을 쓴다.
- 앱마다 고유한 AppUserModelID를 준다. 작업 표시줄에서 앱별로 묶이고 앱의 아이콘으로 보인다.
- 앱을 지우면 시작 메뉴 항목도 지운다.
- 수용 기준: 앱 하나를 설치하면 시작 메뉴에 나타나고, 실행하면 작업 표시줄에 그 앱 아이콘으로 따로 묶이며, 지우면 시작 메뉴에서 사라진다.
- 수용 기준: Windows 검색에 앱 이름을 입력하면 그 앱이 나오고, 누르면 안드로이드가 꺼져 있어도 켜진 뒤 그 앱이 태스크 창으로 뜬다.

### FR-8 알림 (`Agreed`)
- 게스트 알림을 호스트 알림 센터로 보낸다. 제목, 본문, 앱 이름, 아이콘을 싣는다.
- 알림을 누르면 그 알림의 `PendingIntent`를 게스트에서 실행하고, 결과 태스크가 태스크 창으로 뜬다.
- 게스트에서 알림이 지워지면 호스트에서도 지운다.
- 수용 기준: 태스크 창이 하나도 없는 `Dozing` 상태에서 우선순위가 높은 알림이 도착하면 호스트 알림으로 뜨고, 누르면 앱이 열린다.

### FR-9 링크와 파일 연결 (`Agreed`)
- 게스트 앱이 `http`/`https` 링크를 열면 호스트 기본 브라우저로 연다. 사용자가 원하면 게스트 앱으로 열 수도 있다.
- 호스트에서 파일을 게스트 앱으로 열 수 있다(공유와 열기).
- 수용 기준: 게스트 앱에서 웹 링크를 누르면 호스트 기본 브라우저에 그 주소가 열린다.

### FR-10 수명 주기 단계 (`Agreed`)
INTENT D7의 네 단계를 구현한다.
- 안드로이드 태스크 창이 모두 닫히거나 최소화되면 에이전트가 게스트에 화면 꺼짐을 알리고 Doze로 들어가게 한다. 창이 하나라도 다시 보이면 화면 켜짐으로 돌아간다.
- 호스트의 배터리 상태와 절전 상태를 게스트 배터리 상태에 반영한다.
- freeze는 사용자가 고른 경우나 설정한 시간 동안 쓰지 않은 경우에만 들어간다. 기본값은 freeze를 쓰지 않는 것이다.
- 수용 기준: 창을 모두 닫고 정해진 시간이 지나면 상태가 `Dozing`이 되고, 게스트의 `deviceidle` 상태가 idle이다.
- 수용 기준: `Dozing`에서 창을 열면 1초 안에 상태가 `Active`가 된다.
- 절전 상태는 배터리 절약 모드와 호스트의 절전·최대 절전(모던 스탠바이 포함)을 함께 뜻한다. 호스트가 잠들기 직전에 게스트에 알리면, 게스트는 화면을 끄고 Doze로 들어가며 디스크에 쓸 내용을 모두 내려쓴 뒤 준비됐다고 답한다. 호스트는 그 답을 잠깐(최대 2초)만 기다린다. 호스트가 깨어나면 게스트에 호스트의 현재 시각을 보내 게스트 시계를 맞추고, 잠들기 전 화면 상태로 되돌린다. 잠든 동안의 시간은 freeze와 부팅 시한에 세지 않는다. 깨어날 때 게스트가 얼어 있거나 연결이 끊겨 있으면 시각은 녹은 뒤나 다시 연결된 뒤에 보낸다.
- 수용 기준: `Active` 상태에서 호스트가 잠들면 게스트가 화면 꺼짐과 잠듦 알림을 받고, 게스트가 디스크를 내려쓴 답을 보내면 호스트의 대기가 끝난다. 답이 없어도 대기는 2초 안에 끝난다.
- 수용 기준: 호스트가 깨어나면 게스트가 호스트 시각(1초 이내 오차)을 받고, 잠들기 전 `Active`였으면 1초 안에 다시 `Active`, `Dozing`이었으면 `Dozing`으로 남는다. 제어 채널은 그대로 쓰이거나 다시 연결된다.

### FR-11 APK 설치 (`Agreed`)
- 호스트에서 APK 파일을 열거나 동반 앱으로 끌어다 놓으면 게스트에 설치한다. 설치 결과와 실패 이유를 보여 준다.
- 수용 기준: 서명이 올바른 APK를 열면 설치되고 FR-7에 따라 시작 메뉴에 나타난다.
- 탐색기에서 APK 파일을 열거나 동반 앱에 끌어다 놓으면 APK 설치 창이 열린다. 이 창은 설치 프로그램(setup UI)과 같은 모양을 따른다. 밝은 테마와 어두운 테마, 배치, 글꼴, 단추, 진행 화면과 완료·실패 화면이 같다.
- 창은 안드로이드를 시작하기 전에 호스트에서 APK 파일을 읽어 정보를 채운다. 앱 이름과 아이콘, 패키지 이름, 버전 이름과 버전 코드, 파일 크기, 최소·대상 안드로이드 버전, 요청하는 권한(사람이 읽을 수 있는 이름), 서명 인증서 지문을 보여 준다.
- 같은 패키지가 이미 설치돼 있으면 새 설치인지, 업데이트인지(설치된 버전과 새 버전을 함께 보여 준다), 버전 내림이나 서명 불일치인지 알린다. 서명이 다르면 안드로이드처럼 설치를 막고 이유를 설명한다. 버전 내림도 막는다.
- 단추는 설치(업데이트면 업데이트)와 취소다. 설치가 끝나면 열기(앱의 태스크 창을 연다)와 닫기를 보여 준다. 실패하면 이유를 쉬운 말로 보여 준다.
- 안드로이드가 돌고 있지 않으면 설치 과정에서 시작하고, 그 단계를 창에 보여 준다.
- 수용 기준: 서명이 올바른 APK를 두 번 누르면 설치 창이 열리고, 파일에서 읽은 앱 이름, 아이콘, 버전, 권한을 보여 준다.
- 수용 기준: 설치를 누르면 진행 화면을 거쳐 열기 단추가 있는 완료 화면으로 끝난다.
- 수용 기준: 이미 설치된 앱의 새 버전이면 설치된 버전과 새 버전을 모두 보여 주고 단추가 업데이트다. 서명이 다르거나 버전이 낮으면 설치를 막고 이유를 보여 준다.
- 수용 기준: 설치가 실패하면 실패 화면이 그 이유를 쉬운 말로 보여 준다.

### FR-12 바탕화면 위젯 (`Agreed`)
- 에이전트가 `AppWidgetHost`가 되어 사용자가 고른 위젯을 그린다. 위젯 하나는 테두리 없는 호스트 창 하나로, 바탕화면 층에 붙는다.
- 위젯 창 크기를 바꾸면 위젯에 새 크기를 알리고, 위젯이 크기별 레이아웃을 가지면 그에 맞춰 다시 그린다.
- 위젯을 누르면 그 `PendingIntent`를 실행한다.
- 사용자는 DSA 설정 앱에서 위젯을 골라 바탕화면에 두고, 둔 위젯을 뺀다. 명령줄(`dsa widgets`)만으로 위젯을 다루게 두지 않는다.
- 수용 기준: 시계 위젯 하나를 바탕화면에 두면 `Dozing` 상태에서도 시각이 갱신된다.
- 수용 기준: 설정 앱의 위젯 페이지는 설치된 안드로이드 앱이 제공하는 위젯을 모두 보여 준다. 항목마다 앱 이름, 위젯 이름, 미리 보기 이미지(없으면 앱 아이콘), 기본 크기를 보인다.
- 수용 기준: 위젯을 고르면 바탕화면에 놓인다. 앱이 설정 화면(configure 액티비티)을 가지면 그 화면을 먼저 띄우고, 사용자가 마친 뒤 놓는다.
- 수용 기준: 위젯 페이지는 놓인 위젯을 보여 주고, 거기서 뺄 수 있다.
- 수용 기준: 놓인 위젯 창을 오른쪽 단추로 누르면 제거와 크기 조정 메뉴가 나온다.
- 수용 기준: 위젯을 두거나 빼면 설정 앱과 바탕화면에 다시 시작하지 않고 반영된다.

### FR-13 클립보드 (`Agreed`)
- 호스트와 게스트의 텍스트 클립보드를 양방향으로 맞춘다. 이미지는 계획 단계다.
- 클립보드 공유는 설정에서 끌 수 있다. 기본값은 켬이다.
- 수용 기준: 호스트에서 복사한 텍스트를 게스트 앱에 붙여 넣을 수 있고, 반대도 된다.

### FR-14 안드로이드 버전 지원과 자동 업데이트 (`Agreed`)
안드로이드 최신 메이저 버전과 그 바로 전 버전, 두 개를 지원하고, 이미지를 자동으로 업데이트한다(INTENT D14).
- 같은 메이저 버전의 보안 업데이트와, 다음 메이저 버전으로의 업그레이드를 동반 서비스가 받아 적용한다. 적용 전후를 사용자에게 알린다.
- 지원이 끝나는 버전을 쓰는 사용자는 다음 지원 버전으로 올린다. 메이저 버전을 내리는 업데이트는 없다(안드로이드가 데이터의 버전 내림을 지원하지 않는다).
- 이미지는 프로젝트 키로 서명하고, 서명을 확인한 뒤에만 적용한다.
- 수용 기준: 서명이 없거나 맞지 않는 이미지, 지원 목록에 없는 버전, 메이저 버전을 내리는 이미지는 적용하지 않고 이유를 보고한다.
- 수용 기준: 새 이미지가 정해진 시간 안에 부팅을 마치지 못하면 이전 이미지로 되돌리고 세션을 다시 시작한다.
- 수용 기준: 직전 메이저 버전에서 최신 버전으로 업그레이드한 뒤 설치한 앱과 그 데이터가 남아 있다. (수동 확인)

### FR-15 프로그램 자동 업데이트 (`Agreed`)
동반 서비스가 서명된 프로그램 목록을 확인해 새 버전의 설치 파일을 받아 적용한다(INTENT D18).
- 목록은 프로젝트 키로 서명하고, 설치 파일은 목록에 적힌 크기와 SHA-256이 맞을 때만 실행한다.
- 어떤 사용자의 안드로이드도 돌고 있지 않을 때 적용한다. 돌고 있으면 미루고, 사용자가 `dsa update`로 바로 적용할 수 있다. 적용 전후를 사용자에게 알린다.
- 버전을 내리는 업데이트는 없다. 설정으로 업데이트를 끌 수 있다.
- 수용 기준: 서명이 없거나 맞지 않는 목록, 크기나 해시가 맞지 않는 설치 파일, 지금과 같거나 낮은 버전은 적용하지 않고 이유를 보고한다.
- 수용 기준: 안드로이드가 돌고 있는 사용자가 있으면 적용을 미루고, 모두 멈추면 적용한다. `dsa update`는 기다리지 않고 적용한다.
- 수용 기준: 업데이트를 끈 설정에서는 목록을 확인하지 않는다.
- 수용 기준: 실제 Windows에서 이전 버전을 설치해 두면 서비스가 새 버전으로 올리고 다시 시작한다. 설치가 실패하면 이전 버전이 남고 이유를 보고한다. (수동 확인)

### FR-16 키 입력 (`Agreed`)
- 포커스를 가진 태스크 창에서 누른 물리 키를 게스트 키 이벤트로 주입한다. 누름, 뗌, 자동 반복을 구분하고 수정 키(Ctrl, Shift, Alt, Meta) 상태를 함께 싣는다.
- 글자 입력은 FR-6(IME)이 맡는다. 이 항목은 방향키, Enter, Backspace, Delete, Tab, Esc, 기능 키와 단축키처럼 조합하지 않는 키를 다룬다.
- 창이 포커스를 잃으면 눌린 채로 남은 키를 모두 뗀 것으로 보낸다.
- 수용 기준: 텍스트 입력란에서 방향키, Enter, Backspace, Delete, Ctrl+A/C/V가 동작한다.
- 수용 기준: 키를 누른 채 다른 창으로 포커스를 옮기면 게스트에서 그 키가 눌린 채로 남지 않는다.

### FR-17 설정 앱 (`Agreed`)
- DSA의 설정과 상태를 한 곳에서 보고 바꾸는 Windows 앱을 둔다. 디자인은 WinUI 3(Fluent) 지침을 따른다: NavigationView, 설정 카드, Mica 배경, 라이트와 다크 테마, 시스템 강조색.
- 다루는 것: 안드로이드 시작과 종료, 상태(`Stopped`, `Active`, `Dozing` 등)와 마지막 오류, 메모리 사용 내역(호스트의 VM과 동반 프로세스, 게스트의 커널, 캐시, 시스템, 앱별), 렌더링 GPU 선택(D20), 프로그램과 안드로이드 이미지 업데이트 설정, freeze 사용 여부(기본 끔), 버전 정보와 로그 폴더 열기.
- 설정은 동반 서비스의 로컬 API로 읽고 쓴다. 앱은 설정을 직접 파일에 쓰지 않는다.
- 영어와 한국어를 지원하고, 시스템 언어를 따른다.
- 수용 기준: 설정 앱에서 렌더링 GPU를 바꾸면 다음 시작부터 그 GPU에서 렌더링하고, 메모리 화면이 VM과 게스트 내역을 보여 준다. (수동 확인)

#### 기기 정체성
이미지는 Cuttlefish의 이름(제조사 Google, 모델 `Cuttlefish x86_64 phone 64-bit only`, 기기 `vsoc_x86_64_only`)을 그대로 두지 않고 DSA의 이름을 쓴다. 앱과 사용자가 보는 기기 이름이 실제로 쓰는 제품과 맞아야 하기 때문이다. 사용자는 그 값을 설정에서 바꿀 수 있다. 옛 기기 이름을 확인하는 앱과 호환하기 위해서다.
- 기본값: 제조사 `thisisthepy`, 브랜드 `DSA`, 모델 `Desktop Subsystem for Android`, 기기와 제품 이름 `dsa_x86_64`, `ro.build.characteristics`는 `tablet`이다. 지문은 `DSA/dsa_x86_64/dsa_x86_64:<릴리스>/<빌드 ID>/<증분>:user/release-keys`다. 이미지는 user 빌드이므로 지문의 빌드 유형도 `user`다. 증분에는 이미지마다 붙이는 내용 태그가 그대로 남는다.
- `tablet`은 AOSP의 태블릿 구성이 쓰는 값이다. 앱의 화면 배치는 이 값이 아니라 창 크기(가장 짧은 너비)로 정해지므로, 큰 화면 배치를 고르게 하면서 휴대전화 전용 앱을 막지 않는다. `phone` 같은 다른 값도 고를 수 있다.
- 이 값은 모든 파티션(system, system_ext, vendor, product, odm, vendor_dlkm과 이미지에 있는 나머지)의 `ro.product.<파티션>.{brand,manufacturer,model,device,name}`, 그것에서 나오는 `ro.product.{brand,manufacturer,model,device,name}`, 파티션마다의 지문, `ro.build.fingerprint`, `ro.build.product`, `ro.build.flavor`, `ro.build.description`에 똑같이 들어간다. `ro.build.display.id`는 user 빌드처럼 빌드 ID만 담는다. 앱이 읽는 `Build.MANUFACTURER`, `Build.BRAND`, `Build.MODEL`, `Build.DEVICE`, `Build.PRODUCT`, `Build.FINGERPRINT`가 이 값이다. 이미지 검사(`check-image.py`)가 이것을 확인한다.
- 설정 앱의 "기기 정보" 페이지와 `dsa settings set device.<항목> <값>`으로 바꾸는 항목: 제조사(`manufacturer`), 브랜드(`brand`), 모델(`model`), 기기(`device`), 제품 이름(`name`), 형태(`characteristics`), 지문. 지문은 구성 요소(`fingerprint.release`, `fingerprint.id`, `fingerprint.incremental`, `fingerprint.type`, `fingerprint.tags`)를 하나씩 바꾸거나, 지문 문자열 전체(`fingerprint`)를 적는다. 전체 문자열을 적으면 그것이 구성 요소보다 앞선다. 적지 않은 구성 요소는 이미지의 값을 쓰고, 브랜드, 제품 이름, 기기는 위의 항목을 따른다.
- "기본값으로 되돌리기" 단추와 `dsa settings reset device`가 모든 항목을, `dsa settings reset device.<항목>`이 한 항목을 기본값으로 되돌린다.
- 값은 사용자별이고, 동반 서비스가 `settings\users\<SID>.device.json`에 둔다(FR-19). 설정 앱은 이 파일을 직접 쓰지 않는다.
- 바꾼 값은 다음 안드로이드 시작부터 적용된다. `ro.*` 속성은 부팅 중 한 번 정해지면 바꿀 수 없기 때문이다. 페이지는 이것을 알리고, 안드로이드가 실행 중이면 "지금 안드로이드 다시 시작" 단추를 보여 준다.
- 전달 방법: 기본값과 다른 값이 있으면 호스트가 부팅마다 만드는 initrd 복사본에 속성 파일 하나(`/system/etc/ramdisk/build.prop`)를 덧붙인다. 첫 단계 init이 그 파일을 둘째 단계로 넘기고, 이미지의 product `build.prop`이 맨 끝에서 그 파일의 정체성 속성만 가져온다. 속성 서비스가 `ro.*`를 잠그기 전에 init 자신이 읽으므로 SELinux 정책을 넓히지 않는다. 모두 기본값이면 파일을 덧붙이지 않고, 이미지의 값이 그대로 쓰인다.
- 입력을 검사한다. 제조사와 모델은 1~64자의 인쇄 가능한 ASCII이고 앞뒤 공백이 없다. 브랜드, 기기, 제품 이름은 1~32자의 영문자, 숫자, `.`, `_`, `-`이고 영문자나 숫자로 시작한다. 형태는 쉼표로 나눈 소문자, 숫자, `_`의 낱말이고 64자 이하다. 지문은 `브랜드/제품/기기:릴리스/ID/증분:유형/태그` 꼴이고 256자 이하이며, 유형은 `user`, `userdebug`, `eng` 중 하나다. 틀린 값은 아무것도 바꾸지 않고 이유와 함께 거부한다.
- 페이지는 지문이나 모델을 바꾸면 앱 호환성(기기를 확인하는 앱, 결제와 무결성 검사)에 영향을 줄 수 있다고 경고한다. 정체성을 바꾸면 패키지 관리자가 다음 부팅을 업데이트로 보고 앱을 한 번 다시 검사한다.
- 수용 기준: 이미지 검사가 모든 `build.prop`에서 위의 기본값을 확인하고, 정체성 속성에 Cuttlefish의 이름(`Cuttlefish`, `vsoc_`, `aosp_cf_`)이나 지문의 `userdebug`가 남아 있으면 실패한다.
- 수용 기준: 기본값과 다른 정체성이 있으면 부팅용 initrd 끝(bootconfig 앞)에 그 값을 담은 속성 파일이 붙고, 모두 기본값이면 붙지 않는다. 지문 구성 요소와 전체 문자열이 위의 규칙대로 합쳐진다.
- 수용 기준: 틀린 값(허용하지 않는 문자, 길이 초과, 형식이 틀린 지문)은 거부되고 저장된 값이 바뀌지 않는다.
- 수용 기준: 설정 앱이나 CLI로 값을 바꾸고 안드로이드를 다시 시작하면, 앱이 읽는 `Build.MANUFACTURER`, `Build.BRAND`, `Build.MODEL`, `Build.DEVICE`, `Build.PRODUCT`, `Build.FINGERPRINT`와 `ro.build.characteristics`가 설정과 같고, 기본값으로 되돌리고 다시 시작하면 기본값으로 돌아온다. (수동 확인)

### FR-18 접근성 (`Agreed`)
태스크 창 안의 안드로이드 UI를 호스트의 접근성 트리로 내보낸다. 지금은 앱 내용이 호스트에게 그림 한 장이어서, 스크린 리더가 읽지 못하고 UI 자동화 도구도 항목을 찾지 못하기 때문이다.
- 에이전트가 게스트의 접근성 노드(역할, 이름, 값, 상태, 위치, 가능한 동작)를 읽어 제어 채널로 보낸다. 호스트는 이것을 태스크 창의 UI Automation 트리로 내보낸다.
- 트리는 그 창의 태스크에 속한 노드만 담는다. 호스트의 접근성 도구가 트리를 요청하지 않는 동안에는 게스트가 노드를 보내지 않는다. 쓰지 않는 사용자가 메모리와 CPU를 치르지 않게 하기 위해서다.
- 호스트 쪽의 호출(Invoke, 값 설정, 스크롤, 포커스)은 해당 노드의 접근성 동작으로 게스트에 전달한다.
- 이 경로는 터치 입력과 화면 표시를 거치지 않는다. 따라서 입력 지연과 그리기 품질(FR-4, FR-5)을 재는 수단이 되지 못하고, 그 측정을 대신하지 않는다.
- 수용 기준: UI Automation 클라이언트로 설정 앱 창의 트리를 읽으면 목록 항목의 역할, 이름, 화면 위치가 앱이 보여 주는 것과 맞다.
- 수용 기준: 그 클라이언트로 목록 항목에 Invoke를 호출하면 커서를 움직이지 않고 해당 화면이 열리고, 트리도 새 화면으로 바뀐다.
- 수용 기준: 창 내용이나 크기가 바뀌면 호스트가 UI Automation 변경 이벤트를 내고, 트리가 1초 안에 새 상태를 보여 준다.
- 수용 기준: 접근성 클라이언트가 없는 동안 게스트의 접근성 서비스가 노드를 읽지 않는다.
- 수용 기준: 내레이터로 설정 앱의 목록 항목을 차례로 옮겨 가면 각 항목을 읽어 준다. (수동 확인)

### FR-19 저장 위치 (`Agreed`)
DSA가 실행 중에 만드는 파일은 정해진 두 루트 아래 정해진 자리에만 둔다. 기능마다 경로를 따로 정하면 파일이 흩어지고, 제거할 때 무엇을 지울지 알 수 없기 때문이다.
- 루트는 둘뿐이다. 기계 전체의 루트는 `%ProgramData%\DSA`(설치할 때 데이터 폴더를 다른 곳으로 고르면 그 폴더)이고, 사용자별 루트는 그 사용자의 `%LOCALAPPDATA%\DSA`다.
- 경로는 Windows 호스트의 경로 모듈 하나가 만들고, 동반 서비스, 창 관리자, 앱 창, CLI가 모두 그것을 쓴다. 설정 앱(C#)과 설치 프로그램(WiX)은 아래 표를 그대로 따른다. `dsa/host/core`는 경로를 만들지 않고 주입받는다.

기계 루트(`%ProgramData%\DSA`): SYSTEM과 Administrators만 쓸 수 있다.

| 자리 | 담는 것 | 이유 |
|---|---|---|
| `dsa-hostd.json` | 동반 서비스 구성 | 설치 프로그램이 쓰고 서비스가 읽는다 |
| `images\` | 안드로이드 이미지 저장소 | 모든 사용자의 VM이 같은 이미지로 부팅한다 |
| `updates\` | 내려받은 프로그램 설치 파일과 업데이트 상태 | 서비스가 SYSTEM으로 실행하므로 사용자가 바꿀 수 없어야 한다 |
| `settings\` | `machine.json`, `users\<SID>.json`, `users\<SID>.device.json`(기기 정체성), 위젯 배치 | 사용자가 설정 앱에서 바꾸는 값. 서비스만 쓴다 |
| `logs\` | `dsa-hostd.log`, `android-<SID>.log`(게스트 콘솔) | 서비스와 안드로이드의 로그 |
| `tmp\` | VM 부팅마다 만드는 initrd 같은 피할 수 없는 임시 파일 | 아래 임시 파일 규칙 |

사용자 루트(`%LOCALAPPDATA%\DSA`): 그 사용자, SYSTEM, Administrators만 읽고 쓴다.

| 자리 | 담는 것 | 이유 |
|---|---|---|
| `android.vhdx` | 그 사용자의 안드로이드 디스크 | 사용자의 데이터다. 제거해도 남는다 |
| `android.image-version` | 그 디스크가 담은 이미지의 버전 | 디스크를 어느 이미지에서 올릴지 판단한다. 디스크와 함께 남는다 |
| `pstore.vhd` | 게스트 커널이 마지막 로그(커널 메시지와 pmsg)를 남기는 고정 크기 디스크(4 MiB) | VM은 패닉이나 재설정 때 끝나므로 메모리에 둔 기록은 남지 않는다. 크기가 정해져 있어 커지지 않고, 사용자 데이터가 아니므로 제거하면 지운다 |
| `apps\<package>\` | 앱마다 만든 창 프로그램과 그 기록 | 앱 이름과 아이콘을 단 실행 파일 |
| `notifications\` | 알림에 쓰는 앱 아이콘 | Windows 알림이 파일 경로로 아이콘을 읽는다 |
| `logs\` | `dsa-wm.log`, `dsa-app-window.log` | 사용자 세션에서 도는 프로세스의 로그 |
| `compositor.json` | 설정 앱 이전에 고른 렌더링 GPU | 이전 선택을 이어받기 위해 읽기만 한다 |
| `monitors.txt` | 모니터 배치 기록 | 창 관리자의 사용자별 상태 |
| `start-menu.json` | 창 관리자가 만든 시작 메뉴 바로 가기의 목록 | 자기가 만든 것만 고치고 지우기 위해서다 |
| `tmp\` | 사용자 프로세스의 피할 수 없는 임시 파일 | 아래 임시 파일 규칙 |

- DSA 폴더 밖에는 다음만 둔다: 시작 메뉴 바로 가기(설정 앱, 그리고 앱마다 창 관리자가 만든 것), 설치 프로그램의 레지스트리 키(`HKLM\SOFTWARE\thisisthepy\DSA`), 로그인 때 창 관리자를 시작하는 `Run` 값, `.apk` 연결과 파일 상황에 맞는 메뉴 항목, Hyper-V 소켓 서비스 등록(`GuestCommunicationServices`), 알림을 누르면 실행되는 URL 프로토콜 키(`HKCU\Software\Classes\io.github.thisisthepy.dsa-notification`), 알림에 쓰는 앱별 AppUserModelId 키(`HKCU\Software\Classes\AppUserModelId\Thisisthepy.DSA.<package>`), Windows 설치된 앱 목록에 안드로이드 앱을 올리는 앱별 제거 키(`HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\Thisisthepy.DSA.<package>`). 이 밖에는 아무것도 두지 않는다.
- 이름은 Microsoft와 IETF의 관례를 따른다. URL 프로토콜 이름은 다른 프로그램과 겹치지 않도록 프로젝트가 가진 도메인(`thisisthepy.github.io`)을 뒤집어 앞에 붙인다(RFC 7595 3.8절). 패키지 앱의 프로토콜 이름 규칙(소문자, 39자 이하)에도 맞는다. AppUserModelID는 `CompanyName.ProductName.SubProduct` 꼴(`Thisisthepy.DSA.<package>`)이고 128자를 넘지 않는다. 예전 이름(`dsa-notification`, `DSA.<package>`)의 키는 업그레이드 뒤 창 관리자가 처음 시작할 때와 제거할 때 지운다.
- 제거하면 알림 프로토콜 키, AppUserModelId 키, 앱별 제거 키는 지우고, `android.image-version`은 안드로이드 디스크와 함께 남긴다.
- 임시 파일은 되도록 만들지 않고 데이터를 메모리나 파이프로 넘긴다. 피할 수 없으면 해당 루트의 `tmp\` 안에만, 프로세스마다 겹치지 않는 이름으로 만들고, 쓴 쪽이 다 쓰면 지운다. 서비스는 시작할 때 이전 실행이 남긴 것을 지운다. 기계 루트의 `tmp\`는 SYSTEM과 Administrators만 쓸 수 있다. 제품 코드는 시스템이나 사용자의 `%TEMP%`, `std::env::temp_dir()`, `Path.GetTempPath()`를 쓰지 않는다(테스트는 예외).
- 로그는 둘로 나눈다. SYSTEM으로 도는 서비스와 안드로이드(게스트 콘솔)의 로그는 기계 루트의 `logs\`에, 사용자 세션에서 도는 창 관리자와 앱 창의 로그는 사용자 루트의 `logs\`에 둔다. 설정 앱은 두 폴더를 모두 보여 주고 열 수 있다.
- 추적 스위치(`input-trace`, `resize-trace`)는 설정 값이다. 빈 표시 파일로 켜지 않는다. 업그레이드할 때 예전 표시 파일이 있으면 그 값을 설정으로 옮기고 파일을 지운다.
- 수용 기준: `dsa/host`의 제품 코드가 경로 모듈 밖에서 `LOCALAPPDATA`, `ProgramData`, 임시 폴더로 경로를 만들면 실패하는 테스트가 있고, 통과한다.
- 수용 기준: 제거하면 안드로이드 디스크(`android.vhdx`와 `android.image-version`)를 뺀 DSA의 파일, 폴더, 레지스트리 키, 바로 가기가 모든 사용자 프로필에서 사라진다. (수동 확인)
- 수용 기준: 예전 위치에 파일이 있는 PC에 설치하면 파일이 새 위치로 옮겨지고, 사용자의 안드로이드 디스크를 그대로 쓴다. 옮기기 전에 확인하고, 안드로이드 디스크는 지우거나 덮어쓰지 않으며, 옮기지 못하면 예전 위치에 두고 로그에 남긴다.

### FR-20 개발자 모드와 adb (`Agreed`)
개발자가 게스트를 adb로 살펴볼 수 있게 한다. WSA처럼 adb는 릴리스 이미지에 들어 있고, 사용자가 설정에서 개발자 모드를 켤 때만 열린다. 게스트에는 SystemUI가 없어 기기 화면에서 adb 연결을 승인할 수 없으므로 승인을 요구하지 않는다. 제어 메시지는 adb로 보내지 않는다(INTENT D3). adb는 개발에만 쓴다.
- 이미지는 user 빌드 그대로다(`ro.debuggable=0`). adbd는 `ro.adb.secure=0`으로 기기 승인 없이 연결을 받고, TCP 대신 vsock으로만 듣는다.
- 개발자 모드는 사용자별 설정이고 기본값은 끔이다. 설정 앱의 고급 항목과 `dsa settings set developer-mode on|off`로 바꾼다. 바꾸면 이미지를 다시 설치하거나 안드로이드를 다시 시작하지 않고 바로 적용된다.
- 켜져 있으면 호스트가 `127.0.0.1`에만 묶인 포트(기본 58526, 설정으로 바꿀 수 있다)를 열고, 그 연결을 hvsocket으로 게스트의 adbd에 잇는다. 제어 채널로 게스트에 adbd를 켜라고 알린다. 설정 앱은 쓸 주소(`adb connect 127.0.0.1:58526`)를 보여 준다.
- 꺼져 있으면 호스트는 그 포트를 듣지 않고, 게스트의 adbd는 멈춰 있다.
- 수용 기준: 새로 설치한 상태에서 개발자 모드는 꺼져 있고, 호스트의 adb 포트에 연결할 수 없으며 게스트의 adbd가 돌지 않는다.
- 수용 기준: 개발자 모드를 켜면 `adb connect 127.0.0.1:<포트>` 뒤 `adb shell`이 아무 승인 없이 셸을 연다.
- 수용 기준: 개발자 모드를 끄면 호스트 포트가 닫히고 게스트의 adbd가 멈춘다.
- 수용 기준: 호스트 포트는 루프백(`127.0.0.1`)에만 묶이고, 다른 주소로는 연결되지 않는다.
- 수용 기준: 실제 Windows에서 설정 앱으로 개발자 모드를 켜고 `adb connect`, `adb shell`, `adb logcat`, `adb install`이 동작하며, 끄면 연결이 끊긴다. (수동 확인)

### FR-21 게스트 로그 스트림과 진단 수집 (`Agreed`)
안드로이드의 로그는 파일로 쌓지 않고, 읽는 쪽이 있을 때만 흘려 보낸다. 지금처럼 logcat을 직렬 콘솔로 보내면 한 부팅 안에서도 로그 파일이 계속 커지고(8 MB까지 보았다), 직렬 포트의 바이트마다 VM 밖으로 트랩이 나가기 때문이다.
- 원본은 logd의 메모리 안 링 버퍼다. 게스트는 로그를 파일로 쓰지 않는다.
- 호스트는 읽는 쪽이 붙어 있을 때만 게스트 로그를 구독한다. 읽는 쪽은 CLI `dsa logcat`(버퍼, 우선순위, 태그 필터와 `-d` 덤프)과 설정 앱의 실시간 보기 화면(필터와 일시 정지)이다.
- 로그 레코드는 전용 hvsocket 포트로 보낸다. 로그가 많아도 입력과 창 메시지가 늦어지지 않게 하기 위해서다. 구독, 구독 해제, 필터, 수집 요청은 제어 채널로 보낸다. 메시지와 레코드 형식은 프로토콜 정의에서 생성한다.
- 게스트 쪽 다리는 구독 중에만 logd에 붙는다. 보낼 큐는 크기가 정해져 있고, 넘치면 버린 레코드 수를 알리는 레코드를 대신 보낸다.
- 호스트는 최근 기록을 위해 작은 메모리 안 링(약 1 MB)만 두고, 로그 파일을 쓰지 않는다. 형식이 틀린 레코드는 로그 스트림만 끊고, 동반 서비스는 계속 돈다.
- 읽는 쪽이 없으면 로그 경로의 비용은 거의 0이다: 게스트 다리는 logd를 읽지 않고, 전용 포트로 아무것도 보내지 않는다.
- 진단 수집은 요청할 때만 한다. `dsa logs collect -o <zip>`과 설정 앱의 "진단 정보 저장" 단추가 게스트 로그 링 전체, tombstone, ANR 트레이스, dropbox, pstore, dumpsys 요약, 그리고 호스트 로그를 하나의 zip으로 모은다. 게스트는 아카이브를 스트림으로 보내고 게스트 디스크에 임시 파일을 남기지 않는다.
- 커널은 디스크에 쓰는 pstore(pstore/blk)를 켠다. 게스트가 죽어도 마지막 커널 로그와 안드로이드의 마지막 로그(pmsg)가 다음 부팅에 남게 하기 위해서다. VM은 패닉이나 재설정 때 끝나므로 메모리(ramoops)에 둔 기록은 남지 않는다. 기록은 사용자별 고정 크기 디스크(`pstore.vhd`, FR-19)에 두고, 디스크가 정해진 크기를 넘지 않는다. 디스크와 영역 크기를 고른 이유, 패닉 순간에 무엇이 남고 무엇이 남지 않는지는 커널 구성 문서에 적는다.
- 진단 수집이 pstore 기록을 호스트로 보내고 나면 게스트는 그 기록을 지운다. 같은 기록이 다음 수집에 다시 들어가지 않고, 새 기록이 들어갈 자리가 남게 하기 위해서다.
- 직렬 콘솔은 커널의 초기 부팅과 패닉 출력만 나른다. 콘솔 로그 파일은 한 부팅 안에서도 크기 상한을 둔다.
- 로컬 API의 로그 엔드포인트는 호출한 사용자의 안드로이드 로그만 준다.
- 수용 기준: 구독하지 않은 상태에서 게스트 다리는 logd에 연결하지 않고 로그 포트로 아무 바이트도 보내지 않는다. 구독하면 필터에 맞는 레코드만 오고, 구독을 해제하면 다시 멈춘다.
- 수용 기준: 보낼 큐가 넘치면 레코드를 버리고, 버린 수를 담은 레코드가 순서대로 온다.
- 수용 기준: 호스트 링은 정한 크기를 넘지 않고 가장 오래된 레코드부터 버린다. 형식이 틀린 레코드는 로그 스트림만 닫고 제어 채널과 서비스는 계속 동작한다.
- 수용 기준: 버퍼, 우선순위, 태그 필터와 `-d` 덤프가 정한 대로 레코드를 고른다. 보기 화면의 필터와 일시 정지가 정한 대로 동작한다.
- 수용 기준: 게스트 이미지에 logcat을 직렬 콘솔로 보내는 서비스가 없고, 콘솔 로그 파일이 한 부팅 안에서 상한을 넘지 않는다.
- 수용 기준: 실제 PC에서 `dsa logcat`이 실시간 로그를 보여 주고, `dsa logs collect -o diag.zip`과 설정 앱의 단추가 위의 항목을 담은 zip을 만들며, 게스트를 패닉시킨 뒤 다음 부팅의 수집에 pstore 기록이 들어 있다. (수동 확인)

### FR-22 통합 제목 표시줄 (`Agreed`)
태스크 창의 제목 표시줄은 투명하고, 앱 화면이 그 아래까지 이어진다. 요즘 Windows 앱처럼 앱의 색이 창 맨 위까지 닿게 하고, 앱 위에 따로 놓인 회색 띠를 없애기 위해서다.
- 호스트는 태스크 창의 비클라이언트 영역을 클라이언트 영역으로 넓히고(DWM 프레임 확장), 캡션 단추(최소화, 최대화, 닫기)를 직접 그린다. 크기 조절 테두리, 끌어 옮기기, 두 번 눌러 최대화, 시스템 메뉴(Alt+Space, 오른쪽 클릭), Windows 11 스냅 레이아웃(최대화 단추에 머무르기)은 Windows의 기본 제목 표시줄과 같게 동작한다.
- 제목 표시줄 높이는 창의 DPI에서 Windows가 쓰는 캡션 높이(`SM_CYCAPTION`과 테두리 패딩)다. 태스크의 픽셀은 창의 픽셀이므로 호스트는 이 높이를 픽셀로 게스트에 보내고(앱에게는 태스크 밀도에서 같은 높이의 dp가 된다), 게스트는 그 태스크의 위쪽 시스템 바 인셋(`WindowInsets.Type.statusBars()`, `systemBars()`, `captionBar()`)으로 앱에 준다. 앱의 툴바는 캡션 단추 아래에 놓이고, 상태 표시줄 배경은 투명한 제목 표시줄 뒤에 그려진다.
- 에이전트는 앱이 상태 표시줄에 대해 시스템에 알린 것(`APPEARANCE_LIGHT_STATUS_BARS`, 상태 표시줄 색)을 읽어, 바뀔 때마다 제어 채널로 보낸다. 호스트는 밝은 상태 표시줄 위에는 어두운 글리프를, 어두운 상태 표시줄 위에는 밝은 글리프를 그린다. 머무르기와 누르기 색은 Windows와 같게 하고, 닫기 단추는 머무를 때 빨간색이 된다. 값이 바뀌어도 깜빡이지 않도록 다음 그리기에서 한 번에 바꾼다.
- 제목 표시줄 영역의 포인터는 Windows의 것이다. 캡션 단추 위는 단추로, 나머지 띠는 끌어 옮기기 영역으로 처리하고 게스트에 주입하지 않는다. 앱은 이 띠를 시스템 바 인셋으로 받으므로 그 안에 조작할 것을 두지 않고, 띠 일부만 앱에 주면 같은 자리를 눌러도 끌기와 클릭이 섞여 예측하기 어렵기 때문이다. 띠 아래의 좌표 변환은 FR-5와 같고, 창 좌표와 게스트 좌표는 띠를 포함한 창 전체에서 같은 원점을 쓴다.
- 고대비 모드에서는 캡션 단추를 시스템 색(`COLOR_BTNTEXT`, `COLOR_HIGHLIGHT`)으로 그린다. 캡션 단추는 UI Automation에 단추로 드러나며 이름(최소화, 최대화, 복원, 닫기)을 가진다.
- 수용 기준: 100%, 150%, 200% 배율에서 게스트 앱이 받은 위쪽 상태 표시줄 인셋(px)이 호스트 창의 제목 표시줄 높이(px)와 1px 안에서 같다.
- 수용 기준: 밝은 상태 표시줄(`APPEARANCE_LIGHT_STATUS_BARS`)을 쓰는 앱의 창은 어두운 캡션 글리프를, 어두운 상태 표시줄을 쓰는 앱의 창은 밝은 글리프를 그리고, 앱이 테마를 바꾸면 글리프도 바뀐다.
- 수용 기준: 제목 표시줄 띠의 점은 캡션 단추 위에서 단추 히트 테스트 값을, 나머지에서 캡션 히트 테스트 값을 돌려주고, 띠 아래의 점은 게스트에 FR-5와 같은 좌표로 주입된다.
- 수용 기준: 실제 PC에서 최대화 단추에 머무르면 스냅 레이아웃이 뜨고, 띠를 끌면 창이 옮겨지며, 두 번 누르면 최대화와 복원이 된다. 밝은 앱과 어두운 앱 창의 캡처를 기록한다. (수동 확인)

### FR-23 설치된 앱 관리 (`Agreed`)
사용자가 게스트에 설치된 안드로이드 앱을 보고, 열고, 지울 수 있게 한다. 지금은 설치된 앱을 볼 방법이 없고, WSA는 설정의 "앱 관리"와 Windows의 설치된 앱 목록 두 곳에서 이것을 제공했기 때문이다.
- 에이전트가 사용자에게 보이는 설치된 앱(런처 대상 앱)마다 패키지 이름, 이름, 아이콘, 버전 이름과 버전 코드, 크기(앱, 데이터, 캐시), 처음 설치한 시각과 마지막 업데이트 시각, 시스템 앱 여부를 보고한다. 메시지 형식은 프로토콜 정의에서 생성한다.
- 지우기는 에이전트가 `PackageInstaller` 세션으로 한다. 시스템 앱은 지울 수 없고, 요청하면 이유와 함께 거절한다. 사용자가 설치한 앱만 지운다.
- 설정 앱에 앱 화면을 둔다. 앱마다 아이콘, 이름, 패키지 이름, 버전, 크기, 설치 날짜를 보여 주고, 검색할 수 있다. 앱마다 열기(태스크 창), 앱 정보(안드로이드의 앱 정보 화면을 태스크 창으로 연다. 권한, 저장 공간, 알림을 거기서 바꾼다), 제거(확인을 받은 뒤)가 있다. 화면은 다른 설정 화면과 같은 Fluent 설정 카드를 따른다.
- 앱 화면에 "앱 관리" 항목을 둔다. 안드로이드 설정의 앱 목록을 태스크 창으로 연다.
- 창 관리자는 시작 메뉴 항목을 맞출 때 함께 앱마다 Windows 설치된 앱 목록의 항목(`HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\Thisisthepy.DSA.<package>`)을 만든다. 값은 `DisplayName`(앱 이름), `DisplayIcon`(`%LOCALAPPDATA%\DSA\apps\<package>\`의 그 앱 창 프로그램), `DisplayVersion`, `Publisher`, `InstallDate`, `EstimatedSize`(KB), `UninstallString`(`dsa apps uninstall <package>`를 부른다), `NoModify`, `NoRepair`다. 앱을 설치, 업데이트, 제거하면 맞춘다. 창 관리자는 자기가 만든 키만 고치고 지운다.
- CLI는 `dsa apps list`, `dsa apps info <package>`, `dsa apps uninstall <package>`를 둔다. 안드로이드가 꺼져 있으면 켜고 처리한다.
- 수용 기준: 에이전트의 앱 목록 응답이 런처 대상 앱만 담고, 각 앱의 이름, 아이콘, 버전, 크기, 설치 시각, 시스템 앱 여부를 담는다.
- 수용 기준: 사용자 앱을 지우라고 하면 지워지고 결과가 성공이다. 시스템 앱이나 없는 패키지를 지우라고 하면 지우지 않고 이유를 담은 실패를 돌려준다.
- 수용 기준: 창 관리자가 앱 목록을 맞추면 앱마다 제거 키가 위의 값으로 생기고, 목록에서 빠진 앱의 키는 지워지며, 자기가 만들지 않은 키는 건드리지 않는다.
- 수용 기준: `dsa apps list`가 앱 목록을, `dsa apps info <package>`가 한 앱의 정보를 보여 주고, `dsa apps uninstall <package>`가 앱을 지운다.
- 수용 기준: 설정 앱의 앱 화면이 목록, 검색, 열기, 앱 정보, 확인 뒤 제거, 앱 관리를 보여 주며, 밝은 테마와 어두운 테마, 영어와 한국어의 화면 캡처가 CI에서 나온다.
- 수용 기준: 실제 Windows에서 APK를 설치하면 Windows 설정의 설치된 앱에 이름, 아이콘, 버전, 게시자와 함께 나타나고, 거기서 제거하면 게스트에서 지워지고 목록과 시작 메뉴에서 사라진다. DSA를 제거하면 이 항목이 모두 사라진다. (수동 확인)

### FR-24 백그라운드에서 도는 앱 (`Agreed`)
창을 모두 닫아도 포그라운드 서비스로 계속 도는 앱(음악 재생, 내려받기, VPN 등)은 사용자 눈에 보여야 하고, 사용자가 멈출 수 있어야 한다. 창이 없으면 사용자는 그 앱이 아직 돌며 메모리와 CPU를 쓰는지 알 수 없기 때문이다.
- 에이전트는 포그라운드 서비스의 시작과 끝, 그 서비스의 진행 중(ongoing) 알림, 미디어 세션을 관찰해 제어 채널로 보낸다. 메시지 형식은 프로토콜 정의에서 생성한다.
- 포그라운드 서비스를 돌리는 앱마다 Windows 알림 영역(시스템 트레이)에 아이콘 하나를 둔다. 아이콘은 앱의 아이콘이고, 도구 설명은 진행 중 알림의 제목과 본문이다. 아이콘의 정체성은 앱마다 고정된 GUID로 정해, Windows가 앱마다 표시 설정을 따로 기억하게 한다. 아이콘은 창 관리자(`dsa-wm`)가 가진다.
- 아이콘을 왼쪽 단추로 누르면 앱의 태스크 창을 연다. 오른쪽 단추 메뉴는 열기, 진행 중 알림의 동작(미디어라면 일시 정지, 다음 등이며 그 `PendingIntent`를 게스트에서 실행한다), 중지다.
- 중지는 그 앱의 패키지를 강제 중지한다. 처음에는 확인을 묻고, "다시 묻지 않음"을 고르면 다음부터 묻지 않는다. 이 선택은 설정 값이고 동반 서비스가 저장한다.
- 아이콘은 포그라운드 서비스가 시작되면 나타나고, 서비스가 끝나거나 앱이 중지되면 사라진다.
- 진행 중 알림은 반복되는 토스트로 띄우지 않고 트레이 아이콘으로만 보인다. 일반 알림은 FR-8대로 토스트로 띄운다.
- 미디어 세션을 가진 앱은 Windows 미디어 컨트롤(SystemMediaTransportControls)에 연결한다. 제목, 아티스트, 앨범 아트와 재생 상태가 Windows 미디어 플라이아웃에 보이고, 재생, 일시 정지, 다음, 이전 키를 누르면 게스트 미디어 세션의 해당 동작을 실행한다.
- DSA 설정 앱은 "백그라운드에서 실행 중" 항목에 같은 목록(앱 아이콘, 이름, 알림 제목)과 앱마다 중지 단추를 보여 준다.
- 수용 기준: 게스트 앱이 포그라운드 서비스를 시작하면 에이전트가 그 패키지, 알림 제목, 본문, 동작을 보내고, 서비스가 끝나면 끝났다고 보낸다. 진행 중 알림은 토스트로 가지 않는다.
- 수용 기준: 창 관리자는 포그라운드 서비스를 돌리는 앱마다 트레이 아이콘을 정확히 하나 두고, 같은 앱에는 늘 같은 GUID를 쓰며, 서비스가 끝나거나 앱이 중지되면 아이콘을 지운다.
- 수용 기준: 메뉴의 중지는 처음에 확인을 묻고, "다시 묻지 않음" 뒤에는 묻지 않으며, 확인하면 게스트에 그 패키지의 강제 중지를 요청한다.
- 수용 기준: 미디어 세션의 재생 상태와 메타데이터가 SystemMediaTransportControls에 반영되고, 미디어 키가 게스트 세션의 재생, 일시 정지, 다음, 이전으로 전달된다.
- 수용 기준: 설정 앱의 "백그라운드에서 실행 중" 항목이 같은 목록을 보이고, 중지 단추가 그 앱을 멈추며 목록에서 지운다.
- 수용 기준: 실제 PC에서 음악 재생을 시작하고 그 창을 닫으면 제목을 단 트레이 아이콘이 나타나고, 미디어 키가 재생을 제어하며, 중지를 누르면 재생이 멈추고 아이콘이 사라지며 그 앱의 메모리가 돌아온다. (수동 확인)

## 4. 비기능 요구사항

### NFR-1 대기 메모리 (`Agreed`)
- 제안 목표: 셸을 걷어내고 Google 서비스 계열이 없는 구성에서, `Dozing` 상태의 전체 메모리(게스트 VM이 쓰는 몫과 동반 서비스의 합)가 800MB 이하다.
- 측정 방법: 세션 시작 10분 뒤 게스트 `dumpsys meminfo`의 총 PSS, 게스트 VM의 `vmmem` 프로세스 사용량, 동반 서비스 프로세스의 작업 집합을 함께 기록한다. 측정 환경(RAM, CPU, Windows 빌드)을 같이 적는다.
- 앱을 연 상태의 목표: 단순한 앱 하나(Settings)를 연 `Active` 상태에서 DSA 호스트 프로세스 전체(VM, 창 관리자, 앱 창, 서비스)의 private 작업 집합 합이 단기 400 MiB 이하, 최종 250 MiB 이하다. 앱을 하나 더 열 때마다 늘어나는 몫은 80 MiB 이하다. `Dozing` 목표는 위와 같다.
- 측정 방법: 앱을 연 뒤 1분 동안 손대지 않고 `dsa memory`와 각 프로세스의 private 작업 집합을 기록한다. 다른 앱(예: Electron 앱)을 함께 재지 않는다.

### NFR-2 메모리 반환 (`Agreed`)
- 세션을 종료하면 게스트가 쓰던 메모리가 호스트로 돌아간다.
- 호스트 메모리 압박이 오면 게스트의 캐시 프로세스가 먼저 정리된다.
- 수용 기준: 앱 다섯 개를 열었다 닫고 세션을 종료한 뒤, 정해진 시간 안에 게스트 VM의 `vmmem` 프로세스가 차지한 메모리가 호스트로 돌아온다.
- 안드로이드에 고정된 메모리 상한을 두지 않는다. VM의 최대 메모리는 호스트의 물리 메모리에서 Windows 몫(물리 메모리의 10%와 2 GiB 중 큰 값)을 뺀 값이다. 상한이 커도 VM은 게스트가 쓰는 만큼만 잡는다(지연 커밋, 빈 페이지 보고, 차가운 페이지 회수). zram 크기와 lmkd 기준은 실제 크기에 맞춘다. 상한을 두고 싶은 사용자를 위해 `dsa settings`에 고급 설정으로 상한을 둔다.
- 수용 기준: 32 GB PC에서 게스트의 `MemTotal`이 위 식의 값에 가깝고, 같은 PC에서 3 GiB 상한일 때와 비교해 `Dozing`의 `vmmem` 상주 메모리와 부팅 시간이 눈에 띄게 늘지 않는다. (수동 확인, 수치를 기록한다)
- 앱을 닫으면 캐시로 남기지 않는다. 한 패키지의 마지막 태스크가 사라지면 에이전트가 그 패키지의 프로세스를 바로 끝내고, 풀린 메모리와 페이지 캐시를 회수해 호스트로 돌려준다. 배치된 위젯이 있거나 포그라운드 서비스가 돌고 있는 앱은 끝내지 않는다. 캐시 프로세스 수의 상한은 데스크톱에 맞게 낮춘다. 에이전트는 "closed <package>: returned N MiB in T ms"를 로그에 남긴다.
- 수용 기준: 앱 창을 닫고 몇 초 안에 그 패키지의 프로세스가 없어지고, 위 로그 줄이 남으며, `vmmem` 상주 메모리가 줄어든다. 위젯을 배치한 앱과 포그라운드 서비스가 있는 앱은 남는다.

### NFR-3 대기 CPU (`Draft`)

## 5. 경계와 프로토콜 요구사항

### PR-1 전송 계층 (`Done`)
- 제어 채널은 게스트의 vsock과 호스트의 hvsocket으로 잇는다. 호스트 코드는 전송 계층을 추상화해서 Linux(유닉스 소켓)와 macOS(vsock)를 같은 인터페이스로 붙일 수 있게 한다.
- 수용 기준: 같은 프로토콜 테스트가 실제 전송 계층과 메모리 안 가짜 전송 계층에서 모두 통과한다.

### PR-2 프로토콜 단일 소스 (`Done`)
- 제어 채널의 메시지는 한 곳에 정의하고, Rust(동반 서비스), Kotlin 또는 Java(에이전트), C++(합성기의 그래픽 부분)의 타입과 코덱을 생성한다. 손으로 쓴 직렬화 코드를 두지 않는다.
- 연결할 때 프로토콜 버전과 스키마 해시를 교환한다. 다르면 연결을 거부하고 이유를 보고한다.
- 수용 기준: 정의를 바꾸고 한쪽만 다시 생성하면 연결이 거부된다.
- 수용 기준: 체크인한 프로토콜 벡터(메시지와 그 바이트열)를 세 언어의 코덱이 똑같이 인코딩하고 디코딩한다.

### PR-3 그래픽 경로 (`Agreed`)
- 게스트의 OpenGL ES 드라이버는 모든 앱에서 ANGLE이다.
- Vulkan은 원격 방식으로 호스트에서 실행한다. gfxstream을 출발점으로, 전송 계층을 PR-1에 맞춘다.
- 호스트 렌더러는 기본으로 주 모니터를 구동하는 GPU에서 렌더링한다(INTENT D20). 다른 GPU에 연결된 모니터의 태스크 창도 이 GPU가 렌더링한다. 사용자는 설정으로 `integrated`(내장 GPU), `discrete`(외장 GPU), 또는 장치 이름의 일부를 고를 수 있다. 맞는 GPU가 없으면 gfxstream의 기본 순위로 고르고, 합성기 로그에 어느 GPU에서 렌더링하는지와 그 이유를 남긴다.
- 수용 기준: Vulkan CTS의 정해진 부분 집합과 OpenGL ES 앱 하나, Vulkan 앱 하나가 태스크 창에 올바르게 그려진다.
- 수용 기준: 활성 디스플레이 목록이 주어지면, 설정이 없거나 `display`일 때 주 모니터 어댑터의 LUID를 고르고, `integrated`, `discrete`, 장치 이름은 각각 그 규칙이 되며, 주 모니터를 찾지 못하면 기본 순위로 돌아간다. 잘못된 설정은 거부되고 기본값으로 돌아간다.
- 수용 기준: 렌더러는 요청한 규칙에 맞는 Vulkan 장치를 고르고, 맞는 장치가 없으면 기본 순위로 고르며, 어느 쪽이었는지 알려 준다.
- 측정 기준: 일반 앱 스크롤, OpenGL ES 게임, Vulkan 게임 세 가지로 프레임 시간, CPU 사용률, 게스트와 호스트 메모리를 기록한다. dxg 대안 경로를 실험하면 같은 세 가지로 비교한다.

### PR-4 호스트 HAL (`Agreed`)
- 호스트로 옮기는 HAL은 RPC Binder로 게스트와 잇는다. 처음 대상은 동영상 코덱, 오디오, 전원과 배터리다.
- 수용 기준: 게스트의 H.264 동영상이 호스트 하드웨어 디코더로 재생되고, 게스트의 오디오가 호스트 기본 출력 장치로 나온다.

### PR-5 로컬 API (`Done`)
동반 서비스(권한이 필요한 쪽)와 사용자 세션의 앱 사이의 API다(INTENT D15).
- Windows는 named pipe, Linux와 macOS는 유닉스 소켓으로 잇고, 제어 채널과 같은 프레이밍과 전송 추상화를 쓴다.
- 메시지는 한 곳에 정의하고 코덱을 생성하며, 연결할 때 프로토콜 버전과 스키마 해시를 확인한다(PR-2와 같은 규칙).
- 호출자는 운영체제가 확인한 사용자로 정해진다. 메시지에 적힌 사용자 정보는 믿지 않는다.
- 수용 기준: 같은 API 테스트가 메모리 안 가짜 전송과 실제 전송(Windows의 named pipe, Linux와 macOS의 유닉스 소켓)에서 모두 통과한다.
- 수용 기준: 다른 사용자의 프로세스는 로컬 API에 연결하지 못하거나, 연결해도 그 사용자의 안드로이드만 다룬다.

### PR-6 제어 채널 상호 인증 (`Done`)
게스트 앱이 그래픽 포트용 vsock 경로를 통해 호스트 제어 채널 포트에 무단 연결해 에이전트를 사칭하지 못하도록 부팅 단위 비밀값으로 인증한다.
- 호스트는 세션을 시작할 때마다 256비트 난수 비밀값을 만들어 게스트의 `bootconfig`로 넘긴다.
- 게스트 제어 데몬은 일반 앱이 읽을 수 없는 `/proc/bootconfig`에서 비밀값을 읽고, 호스트가 보낸 난수(nonce)에 대한 HMAC-SHA256 증명으로 핸드셰이크를 마친다. 비밀값 자체는 소켓으로 보내지 않는다.
- 수용 기준: 비밀값을 모르는 프로세스나 잘못된 비밀값, 호스트가 보낸 난수와 다른 값으로 계산한 HMAC은 `HelloRejected`로 거부되고 연결이 끊긴다.
- 수용 기준: 이전 부팅 세션의 HMAC을 재전송하면 새 부팅 세션에서 거부된다.
