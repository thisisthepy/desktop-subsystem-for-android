# INTENT

이 문서는 **왜** 이렇게 만드는지를 기록한다. 결정이 바뀌면 이 문서를 먼저 고치고, 그다음 SPEC을 고친다. 결정은 소유자가 내린다.

처음 판은 2026-10-16 소유자와의 설계 논의를 정리한 것이다. 이 판의 결정은 모두 그 논의에서 나왔다. D1과 D2는 같은 날 binder 모듈 조사 결과를 보고 소유자가 바꿨다.

## 1. 동기

- Microsoft는 Windows Subsystem for Android(WSA) 지원을 2025-03-05에 종료했다. Windows에서 안드로이드 앱을 앱별 창으로 쓰는 공식 경로가 사라졌다.
- WSA를 쓰면서 겪은 불편이 출발점이다.
  - 앱을 열 때마다 안드로이드 전체를 콜드 부팅해서 오래 기다렸다.
  - 기본 메모리 사용량이 WSL보다 훨씬 컸고, 한 번 할당받은 메모리를 놓지 않았다.
  - 전용 가상 디스크(VHDX)가 따로 필요했다.
- WSA의 핵심 부분(안드로이드 이미지, 호스트 서비스, GPU 경로, 창 통합)은 닫힌 바이너리라 커뮤니티가 고치거나 이어갈 수 없다. 안드로이드 버전과 보안 패치도 지원 종료 시점에 멈췄다.
- 그래서 **소스가 모두 열려 있고, WSA 수준의 창 통합을 갖추고, WSA보다 가볍게 상주하는** 구현을 만든다.

## 3. 핵심 결정

### D1. 안드로이드는 전용 경량 VM에서 돌린다

안드로이드는 자기 커널을 가진 경량 VM에서 돈다. Windows에서는 WSL이 VM을 만드는 것과 같은 API(Host Compute System, HCS)로 VM을 만들고, 커널을 직접 부팅한 뒤 안드로이드의 init을 바로 실행한다. 중간에 리눅스 배포판이나 LXC가 없다. ChromeOS의 ARCVM, Google의 Cuttlefish와 같은 구조다.

- 얻는 것: 커널을 우리가 정하므로 binder를 내장할 수 있다(D2). 사용자의 WSL 배포판에 아무 영향이 없고, 사용자가 WSL을 켜지 않아도 된다. 사용자의 리눅스 환경과 커널을 공유하지 않아 격리 수준이 높다. Microsoft가 WSL 커널을 바꿔도 우리가 깨지지 않는다. hvsocket으로 붙을 VM의 ID를 우리가 안다.
- 메모리: WSA가 메모리를 놓지 않은 것은 VM이라서가 아니라 설정 때문이다. WSL과 같은 HCS 메모리 설정(pagefile 기반 메모리, 첫 접근 때 커밋, 게스트의 빈 페이지 반환)과 게스트의 free page reporting으로 대기 메모리를 호스트에 돌려준다(C4).
- 디스크: 시스템 이미지는 읽기 전용 파일로 두고 업데이트 때 통째로 바꾼다. 사용자 데이터는 지운 만큼 줄어드는 sparse VHDX나 호스트 폴더 공유에 둔다. WSA의 계속 커지기만 하는 데이터 디스크를 되풀이하지 않는다.
- 치르는 것: HCS로 VM을 만들려면 관리자 권한이 필요해서, WSL의 `wslservice`처럼 SYSTEM 권한 서비스를 설치한다. VM 생성, 메모리 반환 설정, 파일 공유를 WSL에 맡기지 않고 직접 구성한다. 사용자가 WSL도 쓰면 VM이 둘이 되어 커널 하나 몫의 메모리가 더 든다(실측으로 확인한다).
- 실행 위치는 동반 서비스에서 추상화한다. WSL 공식 커널에 binder가 들어오면 WSL 컨테이너를 두 번째 실행 백엔드로 붙일 수 있다.
- 검토한 대안: WSL2 VM 안의 LXC 컨테이너(Waydroid 방식). 처음 판의 결정이었다. binder를 WSL 커널에 외부 모듈로 실을 수 없어서(D2) 기본 경로에서 뺐다. 기본 WSL 커널을 우리 커널로 바꾸는 방식은 `.wslconfig`가 사용자 단위 전역 설정이라 사용자의 모든 WSL 배포판을 바꾸고, WSL의 커널 업데이트를 끊고, 관리자 정책으로 막힐 수 있어서 뺐다.
- 검토한 대안: 기존 WSA를 Waydroid에 가깝게 수정하기. 핵심 부분이 닫힌 바이너리라서 쓸 수 있는 것이 거의 남지 않는다. WSA는 동작 명세서와 참고 자료(공개된 커널 소스)로만 쓴다.

### D2. 커널은 프로젝트가 빌드하고, 사용자는 커널을 빌드하지 않는다

사용자에게 커널 빌드나 교체를 요구하면 사용자 수는 거의 없어진다. 그래서 전용 VM(D1)의 커널을 프로젝트가 빌드해 함께 배포한다. WSL 커널 태그를 바탕으로 해서 Hyper-V 드라이버를 그대로 쓰고, binder, binderfs와 안드로이드가 요구하는 커널 설정을 설정 조각 하나로 더한다. 커널의 바탕을 WSL 태그로 할지 안드로이드 공통 커널로 할지는 커널 작업을 시작할 때 정한다.

처음 판은 binder를 기본 WSL 커널에 외부 모듈로 싣는 것이었다. 조사해 보니 업스트림 binder는 `bool`이라 모듈로 고를 수 없고, 밖에서 빌드해도 WSL 커널이 export하지 않는 심볼을 6.6에서 11개, 6.18에서 14개 쓴다. 비공개 심볼을 실행 중에 찾아 쓰는 우회는 커널 릴리스마다 깨지고 IBT와 부딪혀서 쓰지 않는다. WSL 공식 커널 설정에 binder를 넣자는 제안은 계속한다. 들어오면 WSL 컨테이너 백엔드가 가능해진다(D1).

ashmem처럼 최신 커널에서 빠지는 기능에 기대지 않는다. 커널이 크게 바뀔 때마다 깨지기 때문이다(WSL 6.6에서 ASHMEM이 빠지며 커뮤니티 설치가 깨진 일이 있다). memfd처럼 유지되는 경로만 쓴다.

### D3. 화면은 안드로이드 쪽 hwcomposer와 호스트 쪽 합성기 한 쌍으로 만든다

- 안드로이드의 freeform(자유 창) 모드로 앱 태스크마다 독립된 창 영역을 둔다.
- 커스텀 hwcomposer HAL이 레이어를 한 화면으로 합성하지 않고 태스크별로 묶어 호스트에 넘긴다.
- 호스트의 합성기가 태스크마다 진짜 호스트 창을 만든다. Windows에서는 Win32 창과 DirectComposition이다.
- 창 생성, 크기, 포커스, 입력 같은 제어 메시지는 게스트와 호스트 사이 소켓으로 오간다(Windows는 hvsocket, 게스트는 vsock).

진짜 호스트 창이라 스냅, 둥근 모서리, 다중 모니터, 모니터별 DPI가 따라온다. 창의 DPI가 바뀌면 안드로이드 쪽 화면 밀도를 바꿔 다시 그린다. 창 크기를 바꾸면 안드로이드 태스크 크기를 바꾸고, 새 프레임이 올 때까지 마지막 프레임을 늘려 보여 준다.

- 검토한 대안: WSLg 경유(C3에서 탈락). WSLDroid(`yohanesokta/WSLDroid`)처럼 자체 Weston을 RDP 백엔드로 띄우고 자체 RDP 클라이언트로 받는 방식. WSLg는 빼지만 안드로이드 전체 화면 하나를 압축해 보내는 구조라 C2를 만족하지 못한다. 그 프로젝트의 커널 CI와 설치기 흐름은 참고한다.

### D4. 그래픽은 Vulkan 하나로 모으고, 호스트에서 실행한다

- 시스템 이미지를 우리가 만들므로 모든 앱의 OpenGL ES 드라이버를 ANGLE(OpenGL ES를 Vulkan 위에서 구현하는 계층)로 고정한다. Google도 장기적으로 OpenGL ES를 ANGLE을 통해서만 제공하겠다는 방향을 밝혔다. 그러면 HWUI(Skia의 Vulkan 백엔드), 게임, Flutter, WebView가 모두 Vulkan 한 경로로 모인다.
- **주 경로는 Vulkan 원격이다.** Vulkan 호출을 직렬화해 호스트로 보내고 호스트의 실제 Vulkan 드라이버가 실행한다. Google의 gfxstream이 안드로이드 에뮬레이터에서 Windows와 macOS 호스트를 대상으로 이미 같은 일을 하므로, 새로 만들 것은 전송 계층을 호스트와 안드로이드 VM 사이(hvsocket)에 맞게 바꾸는 일이 중심이다.
- 그려진 결과가 처음부터 호스트 GPU 메모리에 있으므로 "게스트 GPU 버퍼를 VM 경계 너머로 공유하는" 문제가 생기지 않는다. 합성기는 호스트에 있는 이미지를 창에 올리기만 한다.
- **대안 경로는 dxg다.** Hyper-V의 준가상화 GPU(WSL이 쓰는 GPU-PV, 게스트의 `/dev/dxg`) 위에 게스트 Mesa 드라이버(d3d12, Dozen)를 두고 버퍼를 호스트와 공유한다. 이론상 더 빠르고 가볍지만 Dozen의 Vulkan 완성도와 경계 너머 버퍼 공유가 검증되지 않았다. 게임 성능이 중요해지면 별도로 연구한다.
- **HWUI의 Skia 명령 원격은 선택적 개선이다.** 픽셀이 아니라 Skia 그리기 명령을 넘겨 호스트 Skia가 모니터 배율에 맞춰 그리게 한다. Chromium의 out-of-process raster가 같은 구조다. 일반 View와 Compose 앱의 선명도를 올리지만, 게임, 동영상, Flutter, WebView는 버퍼로 나오므로 대체가 아니라 덧붙이는 경로다. Skia 직렬화 형식은 버전 간 호환을 보장하지 않으므로, 쓰려면 호스트 Skia를 안드로이드 이미지와 같은 커밋으로 빌드한다.
- 치르는 것: 원격 방식은 API 호출마다 직렬화 비용이 들고, GPU 메모리를 CPU에 매핑해 쓰는 앱은 Hyper-V가 호스트 GPU 메모리를 게스트에 직접 매핑해 주지 않아 복사와 동기화가 필요하다. 일반 앱에서는 차이가 작고 3D 게임에서 커진다. 동영상 디코딩은 Vulkan과 별개라 따로 경로를 만든다(D5).

### D5. 경계는 HAL에 둔다. ART와 프레임워크는 게스트에 남긴다

VM 안에서도 CPU 연산과 메모리 접근은 하드웨어 가상화로 거의 네이티브 속도다. VM에서 비싼 것은 장치 입출력이다. 그래서 장치만 호스트로 옮긴다.

- 게스트에 남는 것: 리눅스 커널, ART, 안드로이드 프레임워크
- 호스트로 옮기는 것: HAL 아래의 장치. 그래픽 합성(D3), Vulkan(D4), 동영상 코덱, 오디오, 카메라, 전원과 배터리, 클립보드, 위치
- HAL은 원래 안드로이드와 하드웨어 사이의 경계로 설계된 곳이라 호출 빈도가 낮고 인터페이스가 명확하다. 안드로이드의 RPC Binder로 HAL 서비스를 호스트 쪽 프로세스와 소켓으로 잇는다.
- 검토한 대안: ART를 호스트에서 돌리고 시스템 콜만 게스트 커널로 넘기기. 시스템 콜이 초당 수만 번이고, mmap, 페이지 폴트, futex, 스레드, 시그널, binder처럼 프로세스 주소 공간에 묶인 호출은 넘길 수 없다. 결국 호스트가 리눅스 시스템 콜을 직접 구현하는 구조, 즉 WSL1이 되고, 그 전신인 Project Astoria와 WSL1은 호환성과 성능 문제로 Microsoft가 접었다.
- 검토한 대안: ART를 GraalVM으로 바꾸기. 앱은 JVM이 아니라 DEX 바이트코드이고 `android.*` 프레임워크에 기댄다. GraalVM Native Image는 빌드할 때 모든 코드를 알아야 해서 APK를 나중에 설치하는 모델과 맞지 않는다. ART는 이미 AOT 컴파일과 미리 컴파일된 boot image를 쓴다.

### D6. 셸은 호스트가 맡는다

호스트 데스크톱이 셸이므로 안드로이드의 셸을 걷어낸다.

- 런처: 앱 실행은 시작 메뉴가 맡는다.
- SystemUI: 알림은 호스트 알림 센터로, 상태바는 필요 없다.
- 키보드 앱: 입력은 호스트 IME가 맡는다. Windows에서는 동반 서비스가 TSF(Text Services Framework)로 한글 조합을 처리하고, 조합 중인 글자와 확정된 글자를 안드로이드 에이전트가 앱의 `InputConnection`에 넣는다.

셸 통합(시작 메뉴 등록, 작업 표시줄의 앱별 구분, 알림, 링크와 파일 연결)은 두 구성 요소가 맡는다. 게스트의 **안드로이드 에이전트**(시스템 앱)가 앱 목록, 아이콘, 알림, Intent를 넘기고, 호스트의 **동반 서비스**가 앱마다 고유한 ID(Windows에서는 AppUserModelID)로 등록하고 표시한다.

### D7. 기본 대기 상태는 Doze다. freeze는 선택지다

| 단계 | 상태 | 알림·위젯·알람 | CPU | 메모리 |
|---|---|---|---|---|
| 1 | 활성: 안드로이드 창이 떠 있다 | 동작 | 사용 | 사용 |
| 2 | 화면 꺼짐 + Doze (기본 대기) | 동작(Doze 유지보수 시간) | 거의 0 | 유지, 호스트가 회수 가능 |
| 3 | freeze: 오래 안 쓰거나 사용자가 완전 절전을 고름 | 멈춤 | 0 | 유지, 호스트가 회수 가능 |
| 4 | 종료 | 멈춤 | 0 | 반환 |

- 게스트에는 실제 화면과 배터리가 없어서 Doze가 저절로 들어가지 않는다. 에이전트가 신호를 만든다. 안드로이드 창이 모두 닫히거나 최소화되면 "화면 꺼짐"을 알리고, 창이 다시 열리면 "화면 켜짐"으로 돌아간다. 호스트의 배터리와 절전 상태를 안드로이드 배터리 상태에 반영한다.
- freeze(cgroup freezer)는 Waydroid에서 가져온 아이디어지만 기본값으로 두지 않는다. 얼어 있는 동안 메신저 푸시, 위젯 갱신, 알람, 동기화가 모두 멈춰서 셸 통합(D6)과 충돌한다.
- 검토한 대안: 부팅이 끝난 상태를 스냅샷으로 저장해 두었다가 복원하기(안드로이드 에뮬레이터의 Quick Boot). RAM 크기만큼 디스크를 쓰고, 이미지나 설정이 바뀌면 무효가 되고, 그 사이 디스크가 바뀌면 메모리와 어긋나고, 호스트 GPU 상태를 저장할 수 없고, 시계가 점프한다. 사용자 제품에서는 이 경우를 자주 만난다.

### D8. 메모리는 줄이고, 상주 여부는 기기에 맞춘다

- 셸 제거(D6), 64비트 전용 구성(32비트 Zygote 제거), 안드로이드 저사양 기기 설정, 캐시 프로세스 수 축소, 메모리 압박(PSI) 기반 정리로 대기 메모리를 줄인다.
- 32비트 앱은 지원하지 않는다. 32비트 런타임과 Zygote를 유지하면 메모리가 늘어나고, 바탕으로 삼는 AOSP Cuttlefish 공개 빌드 타깃도 64비트 전용(`aosp_cf_x86_64_only_phone`)이다(D14).
- 안드로이드는 "남는 RAM은 낭비"라는 정책으로 캐시 프로세스를 남겨 둔다. VM 안에서는 호스트의 메모리 압박을 모르므로 이 정책을 그대로 두면 메모리를 놓지 않는다. 그래서 캐시 정책을 호스트 기준으로 조인다.
- 추정치(실측 전): 셸을 걷어낸 대기 상태에서 전체 약 500~800MB, Google 서비스 계열을 넣으면 0.7~1.2GB. 메신저 앱 하나를 띄워 두는 체급이다. 실측으로 확인한다(SPEC NFR-1).
- RAM 16GB 이상이면 로그인 때 백그라운드로 시작해 Doze로 상주하는 것을 기본으로 한다. 8GB면 필요할 때 시작하고 오래 안 쓰면 종료하는 것을 기본으로 한다.
- 작업 관리자에는 메모리가 우리 앱이 아니라 VM의 `vmmem` 프로세스로 보인다(HCS는 WSL의 `VmmemWSL`처럼 이름에 접미사를 붙일 수 있다). 동반 앱에서 안드로이드가 실제로 쓰는 메모리를 보여 준다.

### D9. Windows를 먼저 만들고, 프로토콜과 게스트는 플랫폼 중립으로 둔다

게스트(안드로이드 이미지, 에이전트, HAL 클라이언트)와 프로토콜은 플랫폼과 무관하다. 플랫폼마다 바뀌는 것은 호스트뿐이다.

| 계층 | Windows | Linux | macOS |
|---|---|---|---|
| 안드로이드 실행 위치 | 전용 경량 VM (HCS) | VM 없이 호스트 커널 위 컨테이너 | 전용 경량 VM (Apple Virtualization) |
| 전송 계층 | hvsocket | 유닉스 소켓 | vsock |
| GPU | 원격 → 호스트 Vulkan | 원격 불필요, 호스트 GPU 직접 | 원격 → MoltenVK |
| 창 | Win32 + DirectComposition | Wayland | NSWindow + Metal |
| IME | TSF | Wayland 텍스트 입력 | macOS 텍스트 입력 |

호스트 코드는 공통 계층(`host/core`)과 플랫폼 계층(`host/platform/<os>`)으로 나눈다. Linux와 macOS는 계획 단계이고 구현하지 않았다. Apple Silicon과 Windows on ARM에서는 대부분의 안드로이드 앱이 번역 계층 없이 돈다.

### D10. 언어

- 호스트 동반 서비스와 공통 계층: Rust
- 그래픽 경로(gfxstream 이식, 합성기의 그래픽 부분): C++. gfxstream과 AOSP 코드에 맞춘다.
- 게스트 에이전트: 안드로이드 시스템 앱(Kotlin 또는 Java)
- 게스트 제어 채널 데몬: Rust. 게스트에서 호스트와의 제어 채널(vsock)은 이 데몬 하나가 열고, 에이전트와 커스텀 hwcomposer는 게스트 안의 binder로 데몬과 통신한다. 에이전트가 다시 시작해도 연결이 유지되고, 버전과 스키마 해시 확인이 한 곳에서 끝난다. 호스트와 같은 전송 계층 코드(프레이밍, 검사 묶음)를 그대로 쓴다.
- 게스트 HAL: AOSP 관례를 따른다.
- 프로토콜: 한 곳에 정의하고 각 언어의 타입을 생성한다(SPEC PR-2). 정의 형식은 proto3이고, 세 언어가 같은 바이트를 내도록 map, `Any`, unknown field에 기대는 기능을 쓰지 않는다. 프로토콜 버전은 정의 안의 enum으로, 스키마 해시는 정의를 정규화한 텍스트의 SHA-256으로 생성해 각 언어에 상수로 넣는다.
  - 다시 검토할 시점: 호스트 HAL(D5) 때문에 libbinder의 RPC Binder를 Windows로 옮기게 되면(M7), 제어 채널도 Stable AIDL로 합칠지 검토한다. Stable AIDL은 Rust, Java, C++ 코드를 생성하고 인터페이스 버전과 해시 확인이 내장되어 있지만, 지금은 Windows용 libbinder가 없다.

### D11. 이름

정식 이름은 **Desktop Subsystem for Android™**, 약칭 DSA다. 저장소는 `desktop-subsystem-for-android`, 코드 폴더는 `dsa/`다.

- "Windows"를 넣지 않는다. Microsoft 상표 가이드라인은 자사 상표를 제3자 제품 이름에 넣거나 변형하는 것을 금지한다.
- Google의 Android 브랜드 가이드라인이 권하는 "for Android" 형태다. 처음 나올 때 "for Android™"로 쓰고 "Android is a trademark of Google LLC." 문구를 붙인다.
- WSApp처럼 WSA를 잇는 이름은 Microsoft 제품의 후속작처럼 보여 혼동 소지가 있다. "Droid"는 Lucasfilm 상표라 피한다.
- "Desktop"은 Linux와 macOS로 넓힐 여지(D9)와 맞는다. 당분간은 Windows 전용임을 README에 밝힌다.
- DSA는 흔한 약자라 검색에 약하다. 저장소 이름은 약자 대신 전체 이름을 쓴다.

### D12. 공개는 develop에서 release를 거쳐 main으로 한 방향이다

`develop`에서 작업한다. `develop`에 push하면 CI가 기획 문서(`PROJECT.md`, `AGENTS.md`, `CLAUDE.md`, `docs/` 바로 아래 파일)를 뺀 `release` 브랜치를 만들고, `release`에서 `main`으로 가는 PR을 연다. 개발자가 그 PR을 머지한다. compose-rust의 방식과 스크립트를 그대로 가져왔다.

저장소가 공개라면 `develop`은 누구나 볼 수 있다. 이 흐름은 기획 문서를 숨기는 장치가 아니라 `main`을 사용자용으로 깔끔하게 두는 장치다.

### D13. 안드로이드 위젯을 호스트 데스크톱에 띄운다

에이전트가 위젯 호스트(`AppWidgetHost`)가 되어 위젯마다 작은 화면 영역에 그리고, 화면 경로(D3, D4)로 호스트에 넘긴다. 위젯은 테두리 없는 작은 창 하나다. 위젯 연결에는 시스템 권한이 필요한데, 에이전트가 시스템 앱이라 가능하다.

- Windows에서는 바탕화면 층에 붙인 창으로 띄운다. Rainmeter가 쓰는 방식이지만 공식 API가 아니라 Windows 업데이트 때 깨질 위험이 있다.
- 검토한 대안: Windows 11 위젯 보드. 서드파티 위젯은 Adaptive Cards 템플릿으로만 그릴 수 있어서 안드로이드 위젯의 자유로운 레이아웃과 상호작용을 옮길 수 없다.
- Doze(D7) 상태에서도 위젯은 안드로이드의 갱신 주기에 맞춰 갱신된다. freeze 상태에서는 마지막 화면을 보여 준다.

### D14. 게스트 이미지는 AOSP의 공개 빌드 재료로 만들고, 최신 두 버전을 지원하며 자동으로 올린다

- 바탕: Google의 가상 기기 Cuttlefish(x86_64 전용 구성)의 AOSP 빌드를 출발점으로 삼는다. Cuttlefish는 VM에서 도는 기기이고, 이미 gfxstream(Vulkan 원격)과 ANGLE을 쓴다(D4).
- 만드는 방법: AOSP 전체를 빌드하지 않는다. Google CI가 공개하는 해당 버전의 빌드 재료(`target_files`)와 이미지 도구(`otatools`)를 고정한 빌드 번호로 받아, 우리가 바꾼 뒤 다시 묶는다.
  - 뺀다: 런처, SystemUI, 키보드 앱(D6).
  - 넣는다: 에이전트, 채널 데몬, hwcomposer(NDK와 안정 바인더 인터페이스로 따로 빌드한다), SELinux 정책, Hyper-V 디스크에 맞춘 마운트 설정, 우리 커널(D2).
  - 바꾼다: user 빌드 설정으로 바꾸고, 모든 APK와 이미지를 프로젝트 키로 다시 서명한다. 공개 빌드는 비밀 키가 공개된 AOSP test-keys로 서명되어 있어 그대로 배포하면 누구나 시스템 권한 앱을 만들 수 있기 때문이다.
  - 이 과정은 몇 시간짜리 AOSP 빌드가 아니라서 공개 CI에서 돈다.
- 예비 경로: Google이 지원 버전의 빌드 재료를 더 공개하지 않거나, 보안 업데이트를 우리가 필요한 때 받을 수 없으면 같은 기기 정의로 AOSP를 직접 빌드한다. 이때는 별도 빌드 머신이 필요하다.
- 지원 버전: 안드로이드 최신 메이저 버전과 그 바로 전 버전, 두 개를 지원한다. 새 메이저 버전이 나오면 가장 오래된 지원 버전이 빠진다. 지원 버전마다 같은 과정으로 이미지를 따로 만든다.
- 자동 업데이트: 동반 서비스가 서명된 릴리스 목록을 확인해, 같은 메이저 버전의 보안 업데이트와 다음 메이저 버전으로의 업그레이드를 받는다. 지원이 끝나는 버전의 사용자는 다음 버전으로 올린다.
  - 시스템 이미지는 읽기 전용 파일이라 통째로 바꾼다. 새 이미지가 정상 부팅할 때까지 이전 이미지를 지우지 않고, 부팅에 실패하면 이전 이미지로 되돌린다.
  - 사용자 데이터는 안드로이드가 OTA 업그레이드 때와 같은 방식으로 첫 부팅에서 옮긴다. 안드로이드는 데이터의 버전 내림을 지원하지 않으므로, 메이저 버전을 내리는 업데이트는 없다.
  - 이미지는 프로젝트 키로 서명하고, 업데이트는 서명을 확인한 뒤에만 적용한다.
- 검토한 대안: LineageOS(Waydroid 이미지) 기반. 실제 기기 지원과 런처·UI 기능이 강점이지만 우리는 셸을 걷어내고(D6), Waydroid 이미지는 LXC 컨테이너를 전제로 만들어져 VM 구조(D1)와 맞지 않으며, AOSP보다 버전을 늦게 따라온다.
- 검토한 대안: 공개 이미지를 받은 그대로 배포하기. test-keys 서명, D6에 어긋나는 셸 앱, 디버그(userdebug) 설정이 그대로 남는다.
- 검토한 대안: 처음부터 AOSP를 직접 빌드하기. 지원 버전마다 수 시간과 수백 GB가 드는 빌드 머신이 필요하다. 예비 경로로 남긴다.

### D15. 권한이 필요한 일은 서비스가 하고, 사용자 쪽 앱은 로컬 API로 요청한다

VM이나 컨테이너를 만드는 일은 대부분 높은 권한이 필요하다. 그래서 그 일을 하는 서비스와, 사용자 세션에서 도는 앱(시작 메뉴, 합성기, 설정 화면)을 나누고, 둘은 로컬 API로 통신한다.

- 로컬 API는 한 곳에 정의하고(제어 채널처럼 proto3), 제어 채널과 같은 프레이밍과 전송 추상화 위에 올린다. 플랫폼마다 바뀌는 것은 소켓의 종류뿐이다.
- 호출자가 누구인지는 메시지가 아니라 운영체제가 알려 준다. 서비스는 그 사용자 몫의 안드로이드(VM 또는 컨테이너)만 다룬다.

| | Windows | Linux | macOS |
|---|---|---|---|
| 권한이 필요한 쪽 | SYSTEM 서비스(HCS는 관리자만 VM을 만든다) | systemd 시스템 서비스(컨테이너 생성) | 없음. Virtualization 프레임워크는 권한 없는 앱도 VM을 만든다(entitlement 필요) |
| 안드로이드를 띄우는 곳 | 서비스 | 서비스 | 사용자별 launchd 에이전트 |
| 로컬 API | named pipe. DACL로 SYSTEM과 로그인 사용자만 연다 | 유닉스 소켓 `/run/dsa/host.sock` | 사용자 Application Support 아래 유닉스 소켓(권한 0700 폴더) |
| 호출자 확인 | 파이프 클라이언트 가장(impersonation) | `SO_PEERCRED` | `LOCAL_PEERCRED` |

- 검토한 대안: COM. Windows 표준이고 WSL이 쓰지만 Rust에서 다루기 복잡하고 코드가 많다. localhost TCP. 네트워크에 노출되고 권한을 운영체제가 강제하지 못한다. macOS의 XPC. 플랫폼 표준이지만 유닉스 소켓을 쓰면 Linux와 코드 경로가 하나다.

### D16. Windows 설치 파일은 MSI이고, 우리 화면을 가진 setup.exe로 감싼다

- 설치 본체는 WiX로 만든 MSI다. SYSTEM 서비스 등록과 제거를 MSI가 직접 하고, 회사 배포 도구(Intune, GPO)에서 그대로 쓸 수 있다. WiX는 빌드 도구라 우리 라이선스에 영향이 없다.
- 사용자가 실행하는 것은 WiX Burn으로 만든 setup.exe다. 화면은 Burn의 관리 코드 부트스트래퍼로, Windows에 내장된 .NET Framework 4.7.2 위의 WPF로 만든다. Windows 10 1803 이후와 Windows 11에는 이 런타임이 들어 있어서 사용자가 따로 받을 것이 없다.
- 기본 부트스트래퍼에 테마를 입히는 방식은 쓰지 않는다. 컨트롤이 옛 Win32 모양이고 Mica, 둥근 모서리, 다크 모드, 직접 그린 타이틀바를 쓸 수 없어 Windows 11의 Fluent 화면을 만들 수 없다.
- 가상 머신 플랫폼이 꺼져 있으면 설치 화면이 무엇을 켜야 하는지 알려 준다(SPEC FR-1). 설치 파일이 몰래 켜지는 않는다.
- 동반 앱의 UI 프레임워크(PROJECT Q6)가 정해지면 설치 화면도 그 프레임워크로 옮길 수 있다.
- 검토한 대안: MSIX. 서명이 필수이고 SYSTEM 서비스를 넣는 데 제약이 크다. Inno Setup. 단순하지만 MSI가 아니라 회사 배포 도구와 맞지 않는다. Advanced Installer, InstallShield. 상용이라 공개 CI에서 재현할 수 없다. WinUI 3 화면. Windows App SDK 런타임을 따로 설치해야 한다. C++ Win32로 직접 그리기. 런타임은 필요 없지만 컨트롤을 모두 손으로 그려야 해 코드가 크게 늘어난다.

### D17. Waydroid의 이미지와 도구에 기대지 않는다

- Waydroid는 참고 자료로만 본다. 그 코드, 이미지, 도구를 의존성으로 쓰지 않는다.
- 쓸 자리가 없다. Waydroid의 실행 도구는 LXC 컨테이너를 다루는데, 우리는 전용 VM을 쓴다(D1). Waydroid 이미지는 LineageOS 기반이고 컨테이너를 전제로 만들어졌는데, 우리는 AOSP 기반 이미지를 쓴다(D14). 화면은 Wayland 컴포지터를 거치지 않고 우리 hwcomposer가 호스트 창으로 넘긴다(D3).
- Waydroid의 도구는 GPL-3.0이고 이 저장소는 Apache-2.0이다. 코드를 가져오지 않으므로 라이선스가 섞이지 않는다. 아이디어(예: 대기 중 freeze, D7)는 가져올 수 있지만 구현은 이 저장소에서 새로 한다.

### D18. 프로그램도 서명된 목록으로 자동 업데이트한다

이미지만 자동으로 올라가고 프로그램(서비스, `dsa` 명령, 설치 파일)은 사용자가 직접 새 설치 파일을 받아야 하면, 고친 내용이 사용자에게 늦게 닿는다. 그래서 서비스가 이미지와 같은 방식으로 프로그램도 올린다.

- 릴리스에 프로젝트 키로 서명한 프로그램 목록을 둔다. 목록은 새 버전, 설치 파일의 주소, 크기, SHA-256을 담는다. 서비스는 서명과 해시를 확인한 설치 파일만 실행한다.
- 서비스는 받은 설치 파일을 조용히(`/quiet /norestart`) 실행한다. 설치가 서비스를 멈추고 바꾼 뒤 다시 시작하므로, 설치 파일은 서비스와 따로 떨어진 프로세스로 띄운다.
- 서비스가 멈추면 안드로이드도 멈추므로, 어떤 사용자의 안드로이드도 돌고 있지 않을 때 적용한다. 돌고 있으면 기다리고, 사용자는 `dsa update`로 바로 적용할 수 있다. 적용 전후를 사용자에게 알린다.
- 버전을 내리는 업데이트는 없다. MSI 업그레이드가 실패하면 이전 버전이 그대로 남고, 서비스가 다시 뜬 뒤 실패를 알린다.
- 회사 배포처럼 업데이트를 따로 관리하는 곳을 위해 설정으로 끌 수 있다.
- 검토한 대안: 새 버전이 있다고 알리기만 하기. 구현은 가장 작지만 사용자가 결국 직접 받아야 한다. winget이나 Microsoft Store에 맡기기. 사용자가 그 도구를 쓰고 있어야 하고, 게시 절차가 우리 손을 떠난다.

### D19. 표시 경로의 순서와 합성기

2026-10-24 표시 경로 설계 검토에서 결정한 내용이다. 화면 구성(D3)과 서비스 분리(D15)를 구체화하고 확장한다.

- **순서**: 임시 CPU 프레임 복사 경로를 두지 않는다. 창 작업(M3)은 그래픽 원격(M2, hvsocket 위의 gfxstream)이 동작할 때까지 기다린다. 첫 번째 창부터 gfxstream으로 렌더링한 프레임을 띄운다. 버려질 임시 복사 경로를 만드는 비용을 피하기 위함이다. M2는 PROJECT.md에서 M3 앞에 유지한다.
- **레이어의 태스크 묶기**: D3에 적힌 대로 처음부터 단일 freeform 디스플레이를 쓴다. 커스텀 hwcomposer가 에이전트가 보고하는 태스크 ID와 경계 영역(bounds)을 써서 레이어를 태스크별로 묶는다. 태스크마다 가상 디스플레이(virtual display)를 두지 않는다.
- **합성기로의 프레임과 스트림 경로**: 사용자 세션의 합성기가 hvsocket으로 게스트에 직접 연결한다. SYSTEM 서비스가 `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Virtualization\GuestCommunicationServices` 아래에 hvsocket 서비스 GUID를 등록하고 로그인 사용자에게 접근 권한을 부여한다. 설치기나 서비스가 레지스트리 권한을 부여하는 비용을 치르고, 호스트에서 프레임마다 거치는 불필요한 복사 단계를 하나 줄인다. 제어와 수명 주기는 여전히 서비스와 로컬 API(D15)를 거친다.
- **합성기 수명 주기**: `dsa-compositor`는 사용자 로그인 시점에 시작해 백그라운드에서 대기한다. 대기 중 메모리는 약 15~25 MB 수준이다. 창을 띄울 때 프로세스 기동 지연을 없애 창 표시 시간(NFR-4)을 빠르게 하기 위함이다.
- 검토한 대안: 임시 CPU 프레임 복사 경로. 그래픽 원격(M2) 전에 창을 먼저 띄워 볼 수 있지만, M2가 완성되면 버려질 중복 코드를 작성하는 비용이 든다.
- 검토한 대안: 태스크마다 가상 디스플레이 두기. 안드로이드 프레임워크에서 가상 디스플레이를 관리하는 오버헤드가 크고, D3의 단일 freeform 디스플레이 구조에서 에이전트 정보로 레이어를 묶는 편이 단순하다.

### D20. 호스트는 기본으로 화면이 연결된 GPU에서 렌더링하고, 설정으로 다른 GPU를 고를 수 있다

2026-10-26 소유자가 결정한 내용이다. 호스트에서 Vulkan을 실행하는 방식(D4)을 구체화한다.

- 배경: 호스트 렌더러(gfxstream)는 GPU를 스스로 고를 때 외장 GPU에 점수를 더 준다(외장 2000점, 내장 1000점). 화면이 내장 GPU에 연결된 노트북(예: NVIDIA GeForce RTX 4050 Laptop GPU와 Intel Arc Graphics, 화면은 Intel 쪽)에서는 외장 GPU가 골라진다. 그러면 모든 프레임이 GPU 사이를 건너고, 외장 GPU가 깨어 있게 된다. 이 선택은 DSA가 정한 것이 아니었고, 결정으로 남은 적도 없다.
- 기본: 주 모니터를 구동하는 어댑터(GPU)에서 렌더링한다. 합성기가 주 모니터 어댑터의 LUID를 찾고, 렌더러는 `VkPhysicalDeviceIDProperties::deviceLUID`가 같은 Vulkan 장치를 고른다. 프레임이 GPU를 건너지 않고, 외장 GPU를 깨우지 않는다.
- 다른 모니터의 창: 렌더러는 GPU 하나만 쓴다. 그래서 다른 GPU에 연결된 모니터에 있는 태스크 창도 주 모니터의 GPU가 렌더링하고, 그 창의 프레임은 Windows가 GPU 사이로 옮긴다.
- 설정: 사용자가 렌더링 GPU를 고를 수 있다. 값은 `display`(기본), `integrated`(내장 GPU), `discrete`(외장 GPU, 예: 게임), 또는 장치 이름의 일부다. 렌더러가 시작할 때 고르므로, 바꾼 값은 합성기가 다시 시작할 때 적용된다.
- 맞는 장치가 없으면(원격 데스크톱처럼 주 모니터가 GPU에 연결되어 있지 않거나, 이름이 어느 장치와도 맞지 않을 때) gfxstream의 기본 순위로 고르고, 그 사실을 합성기 로그에 남긴다.
- 검토한 대안: gfxstream의 기본 순위를 그대로 쓰기(외장 우선). 성능이 높은 GPU를 쓰지만, 하이브리드 노트북에서 프레임마다 GPU를 건너고 전력이 더 든다.
- 검토한 대안: 항상 내장 GPU. 전력은 적지만, 화면이 외장 GPU에만 연결된 데스크톱이나 MUX 노트북에서는 오히려 GPU를 건넌다.
- 검토한 대안: 창마다 그 창이 있는 모니터의 GPU에서 렌더링하기. GPU를 건너는 일이 가장 적지만, GPU마다 렌더러가 하나씩 있어야 하고, 창이 모니터를 옮길 때 게스트의 리소스를 다른 GPU로 옮겨야 한다.

## 5. 알려진 비용

- 안드로이드 VM을 만들 SYSTEM 권한 서비스를 설치하고 유지해야 한다(D1).
- 커널을 프로젝트가 빌드하고, 보안 패치를 따라가야 한다(D2).
- 사용자가 WSL도 쓰면 VM이 둘이 되어 커널 하나 몫의 메모리가 더 든다(D1).
- Vulkan 원격은 호출 오버헤드와 매핑 메모리 복사가 있다. 3D 게임에서 dxg 경로보다 느릴 수 있다.
- 동영상 디코딩 경로를 따로 만들어야 한다.
- Google Play 서비스가 없으면 상당수 앱이 돌지 않거나 기능이 빠진다(C6).
- 바탕화면 위젯은 비공식 Windows 동작에 기댄다(D13).
- 게스트 이미지는 Google이 공개하는 빌드 재료에 기댄다. 공개가 끊기면 수 시간, 수백 GB짜리 직접 빌드로 넘어가야 한다. 지원 버전이 두 개라 이미지 만들기와 확인이 두 배다(D14).
